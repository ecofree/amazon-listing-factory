## 2. 效率瓶颈清单

按 **实际浪费时间** 降序排列。所有数据均来自实测。

### 瓶颈 #1: stale download artifacts 错误导致的大规模死等

| 属性 | 值 |
|------|-----|
| **浪费时间** | **351.1 分钟 (5 小时 51 分)** -- 4 个任务合计 |
| **单任务浪费** | 47.4 - 115.3 分钟 (随队列位置递增) |
| **根因** | download 完成后 47ms 内即报 `ImageGenerationError: Download artifacts are stale or incomplete`，说明 download manifest 路径解析与 generate 阶段的 artifact 查找之间存在竞态条件 |
| **影响范围** | 4/5 任务 (80%) |
| **质量风险** | **无** -- 这是纯 bug，修复后行为不变 |
| **位置** | download 与 generate 之间的 artifact 路径解析逻辑 |

**详细分析**:

| 任务 | 错误检测时间 | 死等到成功 generate 的时间 | 浪费分钟 |
|------|------------|--------------------------|---------|
| B0F37XBR17 | 13:33:34 | 47.4 分钟 | 47.4 |
| B0FLV3625W | 13:37:55 | 84.8 分钟 | 84.8 |
| B0FKH8HFNP | 13:40:09 | 103.6 分钟 | 103.6 |
| B0F1T8BMMP | 13:41:17 | 115.3 分钟 | 115.3 |

死等时间随任务提交顺序递增，表明存在**队列复合效应** -- 后续重试任务需要等待更长时间。B0GSVF9S8P 因 download 耗时 82 分钟 (自然同步屏障) 而避开了此 bug。

### 瓶颈 #2: Apify 子 ASIN 串行抓取

| 属性 | 值 |
|------|-----|
| **浪费时间** | **2-10 分钟/任务** (取决于子 ASIN 数量) |
| **根因** | `apify.py:86-103` 中 `for variant in variants:` 循环逐一抓取每个子 ASIN，每个 Apify 轮询间隔 5s，超时 300s |
| **实测数据** | tree/6ch (6 子 ASIN) 抓取 32.7 分钟; cabinet (2 子 ASIN) 抓取 3.6 分钟 |
| **质量风险** | **无** -- 纯数据抓取，与图片质量无关 |
| **位置** | `core/source_fetch/apify.py` 第 86-103 行 |

**详细分析**:

tree 类 4 个任务的 fetch 完成时间几乎相同 (13:34 - 13:40)，表明它们被合并到同一个 Apify 抓取批次中串行执行。6 子 ASIN 的 B0F37XBR17 抓取 32.7 分钟，而只有 2 子 ASIN 的 B0FKH8HFNP 也抓取了 97.4 分钟 -- 后者等待时间更长说明被排在了队列后段。

## 3. 优化方案

### 3.1 零风险优化 (纯机械改动，不影响质量)

#### 优化 A: 修复 stale download artifacts 竞态 bug

- **内容**: 排查 download manifest 路径写入与 generate 阶段 artifact 查找之间的竞态条件。download 完成后 47ms 即触发 stale 错误，说明 generate 阶段可能读取了旧 manifest 或路径不一致。
- **实现方式**:
  1. 在 generate 阶段启动前增加 manifest 一致性校验 (检查文件是否存在、时间戳是否匹配)
  2. 如果 manifest 确实 stale，立即触发重新 download 而非等待重试队列
  3. 或在 download 写入 manifest 时使用原子写入 (先写 `.tmp` 再 `rename`)
- **预期收益**: 消除 351.1 分钟浪费 (5.85 小时)，占批次总耗时的 60%
- **质量影响**: **无** -- 修复后 pipeline 正常执行，生成结果完全一致
- **实施难度**: 中等 (4-8 小时)
- **风险**: 低

#### 优化 B: Apify 子 ASIN 并行抓取

- **内容**: 将 `apify.py` 中的 `for variant in variants:` 循环改为 `ThreadPoolExecutor` 并行执行
- **实现方式**:
  1. 使用 `ThreadPoolExecutor(max_workers=min(4, len(variants)))` 并行启动 Apify Actor
  2. 每个线程独立轮询完成状态
  3. 已有的 `ApifyClient` token 轮换和 429 重试机制无需修改
- **预期收益**: 6 子 ASIN 任务 fetch 从 32.7 分钟降至 ~10 分钟 (节省 ~23 分钟); 总节省 2-10 分钟/任务
- **质量影响**: **无** -- 只改变数据获取的并行度，获取的数据完全相同
- **实施难度**: 低 (2-4 小时)
- **风险**: 需关注 Apify rate limit (已有 429 处理)

#### 优化 C: Gemini QA 响应缓存

- **内容**: 为 QA 阶段的 Gemini 调用增加基于内容哈希的缓存
- **实现方式**:
  1. 缓存 key = SHA256(图片文件) + SHA256(prompt) + 模型版本
  2. 缓存存储于磁盘 (JSON 或 SQLite)
  3. 命中时直接返回缓存结果，跳过 Gemini API 调用
  4. 与已有的 visual brief 缓存 (`image_generation.py:2869-2969`) 采用相同策略
- **预期收益**: 重跑任务节省 1-3 分钟; 首次运行无影响
- **质量影响**: **无** -- 相同输入产生相同输出
- **实施难度**: 低 (2-3 小时)
- **风险**: 无

#### 优化 D: 提高 QA 并行度默认值

- **内容**: 将 `_qa_workers` 默认值从 `min(4, ...)` 提高到 `min(8, ...)`
- **实现方式**:
  1. 修改 `vision_qa.py:315-324` 中的默认上限
  2. 保留 `AMAZON_FACTORY_QA_WORKERS` 环境变量覆盖能力
- **预期收益**: 20+ 张图片任务 QA 阶段提速 1.5-2x (节省 2-5 分钟/任务)
- **质量影响**: **无** -- 更多 worker 并行执行相同的 QA 检查
- **实施难度**: 极低 (10 分钟)
- **风险**: 需确认 Gemini API 并发限制 (已有 endpoint 负载均衡)

#### 优化 E: 图片下载并行化

- **内容**: 将 `asset_manager.py` 中的图片下载循环改为并行
- **实现方式**:
  1. 使用 `ThreadPoolExecutor(max_workers=8)` 并行下载同一子 ASIN 的所有图片
  2. 与同文件中 role assignment 已使用的线程池模式一致 (第 223 行)
- **预期收益**: 每个子 ASIN 节省 10-80 秒; 多子 ASIN 任务总节省 1-5 分钟
- **质量影响**: **无** -- 纯 I/O 操作
- **实施难度**: 低 (1-2 小时)
- **风险**: 无

#### 优化 F: 角色一致性校验 (guard) 增加缓存

- **内容**: 为 `_role_consistency_guard_data` 的 Gemini 调用增加缓存
- **实现方式**:
  1. 缓存 key = 图片 SHA256 + 角色分类配置哈希
  2. 与优化 C 共享缓存基础设施
- **预期收益**: 重跑任务节省 15-30 秒/任务
- **质量影响**: **无** -- 相同图片 + 配置 = 相同校验结果
- **实施难度**: 低 (1-2 小时，可与优化 C 合并实现)
- **风险**: 无

#### 优化 G: 流式 QA manifest 批量写入

- **内容**: 将 `write_intermediate_manifests` 的调用从每次任务完成改为批量写入
- **实现方式**:
  1. 每 N 个任务完成 (如 N=5) 或每 T 秒 (如 T=30) 写入一次
  2. 保持最后一次完成时的强制写入
- **预期收益**: 减少 80% 的 manifest 文件写入 (节省 10-30 秒/任务)
- **质量影响**: **无** -- 纯 I/O 调度优化，最终输出完全一致
- **实施难度**: 极低 (30 分钟)
- **风险**: 无

#### 优化 H: `_source_image_context` manifest 读取缓存

- **内容**: 将 `_download_reference_images.json` 的读取结果缓存在内存中
- **实现方式**:
  1. 在 `_source_image_context` 函数中增加 `functools.lru_cache` 或模块级缓存
  2. manifest 在同一 pipeline run 中不会变化，缓存安全
- **预期收益**: 减少 20+ 次重复文件读取 (节省 1-2 秒/任务)
- **质量影响**: **无** -- 纯 I/O 优化
- **实施难度**: 极低 (15 分钟)
- **风险**: 无

#### 优化 I: compare 与 download 阶段并行

- **内容**: 对于 compare 阶段耗时较长的任务 (如 B0GSVF9S8P 的 81.2 分钟)，将 compare 和 download 阶段并行执行
- **实现方式**:
  1. compare 只读取 fetch 阶段的源数据
  2. download 只需要 fetch 阶段的 ASIN 列表
  3. 两者无数据依赖，可用 `ThreadPoolExecutor` 并行
- **预期收益**: 对 compare 耗时长的任务可节省 1-60 分钟; 对 compare 耗时短的任务 (< 1 分钟) 几乎无收益
- **质量影响**: **无** -- 两个阶段的输出互相独立
- **实施难度**: 中等 (3-5 小时，需要修改 pipeline 阶段编排)
- **风险**: 低 (需确保两个阶段的 artifact 写入不冲突)

### 3.2 低风险优化 (微小质量权衡，高效收益)

#### 优化 J: QA 循环失败快速降级

- **内容**: 当同一张图片连续 3 次 QA 失败且失败模式相同时，提前触发 `source_preserving_fallback` 而非继续重试
- **实现方式**:
  1. 跟踪每张图片的失败历史
  2. 检测连续 3 次相同失败模式 (如连续 `typography_legibility`)
  3. 提前切换到 fallback 策略
- **预期收益**: B0GSVF9S8P 的 func02 图片从 7 轮 (102 分钟) 降至 3 轮 + fallback (~30 分钟)，节省约 **70 分钟**
- **质量影响**: **低** -- fallback 策略 (`source_preserving_fallback`) 本身已通过 QA，只是可能不如经过 7 轮优化后的版本精细
- **实施难度**: 低 (2-3 小时)
- **风险**: 最终图片可能不如反复优化后的版本美观，但功能完整性有保障

#### 优化 K: 高置信度图片跳过二次审核

- **内容**: 对于首次 QA 得分高于阈值 (如 90 分以上) 且无风险标志的图片，跳过 `_apply_qa_second_review`
- **实现方式**:
  1. 在 `_apply_qa_second_review` 入口增加分数阈值判断
  2. 仅对边缘分数 (60-90) 或有风险标志的图片进行二次审核
- **预期收益**: 减少 30-50% 的 Gemini API 调用 (节省 1-2 分钟/任务)
- **质量影响**: **低** -- 高分图片极少在二次审核中被修改，但理论上存在漏检风险
- **实施难度**: 低 (1-2 小时)
- **风险**: 可能遗漏极少数高分但有隐藏问题的图片

---

### 3.3 不建议的优化 (会损害质量)

以下优化在分析过程中被考虑但因可能损害输出质量而被排除:

| 优化方案 | 理由 |
|---------|------|
| 减少 QA 重试次数上限 | 当前 5 次重试是质量保障的关键。降低上限会导致更多图片被放弃或接受低质量版本 |
| 降低 QA 通过阈值 | 当前阈值已经过调校，降低会导致低质量图片通过审核 |
| 跳过 OCR 交叉验证 | OCR 验证能捕捉 Gemini 视觉模型遗漏的文字错误，移除会降低文字准确性 |
| 减少图片生成 provider 并行数 | 已有 work-stealing 模式高效运行，减少并行数只会增加等待时间 |
| 降低图片分辨率/质量 | 会直接影响 Amazon listing 的视觉效果和转化率 |
| 跳过 visual brief 计算 | visual brief 是图片生成质量的核心引导，跳过会导致生成图片与产品不匹配 |
| 减少 Gemini 模型降级链 | 当前 3 级降级 (如 gemini-2.5-pro -> gemini-2.0-flash -> gemini-1.5-pro) 确保了可用性 |
| 跳过角色一致性校验 | 该 guard 防止错误的角色标注，移除会导致图片功能标注错误 |
