1. **BUG-06** `_fallback_score` 无条件通过 -- 改为返回 `rejected`
2. **BUG-07** `task_queue.join()` 无超时 -- 改为 deadline 轮询
3. **BUG-08** 管线无全局超时 -- 添加 `_pipeline_deadline` 检查

这 4 个修复都是**质量改进**，不是功能修复。核心功能断裂点 (R2 上传、文案生成、数据校验) 全部未修。

## 二、这些 bug 是孤立的还是系统性的？

**结论: 大部分是孤立的，可以单独修复。但有一个根本性的架构矛盾。**

### 孤立 bug (可单独修复，无连锁反应)

| Bug | 本质 | 修复难度 |
|-----|------|---------|
| BUG-01 | R2 凭证/配置问题 | 低 -- 补凭证或加 HEAD 校验 |
| BUG-03 | DeepSeek prompt 缺 JSON 约束 + 违禁词 | 中 -- 改 prompt 模板 |
| BUG-04 | 缺少默认值配置 | 极低 -- 加一行 `DEFAULT_COUNTRY_OF_ORIGIN` |
| BUG-12 | 标题后处理缺失 | 极低 -- 加 `.rstrip(".")` |
| BUG-13 | 规则 fallback 拼接了字段标签 | 低 -- 加 `re.sub` 清洗 |
| BUG-16 | Apify 串行抓取 | 中 -- 改为并发请求 |
| BUG-17 | Excel 文件锁无异常处理 | 极低 -- 加 `try/except` |
| BUG-20 | 模板路径解析失败 | 低 -- 修复 `_path_lookup` 映射 |
| BUG-21 | 图片下载无重试 | 低 -- 加 retry loop |

这些 bug 各自独立，修一个不影响另一个，总工作量大约 **2-3 个开发者周**。

### 共享根因的 bug 群

**根因 A: 管线缺乏数据完整性校验 (BUG-01, BUG-05, BUG-10, BUG-15)**

这 4 个 bug 形成一条**静默失败链**:

```
Apify 返回空字段 (BUG-10) --> 模板生成时字段为空 (BUG-04/20) --> R2 未上传但标记成功 (BUG-01) --> CSV 无 job_id 无法追溯 (BUG-15) --> main_image_url 为空 (BUG-05)
```

每个环节都**静默失败**，没有一环抛出硬错误阻止下游执行。这不是一个 bug，而是**一条设计原则的缺失: 缺乏"脏数据即终止"的守门机制**。

**根因 B: 图片生成管线的根本矛盾 (BUG-11, BUG-14, BUG-18, BUG-22)**

func/detail 图片要求同时满足:

1. **产品像素级保真** -- 不能改变产品外观
2. **文案重新渲染** -- 要在图上加文字/标注
3. **布局重新设计** -- 不能和原图一样
4. **文本可读性** -- QA 要求 typography_legibility >= 8

这四个要求对当前所有图片生成模型 (三个 provider) 来说是**互相矛盾的**。没有任何现有模型能可靠地在保持产品不变的同时生成可读的文字标注。

这导致了:
- ~40% 的 func 图首次 QA 失败 (BUG-11)
- 失败后 source-preserving fallback 复制原图回来，但标记为 "accepted" 无法区分 (BUG-18)
- 止损哈希包含文本描述，每次重试文案不同就重置计数 (BUG-22)
- Gemini 垃圾响应被永久缓存 (BUG-14)

**这不是代码 bug，是架构层面的目标冲突。** 修复方向是将文字叠加从图片生成模型中分离出来，改为后处理合成。

### 结论: 22 个 bug 中，13 个是孤立的，9 个共享 2 个根因。

## 三、项目是否有根本性的架构问题？

**结论: 管线骨架是合理的，但有三个结构性弱点。**

### 管线设计: 合理

管线的阶段划分 (scrape -> download -> generate -> QA -> publish -> template) 是清晰的。每个阶段有明确的输入/输出，支持 resume，有事件系统。这比很多项目的架构要好。

### 三个结构性弱点

**弱点 1: 静默失败 (Silent Failure)**

这是最严重的问题。当前管线中至少有 **6 个点** 会在数据缺失时静默通过而非报错:

- Apify 空字段通过 schema 校验 (BUG-10)
- `country_of_origin` 空白只产生 warning 不产生 error (BUG-04)
- R2 上传失败但 publish 标记 `status: "ok"` (BUG-01)
- `_fallback_score` 在无 QA 规则时自动通过 (BUG-06, 已修)
- source-preserving fallback 标记为 "accepted" (BUG-18)
- `_safe_event_put` 丢弃错误事件 (BUG-09)

**诊断: 管线的错误传播机制是"尽力而为"的，不是"至少一次"的。** 关键路径上的错误可以被任何一环吞掉。

**弱点 2: 缺乏端到端数据校验**

从 Apify 抓取到 Excel 输出，没有一个"数据完整性检查点"验证所有必填字段是否非空、所有 URL 是否可访问、所有映射是否成功。校验分散在各个阶段内部，且大部分是 warning 而非 error。

**弱点 3: 缓存无质量门控**

Visual brief 缓存 (BUG-14) 和图片下载缓存都没有"写入前校验"机制。坏数据进入缓存后会污染所有后续运行，且没有缓存失效策略。

### 数据流可靠性

数据流本身是单向的、可追踪的。`job_status.json` 记录了每个阶段的状态。但 **状态记录和实际结果脱节** -- publish 阶段可以标记 "ok" 而实际上传为 0。这意味着你不能信任状态文件。

### 错误处理

错误处理覆盖了大部分情况 (retry, backoff, fallback)，但在**关键路径的末端** (模板生成、发布) 失效了。前面的错误处理很好，最后一公里很差。

## 四、为什么之前的工作流花了很长时间？

**结论: 主要是因为 bug 造成了巨大浪费，其次是代码量大需要仔细审查。**

### Bug 造成的时间浪费

| 来源 | 时间 |
|------|------|
| BUG-02 路径错误导致重复下载 | 351 分钟 |
| BUG-16 Apify 串行等待 | ~270 分钟 |
| BUG-22 止损重置导致无限重试 | 102 分钟 |
| BUG-08 无全局超时 (修前) | 最高 210 分钟/job |
| **合计** | **~933 分钟 (15.5 小时)** |

5 个测试 job 的名义总运行时间约 8-10 小时。如果去掉 bug 浪费，实际需要的时间约 3-4 小时。**bug 导致的开销占总时间的 60% 以上。**

### 代码量

项目有 6 个核心模块 (apify.py, image_generation.py, vision_qa.py, pipeline.py, publish.py, template_engine.py)，每个 800-2700 行。总代码量约 8000-10000 行。对 AI agent 来说，完整审查需要多轮读取和交叉引用，这本身就需要时间。但这是正常的、不可压缩的工作。

### Agent 技术问题

五份报告的产出本身是高质量的，但报告之间有部分重复 (同一个 bug 在多个报告中被独立发现)。这不是浪费 -- 交叉验证增强了置信度 -- 但如果有一个统一的 bug 追踪表可以避免重复工作。

## 五、总体判断：这个项目值得继续投入吗？

**结论: 值得。核心架构健康度 6/10，可修复到 8/10。**

### 核心架构是否健康？

**骨架健康，关节有问题。** 管线的阶段设计、事件系统、resume 机制、多 provider 图片生成、Vision QA 系统都是合理的、有深度的设计。这不是一个拼凑出来的东西。

但管线的**错误处理哲学**有问题 -- 太倾向于"静默降级"而非"快速失败"。在生产系统中，静默降级比硬崩溃更危险，因为你不知道数据已经损坏了。

### 修复已知 bug 的工作量有多大？

| 优先级 | 工作量 | 内容 |
|--------|--------|------|
| P0 (阻塞发布) | 1-2 天 | BUG-01/05 (R2 上传 + URL 校验) |
| P0 (数据完整性) | 1 天 | BUG-04/10/20 (默认值 + Apify 校验 + 映射修复) |
| P1 (文案质量) | 2-3 天 | BUG-03/12/13 (prompt 修复 + 后处理 + 清洗) |
| P1 (效率) | 1-2 天 | BUG-02/16 (路径解析 + 并发抓取) |
| P1 (防御性) | 1 天 | BUG-14/15/17/21 (缓存校验 + job_id + 异常处理 + 重试) |
| P2 (架构) | 3-5 天 | BUG-11/18/22 (func 图文字合成方案重设计) |
| **合计** | **9-14 天** | 1 个全栈开发者 2-3 周 |

### 能否达到"稳定生产"状态？

**能，但有条件。**

分两个阶段:

**阶段一 (2 周): 让管线能跑通。** 修复 P0 和 P1 级别的 16 个 bug。目标是: 5 个 job 全部跑通，所有必填字段非空，文案 90%+ 合规，总运行时间 < 2 小时。

**阶段二 (1-2 周): 让管线可靠。** 重新设计 func 图片的文字叠加方案 (后处理合成替代模型直出)，添加端到端数据完整性检查点，实现缓存质量门控。

阶段一完成后，项目可以用于"人类审核 + 半自动"的工作流。阶段二完成后，才能实现真正的无人值守生产。

## 六、最紧急的 3 件事

**按"不修就没法用"排序，不是按重要性排序。**

### 1. 修复 R2 上传 + URL 校验 (BUG-01 + BUG-05)

**理由: 没有图片 URL，零个 listing 能发布到 Amazon。这是管线的最终输出，输出为空则前面所有工作全部白费。**

具体动作:
- 确认 R2 凭证在环境变量中正确配置
- 在 `publish.py` 中添加上传后 HEAD 请求校验
- 在 `template_engine.py` 中将 main_image_url 空白从 warning 升级为 error
- 在 R2 CSV 中添加 job_id 字段 (BUG-15)

### 2. 修复文案生成链路 (BUG-03 + BUG-04 + BUG-12 + BUG-13)

**理由: 文案是 listing 的第二大核心内容。86% 失败率 + 标题格式错误 + 文本损坏 = 所有 listing 的文字部分不可用。**

具体动作:
- 在 DeepSeek prompt 中添加 JSON 输出格式约束
- 在 DeepSeek prompt 中嵌入 Amazon 违禁词列表
- 在 `copy_writer.py` 中添加标题后处理: 去除末尾标点
- 在 `template_engine.py` 中添加 `DEFAULT_COUNTRY_OF_ORIGIN` 环境变量
- 修复规则 fallback 的字段标签拼接 bug

### 3. 修复数据完整性守门 (BUG-10 + BUG-20 + BUG-02)

**理由: Apify 数据残缺 + 模板映射失败 = 输出的 Excel 文件中大量字段为空。即使 R2 和文案都修好了，如果核心属性 (size_name, 规格参数) 还是空的，listing 依然不合格。**

具体动作:
- 在 `apify.py` 中添加 bullets/description/specs 非空校验
- 修复 `template_engine.py` 的 `_path_lookup` 对 size_name 的解析
- 统一 artifact 路径解析策略，消除绝对/相对路径混用 (BUG-02)
