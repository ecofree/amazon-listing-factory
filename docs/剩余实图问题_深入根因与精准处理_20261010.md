## 一、这次进一步确认了什么

不能把所有残留归成一个病因。现在可以区分以下责任：

1. **确定的编译信息损失**：带 mask 的功能图覆盖了 `detail_only` 范围；文字到功能的绑定存在于合同，却没有把功能事实投影进最终提示词。
2. **确定的审查协议矛盾**：审查说明允许缺动作时修状态或缩小目标，解析器却只允许这类问题指向文案。
3. **确定的规划/观察未纠正**：床/柜 state 仍混入布局；Rose 把擦拭与整枝合并，保留证据不足的具体螺纹机制，三动作目标却只有两项具体演示。
4. **确定的隔离采样器差异**：白床重复审查未带上程序新产生的 P4 诊断；生产控制器已有传递路径。不能拿这次局部采样的重复行为证明生产控制器同样丢反馈。
5. **确定发生、远端机制未知的执行偏移**：柜体和树体的原位置/尺度指令完整上传，native 仍移位。现有证据不足以区分网关实际处理与模型遵从。

其中第1、2项是本次进一步找到的程序/协议缺口；上次测试通过没有覆盖这些语义保留行为。第3项说明上轮替换规划/审查说明后，真实模型依然没有落实要求；不能将说明文字存在当作修复成功。

## 二、床架为什么仍重绘

### 2.1 已离线复现：mask 分支覆盖局部范围

责任代码：[image_prompt_compiler.py](D:/Amazon_pics/amazon_listing_factory/core/image_prompt_compiler.py:368) 的 `_role_content()`。

当前逻辑先按 `presentation.scope` 生成局部或整件说明，然后只要第一个附件有 `protected_mask`，便整段覆盖该说明。被覆盖的局部说明包含：

```text
selected product details
without reconstructing a whole product
```

原木床 `func_02` 的合同明确为 `detail_only`，实际发出的 mask 分支却没有保留这个范围区别。纯本地控制实验只替换这个 scope，当前编译出的整份 prompt 字符及 SHA 都不变；Coffee 的 masked func 同样如此。

这是**编译投影实验**，不是声称变成 whole_product 的草稿也能通过上游合法性校验。它证明的是最终编译器没有保留这项输入语义。上一轮动手前 baseline 已有同一覆盖分支，所以这是未修复的存量问题，不是此次审计新引入。

### 2.2 规划也保留了扩大画面范围的含混内容

原木床的原上图仅左上局部，下图仅右下入口局部；但 state 仍为 `Upper and lower split views...`，goal 仍为 `perimeter guardrails`。这些字段从未批准草稿保留到当前 repair 后，布局语言没有被删掉。

它们不构成合法的移位权限：实际 prompt 同时要求原位、尺度、机位和不补出原图界外产品。native 却把两块局部变成上下全宽床视图，视角变浅、可见范围扩大、横梁及入口柱木纹重画。

因此能确认：**局部范围被弱化、规划布局未清理、实际执行违反保留合同**。不能证明只改一个 scope 就一定消除木纹重绘，也不能将所有变化唯一归于网关、模型或 INT8。

### 2.3 最小处理

- 在同一个 `_role_content()` 内让 mask 与 scope 共同决定范围；masked detail 保留原局部构件及原源窗，masked whole 保留整件/实例。
- 直接替换覆盖分支，避免把无 mask 旧句中的 `crop and uniformly scale` 拼到固定 mask 约束后，产生新矛盾。
- 通过原 planner/repair 去掉 state 的分屏、放大、取景等布局语言；原局部功能的目标不能暗示补完整床。
- 用现有编译行为用例验证 scope 仍有意义，再以当前同一原木床样本验证 native。代码对照只证明信息保留，真实保真仍须另验。

## 三、柜体与树体为什么移位、放大

### 3.1 已排除本地输入变形与指令丢失

本次离线重放7张实际输入准备与 multipart 编码：

- 实际源图 SHA、实际 prompt SHA、重编码 mask SHA 均匹配原付费回执。
- mask 的 alpha 与原始 mask 逐像素相同，未翻转保护/编辑区域，没有本地平移。
- multipart 分别发送 `image` 与真正的 `mask` 字段，未把 mask 当第二张参考图。
- 上传源图仍是原1500×1500；原位置、尺度和选中对象源窗已经进入实际提示词。
- 本轮审计的相关生产/测试文件相对上一轮完成记录没有新的变化。

原请求为1024×1024、实际返回1254×1254；当前本地产物合同是正方形而非精确1024。这项差异没有证实 mask 失效，也不能单凭此推断服务端做了哪种转换。

### 3.2 柜体：实际是整体几何变换，不只是材质变化

Coffee `func_03` 的实发 prompt 有明确原位/原尺度要求。source/native 统一到768×768分析，在源保护区内限制结构匹配并排除背景及边缘，9个上部柜结构匹配点支持约15–16%放大、约3.7%画宽左移及15.4%画高下移；整图目测同样看到柜体放大、下移。

数值仅是上部结构的近似变换证据，不能扩成整柜精密验收。当前 state 的 `circular inset` 也是布局语言，可能促使模型重新排版产品。该贡献尚无独立生图因果对照。

### 3.3 树体：数量执行了，几何要求没有完全执行

Begonia 的 `obj_07_front/left/back`、原始源窗、保留两株、删除back及各自原位置/尺度均正确投影。native 恰好保留两株。

同实例限定的局部特征分析支持：

| 实例 | 近似尺度/位移 |
| --- | --- |
| front | 约0.985倍，略缩小；左移约4%画宽，上移约1.6%画高 |
| left | 约1.075–1.080倍，放大约8%；右移约2.6%画宽，上移约4.3%画高 |

所以准确说法是**两株均移位，左株放大，前株略缩小**，不是所有树都放大。自由匹配曾把同款花叶跨实例错配并得出约1.45倍伪结果，已排除；最终结果只作局部近似证据，不新增阈值或自动生产闸门。

### 3.4 处理边界

优先清理现有规划的产品/布局含混及编译损失。对于现有清晰身份和位置要求，不继续堆同义句或重算同一大致 mask。若清晰合同仍无法兑现，应在同一固定样本上验证远端执行，或读取已有request ID对应的服务端接收/转发证据。

本地 `supports_mask`、上传SHA和模型别名仅证明本地请求准备；它们没有证明网关消费 mask 或真实上游模型身份。此处仍不能给出“换INT8即可解决”或“只加一句提示词必定解决”的结论。人工本次不验收这些几何改变，不意味着增加新的自动几何/像素阈值。

## 四、引线为什么错位

### 4.1 绑定没有从合同中消失，具体内容在编译时被省掉

责任代码：[image_prompt_compiler.py](D:/Amazon_pics/amazon_listing_factory/core/image_prompt_compiler.py:389) 的 `_copy_associations()`。

Coffee 的 `magnetic_catch` feature、physical_facts、对应part和copy target仍存在，target feature 也经过存在性校验。但编译器取到 `(number, feature)` 后仅保留附件编号，生成：

```text
TEXT item N targets the specific visible component or operation named in its authored text within attachment N
```

具体feature身份和物理事实被丢掉，最终由模型按文案名称重新定位。源图已经没有引线，新native的端点落在磁吸扣下方木面：这是这次实际错误第一次出现的位置。

这能证明**投影弱化及实际定位错误**，不能证明 feature 投影完整后模型绝不再偏。没有证据表明SAM将扣件owner删除，也不能把错误指到超分。

### 4.2 最小处理

在现有函数内替换泛化句，用已经选中的唯一 source/feature 及必要的已验证物理事实描述目标；有明确对应的现有part时沿该归属表达。不把所有源观察全文塞回提示词，不另建引线控制器，不让代码绘线或凭空推断端点。

标题保持无目标；只为有当前合法绑定的标签投影其目标。复制source文案不能替代物理定位。后续验收看native端点实际是否落在该实体，而不是只检查标签文字存在。

## 五、擦拭为什么遗漏

### 5.1 源动作在生图前就被合并，合同未兑现三动作目标

Rose 的源图明确有布接触花瓣。旧观察合并装配/整枝/擦拭；新观察虽然改feature IDs，却仍用 `petal_maintenance` 表达 `wiped/shaped`。

初始待审草稿已有三动作goal、两动作copy及泛称step insets的state。本次repair主要解决object ID错误，动作数量与承诺未同步。最后审查返回 `product_depiction/product_region=supported`，没有指出这项矛盾。实际native只有装配和双手整枝，布擦拭消失。

代码中没有“copy权重高于goal”的排序算法；goal也确实上传了。能确认的是**具体动作的观察、计划、修订和审查没有闭合**，不能据两项输出猜模型内部权重。

### 5.2 另有可离线复现的审查路由矛盾

责任代码：[visual_semantics.py](D:/Amazon_pics/amazon_listing_factory/core/visual_semantics.py:595) 的 `_planning_review_rows()`，当前operation关系约束位于该函数中。

审查说明要求：缺承诺动作应修目标/状态或缩小goal。但解析器对 `relation.kind=operation` 只接受 `target_path=display_copy`，指向 `presentation.state` 或 `visual_goal` 会被拒绝。

使用Rose实际源证据上下文，隔离同一条动作finding，仅改变target_path，离线结果：

| 指向 | 当前结果 |
| --- | --- |
| presentation.state | 拒绝 |
| visual_goal | 拒绝 |
| display_copy | 接收 |

这是现行审查合同与程序边界的确定矛盾；本次真实review没有报出动作finding，所以不能把它当成该次漏报的唯一原因。它会阻碍原流程表达正确修复责任，应修同一个关系验证器。

### 5.3 必要演示中的产品材料也没有被保护

Rose三个右侧演示窗口的alpha均为0。窗内的地钉、底盘和花瓣实际材料没有保护；当前parts为空，editable_objects将 `circular inset bubbles` 当作整片可编辑区域。

窗口面积不是漏保产品面积，手、布、箭头和圆边应继续可编辑。需要把演示中的物理产品材料纳入现有parts，允许重排图形与换道具。蒙版补齐只能减少风险，不能自动保证缺失的擦拭动作被模型补回来。

### 5.4 机制断言先来自观察，再进入文案

源图可见旋转箭头和接触关系，不能清楚看到具体螺纹。观察先写 `threads/locks`，copy再写 `Threaded spike screws easily into base plate`。这是源事实被过度具体化，不是GPT凭空创造这条文字；看不见螺纹也不证明实物一定无螺纹。

### 5.5 最小处理

- 沿现有feature ID把擦拭与整枝分开；不增加识别模型或阶段。
- 原 `correct_evidence → repair → review` 收回证据不足的具体机制，同时更新state/goal/copy，保留可见的对接和旋转证据。
- 在唯一关系验证器内区分动作修复与文案修复：动作可以合法指向state/goal；文案问题继续指向display_copy，不把两类无限放宽到任意字段。
- 在同一次现有审查中针对已承诺动作逐项判断证据及计划展示。可缩小目标，无需为每个源事实强制写文案；不能留下三动作承诺与两动作计划。

## 六、白床为什么未通过

P4原坐标 `(0.384,0.505)` 在后护栏两根白色竖条之间的棕色背景墙。该点不被mask保护正确；待修的是原intent把背景当成产品的正点。

实际四次审查：首轮补真实漏选屋顶P3；第二轮把P4误称护栏并漏必需 `operation`；后两轮返回空 `point_checks` 却称supported，被既有owned-support检查退回。没有产生合法的“此点是背景、修intent”finding，所以planner repair没有获得有效动作，不是只换生图模型就能恢复。

当前审查示例允许没有点缺陷时 `point_checks=[]`；模型后两次恰好用了该形状。示例可能促使泛化通过，但内部注意力原因未知。原图裁片、坐标、source ID没有错配；点标记和较小裁片可能遮住精确中心，这只能列为促因，不能宣称唯一病因。

**隔离差异必须单列**：第三轮应用时生成的P4程序诊断没有被隔离采样器带入第四请求；生产 `note_diagnostics` 已有这项传递。原采样器还错误清掉此前屋顶已用的一次SAM预算，上轮已只修本轮reservation guard，原0台账保留。两者均不能当作生产控制器故障或剩余额度。

最小处理：沿已有point map明确把当前必需支持冲突的点列为本次需裁决对象，要求判断其原图中心材料/归属，再走已有intent或mask修复；替换容易被误用的空supported示例，不要求所有正常点追加证明。改善标记展示而不覆盖源中心。后续采样需复用生产诊断传播，不能再复制一套不完整反馈循环。

## 七、蓝柜为什么未通过

初审已经正确把P4/P8清洁布错点派给intent修订。问题发生在修订返回格式：

1. 第一次repair请求、输入schema和当前/基线示例均没有 `visual_setting`，模型返回时自行添加这个字段。
2. 当时compiler只报 `image_direction needs the current named design fields`。第二次repair携带这个非法draft，仅收到笼统报错，模型保留额外字段并改值为 `graphic_canvas`。
3. 两次都是完整STOP JSON，不能归因截断；陌生字段被正确拒绝，没有形成合法新合同或新SAM输入。

精确missing/unknown字段反馈已在上一轮末尾修改，当前应明确指出 `image_direction.visual_setting`；本轮只核查，没有再次修改或付费验证。它解决具体反馈不足，尚不能证明真实下一次返回一定合法。不要再次把同一补丁当新整改，也不要自动剥字段或放宽schema。

Blue源图有擦拭事实，但当前state/goal没有承诺必须展示手布。保持清洁布可编辑本身正确；源动作是否保留应由当前计划明确选择，不能用mask误保护清洁布，也不能把所有源图要素一律要求保留。与Rose的“明确承诺擦拭却遗漏”须分开。

## 八、建议实施顺序与停止条件
