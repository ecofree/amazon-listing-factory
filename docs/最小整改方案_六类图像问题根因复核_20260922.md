# 最小整改方案：六类图像问题的根因复核

日期：2026-09-22。范围：`freeze_4asin_2var_20260921_round2` 的 P01—P06、规划与成套设计。

## 1. 总结

这六项不能全部归为随机生图，也不能全部归为程序错误。

本轮最小修订应针对三个可重复的缺口：

1. **规划决定了“说什么”，但一些输出没有把“哪个部件、哪个分区、什么安装状态”表达清楚。** 图像模型在重新构图时补全了错误关系。
2. **设计说明、源图事实和本图获准显示的内容边界不够鲜明。** 36.5 英寸及新增文案有可追溯来源；存在把证据搬到错误图、错误部位的问题。
3. **同一张图的具体场景与类目/共享设计指令发生冲突。** 厨房用途有商品文案来源，类目又强制浴室梳洗台。

P06 的重复词则没有发现程序复制证据。现有文字比对已经能拒绝这种重复；在保持当前生成方式、只执行到生图的前提下，不能保证模型文字输出零错误，不能用替换一个词宣称根治。

**本方案只修改已有事实处理、规划、规划审查和提示词投影中的责任缺口；阶段、调度、重试、候选、发布和测试范围保持既定规则。此次仅提出方案，没有改生产代码或调用模型。**

## 2. 本次新查清的事实

### 2.1 P03 的数字和文案都能追溯到输入

- 白木床 func 的第一张编辑源图是床头细节，第二张 `source_01` 是完整尺寸图，图上就有 **36.5 英寸**。
- 同 child 的测量目录将其登记为 `source_01:m_height`、bed frame / height；本 func 的 `measurement_ids=[]`，所以它是**已有商品证据，但未被本图选择的尺寸**。
- 实际提示词第一段包含 `supportive lounging and pillow retention`；目标状态与观察包含 `recessed ... panels`。成图分别变成 Supportive for Lounging、Helps Keep Pillows in Place、Recessed Panel Detailing。
- 唯一获准渲染文案是 Tall Headboard Comfort。实际请求没有把上述三个短句加入可渲染清单。

可以确认存在输入来源与输出的一一对应；没有同输入重复实验，不能进一步声称掌握了模型内部生成过程。

### 2.2 P01 还有上游资料混杂，不能直接把资料当真值

白柜原始 `source/apify_raw/B0F7LDBLCY.json` 的 attributes 已经包含：

- `15.75"D x 31.5"W x 78.74"H`；
- `Floor Mount`；
- 层板数 `6`。

这不是归一化程序凭空新增的值。它们被带入 product_family 和规划事实目录；但源图是壁挂小柜，标题也明确 wall cabinet。现有 resolved_facts 只对门/抽屉/层板等有限字段作处理，此例没有安装类型裁决。spec 与 specific 中重复的 6 也不是两份独立的实物证据。

**不能证明“6”直接导致了六格重绘**：实际图像请求没有传入全部商品 specs。能确认的是规划阶段收到矛盾资料，且“总层板数”无论真伪都不能推导门的位置和隔间分布。

另外，白柜 size 的两个实际附件没有整体长宽高标注，测量目录也只有 1.26 英寸层板孔距；实际提示词没有选择整体尺寸。成图出现的 23.6 / 18.9 / 6.3 英寸在已核查的该次请求输入中没有找到授权来源，不能再把它们当成已经核实的商品尺寸。

### 2.3 厨房用途有来源，真正冲突在后续指令

白柜商品 bullets 明确列出 bathroom、kitchen、living room、bedroom、entrance passageway 等用途。因此厨房/玄关规划并非必然凭空扩展。

- 规划器收到的类目上下文在 420 字符预算下没有包含 avoid 列表，而且明确说明类目房间只是建议、child 事实决定用途。
- 但生图编译器随后从 `medicine_cabinet/manifest.yaml` 原样加入：`Show vanity use ...`。
- 同一张图又明确要求 kitchen wall / spices；共享 environment 也继续强调 bathroom vanity、grooming accessories、white linens。
- 现有设计审查输入没有包含 `Show vanity use` 这条后加入的具体规则。于是出现**规划通过，执行时增加矛盾指令**。

因此应纠正上一报告：不能以未完整发送给规划器的 avoid 列表，直接判定规划违规；应修复执行指令与已授权场景的矛盾。

## 3. P01：为什么改变柜体结构，是否跨类目复发

### 原因链

1. 源图的毛巾杆明确只挂在左下格下面。
2. 观察把它压缩成 `towel bar attached to the underside` / `bottom gold towel bar`，丢失了左下格归属。
3. 规划仅要求整柜、关门、底部毛巾杆；没有补回该归属。
4. 图像模型获得重新设计布局的自由，绘制新的整柜和细节图；这些请求均未使用像素保护 mask，所以这是参考图条件下的生成编辑，不是产品像素原样搬运。
5. 模型把“底部毛巾杆”画成横跨底部，将“门内两层板”扩展成另一种整柜六格结构。现有审查评价的是计划，不是后来真实生成的局部图。

**确定的是关系信息不完整及输出重绘；不能确定模型的某一个词就是唯一触发原因。** 源图并未消失，因此也不能说只要补一句位置描述就保证不重绘。

### 是否只影响柜子

不会局限于柜子。这种“名称/数量正确，关系错误”的机制可影响：床架中心支撑属于哪根梁、磁吸扣属于哪个门腔、安装件连接哪一个面、地钉插入哪种介质、局部放大图是否仍是同一部件。此次 P02/P04/P05 已证明关系问题跨部件和类目出现；其余举例是风险范围，不冒充已经确认的缺陷。

### 最小修订

- 替换现有观察 schema 中宽泛的 physical_facts 示例及对应说明，使必要结构事实保留“部件—所属区域—连接对象”；仍使用现有字符串字段。
- 在已有 presentation.state 表达本图必须保持的关系；源图明确时，写清左下格毛巾杆、门内对应区域。不要把整个图库的零件清单都塞进去。
- 现有 product_depiction 审查核对这些必要关系，reason 指出具体证据/缺口，而不只判断“确实有毛巾杆/层板”。使用现有 revise_plan / correct_evidence 和既有次数限制。
- 对局部图、引线等画面元素，模型可以设计布局，但涉及产品结构时必须沿用被选源图的部件与状态；看不到的新安装面不靠推测补出。
- 图像中的总数、商品总层板数不自动授权每个隔间的分配；不新增部件关系图数据库、坐标系统、抠图/合成阶段。

对白柜 size：现有目录只有 1.26 英寸孔距，当前计划应真实表达这一测量及可见结构；整体尺寸目标必须有实际选中的对应证据后才能采用。不要为了让图“像完整尺寸图”补三个数字。

## 4. P02：偶发、模型执行问题还是设计问题

应拆成两件事。

### 4.1 引线：欠明确的设计 + 模型执行偏差

- 原图是独立的圆形硬件细节，没有成图中那两条错误定位引线。
- 当前计划只写了 targeted close-up callouts，以及 top magnetic catch、metal hinges 等名称；没有确定左侧门腔，也没有说明闭门视图能否指示隐藏安装点。
- 图像模型自行采用引线布局，错误地连到右侧开放区。

**单张结果无法测出随机失误率，但设计缺口确实存在，不能把全部责任交给随机性。** 正确的独立细节图无需引线；若使用引线，必须有源图支持的目标部件。

最小修订与 P01 共用：现有规划/审查说明真实所属关系；对于主图中不可见的安装点，可以采用独立细节展示，不强制连线。这里是规划时的设计选择，不是运行失败后的新 fallback。

### 4.2 错字：上游编辑缺失，不是这次模型随机拼错

`Premiu` 在源图、提取的证据文本、DisplayCopyContract、请求文字和成图中一致存在。

当前 `_copy_needs_review()` 对与源文完全一致的字符串不发起改写事实审查，这对避免重复审查有价值，但“原文一致”只证明没改变来源，不证明英语正确。

最小修订放在**现有 Gemini 文案规划**：先做拼写、语法和精简，再绑定原事实。可直接去掉无事实价值的 Premium，使用 Metal Hinges；这不是给 Premiu 做全局字符串替换。保留现有事实审查处理改写后的事实含义，不把所有原文再送一个校对服务。

## 5. P03：如何阻止参考事实和说明变成额外显示内容

这里同时发生两次错误：

1. 参考图上的整床高度被搬到本来不展示尺寸的功能图；
2. 整床高度被套到床头局部高度。文案则由设计目标转成了额外标签。

现有提示词虽然已有“完整文案清单”，但 ROLE 又有可直接改写成卖点的句子、第二张图有完整数字图形，STYLE 在无测量任务里也输出 numeric_style。不能证明 numeric_style 独自导致加尺寸，但它是本图不需要的指令。

### 最小修订

- 规划选择必要参考图：床头 detail_only 已有足够细节证据时，不惯性追加尺寸图；如果尺寸图确实是唯一必要结构证据，继续允许使用。
- 替换现有参考/文字边界说明：附件只授权身份与被选结构，附件文字、尺寸和设计说明不直接授权显示；显示数字只来自本图 measurement_authority 或已获准的带限定文案。
- 对 `measurement_ids=[]` 的本图，明确表达没有额外测量标注；按现有字段投影，不新增校验阶段。
- 没有选定测量时不输出 numeric_style；实际用途/几何说明写在 state，精确显示文案仍只由 DisplayCopyContract 产生。
- 不删除有用的 supportive lounging 等所有设计意图，也不把模型曾经擅自增加的文字追认进合同。只在确有信息价值时由规划明确选择。

这降低输入诱导与冲突，不能从理论上保证模型永不越界。本次真实成图才能检验效果。

## 6. P04：床垫厚度箭头为什么错，最小方案怎么选

### 已确认与不确定

- 数值和对象来自源图，合同正确选择 recommended mattress thickness，数值是 8–12 英寸。
- 源图以透明床垫示意范围表达厚度；目标状态写 mattress placement outline，模型改成了实体白床垫，并把原本范围标识改画到床垫上方空中。
- `evidence_type=dimension_line` 描述源图证据类型，不等于已经规定新画面的真实上下端点。当前合同依赖自然语言和图像模型理解关系。
- 因而它是**转换表达方式时的关系执行错误**；没有足够重复样本证明随机概率，也没有证据指向程序换错单位或传错尺寸。

### 本轮最小方案

在已有 presentation.state 中选择源图支持的厚度示意状态，注明“推荐厚度范围，非已售床垫的实测值”；箭头绑定同一床垫示意的底面与顶面，保留上下边界可见。模型继续设计构图，不能把箭头搬成床垫上方的空隙。

**修正上一报告建议：本轮不直接改成纯文字、删除箭头。** 当前后续候选绑定逻辑对 dimension_line 同时要求源图与成图端点；只删箭头可能引入后续 inconclusive。若未来要全面区分“来源是尺寸线”和“输出为文字说明”，需连同现有测量表示与校验一起处理，不伪装成一句提示词的小改。

本轮也不全局把范围数字变成箭头或全部取消箭头；只解决这个被选择的表达及其测量对象。

## 7. P05：产品展示还是实际使用，谁负责判断

三种画面应明确区分，使用现有 role、scope、environment_mode、presentation.state 即可：

| 意图 | 正确表达 | 责任 |
|---|---|---|
| 展示所售产品及地钉形状 | 技术画布上的未安装产品、地钉细节，允许完整露出尖端 | 规划选择未安装展示状态；生图模型安排画面 |
| 实际安装/使用场景 | 软土插入地钉；硬地面的盆栽使用源证据支持的容器与固定介质 | 规划先选择适用场景及安装方式；生图执行接触与遮挡关系 |
| 装配/安装说明 | 展示插入过程和必要部件，区分未安装与安装完成 | 规划区分步骤状态；生图表达动作和部件关系 |

白底上裸露地钉不是错误。此次 func_02 的木甲板/石路以及 scene_02 的庭院使用场景把裸钉表现成可自行稳定站立，才是问题。

装饰盆在该商品源图、安装说明里有证据，而且 pot not included 有明确来源。可以作为非售配件使用；无需让用户再决定，也无需让程序增加“盆栽配件识别流程”。不能由模型为了画得好看发明新的支架、底座或出售配件。

**最小修订：** 在原规划 state 中明确“未安装展示”或“使用中的固定方式”，并让物理关系审查核对场景地面与支撑是否兼容。模型负责盆的非产品造型、摆放、光照等审美决定，不自行更改商品的固定方式。不能要求使用场景始终露出全部地钉，否则会再次诱发这种错误。

## 8. P06：重复词的根因与修复边界

### 文字重复

- DisplayCopyContract 和实际请求都是 `Planter container placement (pot not included)`，没有重复 not。
- 当前只有一次该图错误输出，不能证明所有长文案/括号都会重复，也不能声称程序把同一文案拼了两次。
- 候选经过 Real-ESRGAN 超分，已完成回执的原始图字节按现有清理逻辑删除；此次无法逐像素区分基础生成与超分的贡献。结合完整词语重复，模型文字绘制失误是合理判断，但不是已证明的唯一内部原因。
- 本轮直接调用现有 `_line_matches_any()`：正确句子为 True；加一个 not 的版本为 False。现有比对没有把重复词当合法句子放行。

所以这里**不安排“替换 not”“加重复词黑名单”“再加一遍禁止重复”或新增 OCR 服务**。复用前述文案精简和输入边界修订以减少负担；纠正当前成图仍需实际生图编辑验证。

只到生图的候选不具备自动文字验收结论。以后若运行既有 QA，按原有文字合同检查；当前继续由用户要求的逐图检查判断。本方案不擅自开启 QA。零文字错误无法在这些约束下由程序事前保证，这一点不能用“已经解决根因”掩盖。

### 安装细节

它与重复词不是同一个原因。紫树的整体目标已经写插土/放盆，但生图新加的圆形盆内细节没有完整表现固定介质。与 P01/P05 共用“所有产品局部都保持同一安装状态和关系”的修订；不要要求复制源图每个圆圈，也不要只改正文留下错误局部图。

## 9. 成套设计：本轮真正该改的内容

### 9.1 场景只由本图 state 决定

- medicine_cabinet 的 scene 规则去掉 `Show vanity use`，保留门面、开门方向和壁挂结构保真要求。
- 类目浴室偏好保留为缺少明确用途时的设计建议；替换禁止有据跨房间场景的绝对写法。
- 共享 environment_and_staging 只写风格与氛围，不再夹带浴室台盆、毛巾等固定房间/物品清单。具体房间与必要物品由本图 state/components 表达。
- 不增加新环境分类器、房间白名单或关键词拦截。其它类目使用同一个已有字段所有权规则，不全局删除合理的品类结构限制。

### 9.2 每张图的目标应能被画面证明

规划器当前已要求分配买家问题，但一些目标仍把“承重强”“涂层耐用”交给普通房间照片证明。最小修订是替换原分工指令：先确定本图可见证据和目标状态，再写能够通过该画面回答的买家问题。

同一产品的成套图可分别承担外形、使用状态、收纳空间、安装方式、局部机制、实际尺寸。风格可以统一；不能把同一功能换背景后包装成新事实。

**保留现有槽位。** 当真实证据不足以形成更多卖点时，可用有意义的角度/状态补充，不强制每张都发明独立卖点，也不以信息差异不足给整个 Job 增加阻塞。全套信息分工在已有一次 child 规划中完成，不新增全套设计评分/二次策划。

### 9.3 A06 的决定

本轮先修以上两个缺口，不开放任意角色转换、不重构任务身份/候选复用/图库合并。只有修订后的规划仍因现有锚点资格无法引用真实证据时，才进一步处理那个局部限制。此次证据不足以支持“必须立即全面开放 A06”。

## 10. 最小实施范围
