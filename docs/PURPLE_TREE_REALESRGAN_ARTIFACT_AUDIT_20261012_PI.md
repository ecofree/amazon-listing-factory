# 紫树 func 竖向残影：RealESRGAN 责任与内部原因复核

日期：2026-10-12。对象仅为 `B0GG3M4DL8/func` 的原生输出、发布后处理和已有复现文件。

## 结论

**残影是当前这份 `realesrgan-x4plus` 模型资产对该图文输入产生的确定性重建伪影，不是生成接口重新画出的内容，也不是后续 Lanczos 缩小才产生。**

这次不只重跑了生产路径，还用同一局部、同一模型图/权重做了设备和计算精度对照：单块处理、单线程、Intel GPU、NVIDIA GPU，以及独立 CUDA 图重建的 FP32/FP16 计算，都出现同类竖向残影。

因此：

- 不能再把它简单归为分块拼接、多线程竞争、错误选择 GPU 或某块显卡故障。
- FP32 运算也不能消除它；FP16/不同运行实现会影响强度，但不是伪影出现的唯一条件。
- 本结论针对**本地正在使用的模型图及权重**。尚未比对独立取得的官方原始 FP32 checkpoint，不能进一步断言是官方模型普遍缺陷、训练特性还是本地导出/半精度权重存储的影响，更不能宣称权重文件损坏。

本次没有改生产代码、全局配置、正式候选或批准记录，没有新的付费生图请求。

## 1. 实际生产链路

`core/candidate_state.py`：

```
原始付费响应
→ assert_native_image
→ normalize_native_image
→ upscale_for_publication_with_backend
→ 候选暂存/完整性检查
→ 不可变候选及 manifest
```

本例原生输入是 **1254×1254、RGB PNG，无 alpha/ICC 等附加信息**：

- SHA：`8ee8c910e77a5b72d6c4793019477a80987b8376551b73123f3a39172721316c`
- normalize 前后字节相同，排除本例由透明通道合成、颜色转换引入。

`core/image_upscale.py` 在原图小于 1600、backend=auto 且 exe 存在时调用：

```
realesrgan-ncnn-vulkan.exe -i source.png -o enhanced.png
  -m <models> -n realesrgan-x4plus -s 4 -f png
```

然后再用 Lanczos 将 **5016×5016** 缩为 **1600×1600**。这是非线性内容重建后缩小，不是一次普通的尺寸插值。

## 2. 中间结果定位

这次保留了生产函数临时目录中通常会消失的 4× 中间图。

- exe 返回码为 0；4× 输出已经有残影。
- 再按生产代码缩到 1600，完整 SHA 为：
  `8fcdda874db3fa86b46e7eb23f34e184fbb2b01f746c75b0d49e6ac8c43ddc63`
- 与正式初始失败候选及前一次隔离复现完全一致。
- 既有三个 1600px 检查框的深色像素数仍为 **1185 / 411 / 391**。
- 相应的 4× 检查框里已经有 **11815 / 4070 / 4001** 个深色像素。

所以 Lanczos 缩小只是保留了已有问题，而非新制造残影。

## 3. 控制变量排查

| 对照 | 结果 | 能排除什么 |
|---|---|---|
| 生产默认命令，原始全图 | SHA 精确复现 | 不是偶发的一次坏网络响应或错误文件选择 |
| 固定 tile=256，其他不变 | 残影仍在，三个框为 1103 / 384 / 309 | 改分块尺寸不解决；不能只怪自动 tile |
| 同参数明确指定 GPU 1（RTX 2060） | 输出 SHA 与自动选择时完全相同 | 本机该路径自动选择的结果等同于 RTX，不是误用了核显 |
| 固定 GPU/tile，线程改 1:1:1 | 输出 SHA 仍完全相同 | 不支持多线程竞争造成这份残影的假设 |
| 256px 局部，tile=256，NVIDIA | 单块输出仍有明显竖纹 | 多块拼接不是产生伪影的必要条件；1254 非标准尺寸也不是必要条件 |
| 同一局部、同权重，Intel GPU | 仍有同位置同形态残影，强度不同 | 不能归为某一块显卡独有的硬件/驱动故障 |
| 同模型资产，独立 CUDA 图重建，FP32/TF32 关闭 | 仍有残影 | 不是只有 NCNN/Vulkan 路径或 FP16 计算才出现 |
| 同一重建图，FP16 | 仍有残影 | 精度变化影响数值，但单改计算精度不是完整修复 |

Intel 全图对照在 90 秒超时，未产出完整结果；**该次不计为成功、也不作为“全图干净”的证据**。随后换同一局部做设备对照，分别正常完成。

局部裁剪只用于确定原因，不是生产裁剪、拼回产品或最终图片处理方案。

## 4. 模型响应与精度证据

### 4.1 输入并没有同等可见程度的线条

原生图的三个对应近白区域，最小通道值分别为：

- 第一处：253 / 253 / 253；
- 第二处：251 / 251 / 250；
- 第三处：253 / 253 / 253。

原图有非常轻微的近白像素波动，但不是放大结果里那些明显的彩色竖纹。普通 Lanczos 对照也没有这些深色纹理。

### 4.2 排除“只改成 FP32 就好”的简单判断

在已经安装的 Torch 环境中，按本地 `.param` 重建了 999 个运算节点，使用原 `.bin` 的 351 组卷积权重，完整读取 **33,424,520 字节**，没有换权重或重新训练。

这个验证程序仅存于审计目录，不是项目的新放大后端。

所有权重块原本为 FP16 存储；分别用 FP32 和 FP16 计算，同一 256px 局部、相同 10px 反射 padding，观察原图第一处残影对应的同一个 4× ROI：

| 运行方式 | ROI 深色像素数（通道最小值 <180） | ROI 最小 RGB |
|---|---:|---|
| NCNN / NVIDIA | 10475 | 134 / 124 / 113 |
| NCNN / Intel | 3309 | 154 / 145 / 138 |
| CUDA 图重建 / FP32 | 3620 | 153 / 144 / 138 |
| CUDA 图重建 / FP16 | 3963 | 151 / 142 / 136 |

FP32 输出为有限值，没有通过 NaN 替换等方法修饰。图像的文字、圆框与残影形态可直接对照；Intel 与该 FP32 图的全局像素平均绝对差约 0.075/255。

NVIDIA/NCNN 路径明显加重了这个 ROI 的伪影，但较弱的伪影在其他计算路径仍然存在。因此应区分**伪影来源**与**数值实现对强度的放大**。

限制：将已半精度存储的权重转成 FP32 运算，并不能恢复原始 FP32 权重。因此这里排除的是“单纯 FP16 运算是唯一原因”，没有排除权重转换/存储的影响。

## 5. 项目为什么会把它保存成候选

这是另一个已经能从代码确认的问题：

1. `auto` 只按尺寸与 exe 是否存在选择 RealESRGAN，没有区分照片与已经排好文字/线框的功能图。
2. RealESRGAN 是会重建内容的模型；该步骤对本例不再是视觉中性的尺寸调整。
3. `_realesrgan_resize()` 只要进程成功、PNG 可读就返回；本例退出码是 0。
4. 现有回退只对超时、启动、退出失败、读图失败等异常生效。**不会因可解码图中出现残影自动触发。**
5. 后面的 `assert_image_output()` 检查尺寸、字节上限、解码和空图，不检查局部新生纹理。

因此“合法落盘”并不矛盾：它通过的是文件完整性，不是后处理保真或最终画质。

一旦责任在这一步，向生成模型再发 targeted_edit 无法保证解决，因为干净的新原生结果还会再次经过相同的内容重建路径。之前那次修图请求已经保存，不应删除其失败证据。

## 6. 建议的处理方向（未实施）

- 对当前已有合格分辨率、只需变为发布尺寸的图文/功能/尺寸输出，优先采用**明确、可追溯的确定性尺寸处理**；本例已有同原生输入的 Lanczos 干净对照。
- 不要把调 tile、线程、GPU 或强制 FP32 当成已经验证的完整修复。
- 如果继续保留神经超分，应作为显式、经过独立质量验证的处理策略，而不是安装 exe 后自动介入所有小于 1600px 的图。
- 当前失败文件不可覆盖。应通过现有候选/回执体系受控重新提交派生结果，绑定原生 SHA、后处理策略及新的最终 SHA；旧批准不能自动套用到新文件。
- 不需为解决本次残影重新请求付费图片生成。应复用已保存的原生响应，但仍须对重新处理后的实际图进行验收。
- 后处理策略修改不能只改一个全局开关便宣称旧候选修好：已提交的不可变候选与缓存必须按身份规则处理。
