# 事实到成品一致性精准整改方案

日期：2026-09-17。状态：待实施方案，不是修复完成报告。

依据：`test_runs/freeze_4cat_2var_20260917_scoped/review_sheets/ROOT_CAUSE_AUDIT_20260917.md`，以及本次再次核对的当前参考解析、文案合同、规划复核和 prompt 编译代码。

## 1. 目标和不变边界

目标不是让生成图复制源图，而是：**产品事实不变，设计可以重做；同一个 child 的设计意图从规划到实际请求不失真，成品是否兑现必须看实际图片。**

- 不新增 stage、controller、QA 流程、第二套 prompt、feature flag 或候选流程。
- 不把本方案的 P0–P4 变成生产 stage；它们只是开发实施顺序。
- 不锁定源图的床品、墙面、家具摆件、构图、字体和旧信息图样式。不重新建立源图全部道具识别及保留合同。
- 产品颜色、结构、部件、尺寸、材质及真实功能不能自由改写；普通道具与售卖配件必须区分，不能把随产品出售的部件当成装饰删除。
- 同 child 保持配色与图形语言一致，不要求不同 child 或整个 family 共用配色。
- 主图遵守现有类目策略：床架 lifestyle；其它本轮类目按已有白底策略。不修改模板默认值和商业事实。
- 审美由 Gemini 规划、GPT 实现、人工实图比较；不新增自动审美失败门槛。
- 不保证生成模型绝不重绘。正确输入和语义能降低风险，不能代替现有硬事实验收。

## 2. 本轮问题的因果边界

74 个已形成角色生成了 50 张；13 个生成前阻塞，11 个生成或下载未完成；另有 2 个源图观察未解决，未包含在 74 个角色内。不能把 50 张有文件等同于质量通过，本轮没有运行 QA。

| 问题 | 已确认原因 | 不能用什么方法替代修复 |
|---|---|---|
| 推荐床垫 `≤6"` 变成 `6 in` | 程序提取数字后取 `[0]`，丢失比较符；范围也有丢端点风险 | 增加“尺寸必须准确”的提示词 |
| White 浴室柜 func 被拒绝 | 规划目录提供同 child 多源事实，下游却按单源 ID 重新限制 | 反复要求 Gemini 换一种说法 |
| 12 个角色缺规划复核 | timeout/EOF 等通信失败；下游部分错误归属退化成 brief blocked | 把未复核当成规划事实错误或自动通过 |
| 局部磁吸、植物细节变成新整物 | `detail_only` 执行表达弱，售卖数量与画面数量混用；模型越界补全 | 给所有 func 强制附整物并要求展示整物 |
| 黑柜少底格、多隔板、尺寸对象错位 | 部分任务输入含正确结构，模型仍然改错；观察结构描述也不充分 | 仅校验数字存在、JSON 完整或 prompt 有 preserve |
| 字体、盖毯、徽标漂移 | 正确共享设计已传入，但执行不稳；实际附件还带源样式竞争 | 恢复固定色板或继续重复色值 |
| 缺图无法无风险自动补齐 | 已返回响应、未受理、结果不明三类恢复能力不同 | 所有 502/EOF 都换 provider 重新付费生成 |
| 批次一直单并发 | 内存准入限制与启动时固定线程池上限叠加 | 取消内存保护或再建调度器 |

源图样式仍进入附件是事实；某个最终色值是否由源图直接诱发、影响多大，仍需控制变量实测，不能把推断写成已证明的唯一原因。当前色彩工具运行的是规划色值诊断，不是自动选色或成品颜色检测。

## 3. 一条链路、各自唯一职责

| 现有环节 | 唯一负责内容 | 不应负责内容 |
|---|---|---|
| 观察与事实整理 | 同 child 的产品身份、可见结构、测量完整含义、来源与适用对象 | 继承源图审美；把普通道具变成必须保留的产品 |
| Gemini 视觉规划 | 受众/市场/使用场景、child 配色、字体/图形系统；每图目标、展示范围和证据选择 | 改写产品事实；代替源证据发明结构；为每图另建冲突色板 |
| 现有参考解析器 | 把选中的证据落实为真实附件、用途、裁剪范围和顺序 | 另选设计路线；把裁剪当产品分割；静默换源图 |
| 现有 prompt 编译器 | 单向投影已确定的事实、范围、设计和附件位置 | 再规划一次；猜丢失的事实；添加一套平行限制 |
| GPT 生图 | 在上述边界内设计构图、排版、光照、材质和生活细节 | 因布局需要改结构、改测量对象或恢复源样式 |
| 现有验收及人工检查 | 判断实际成品的结构、事实、发布条件；人工判断美感与统一性 | 把规划通过当成成品通过；新设审美评分关卡 |

不再增加一份“全链路总合同”来复制所有字段。复用已有事实目录、VisualDesignKit、ImageTask、generation_references 和请求/结果记录；各层只引用或投影，不产生第二份可独立修改的事实及配色权威。

## 4. P0：先修事实和引用范围

### 4.1 保留完整测量含义

修改 `core/final_source_intents.py` 的测量投影及 `core/text_evidence.py` 对应解析/比较逻辑，并核对既有 measurement authority 的消费端。

- 删除以 `extract_measurements(text)[0]` 取代完整测量表达的行为。
- 在既有测量记录内保留数值或范围、单位、比较符、限定语、测量对象及已有端点绑定；原文继续用于追溯，不作为另一套运行指令。
- 单位换算不改变命题：上限仍是上限，推荐厚度不是床架高度，范围不能退化为单值。
- 去重按对象、轴向、端点和命题含义判断，不按数值去重。两个不同部位同为 8.5 in，仍是两个量测。
- 下游比较必须比较含义，不能把 `≤6` 和 `6` 当作相同事实。转换精度沿用当前统一规则，不自行发明容差。

验收：当前 `≤6"` 样例从观察到最终 prompt 仍表示 recommended maximum；`6–8 in` 保留两端；同值不同对象不合并。先离线证明，无需付费生图。

### 4.2 同 child 事实可以跨源引用，适用范围不能跨错产品

以现有 child 证据目录为引用权威，同时修改 `_planner_evidence`、`_available_claims`、`_copy_binding`、`build_display_copy_contract` 的相关消费者。

- 删除下游重新构造 source-only 事实池的旧限制；图的主参考来源不再独占这张图可使用的所有事实。
- 每条事实继续保留 child、来源、对象和事实类型。可见形状不能自动证明实木、承重、静音等材料或性能命题。
- 同 child 的其它源图事实可以支持文案；当前画面要演示某部件时，还必须有能支撑该部件的视觉证据。
- 跨源存在真实冲突时，保留冲突并交回现有纠错责任环节，不选“有利的一条”蒙混通过；只影响依赖该事实的角色。
- 不扩大为整个 family 任意共享事实；同色、同标题也不能替代 child 身份证明。

验收：White 浴室柜本轮三个真实 evidence ID 能正常引用；其它 child 的 ID 和不支持材料/性能的 ID 仍不能通过。两个下游校验点必须一起修改，避免规划放行、编译又拒绝。

## 5. P1：规划必须与实际附件对应，但不锁死设计

### 5.1 明确整物、局部、状态变化的不同证据需求

在现有 `image_direction.presentation`、`evidence_usage` 和参考解析器内处理：

- 整物图：选取能支持完整结构的同 child 视图。观察需描述有区别意义的结构，如底部开放格、实际隔板、抽屉和连接关系，不能只写“一个柜子”。这不是增加所有类目的固定部件计数表。
- 局部图：输出是被选部件的细节展示；不要求画出整件商品，更不要求画满售卖数量。
- 整物加细节：规划确实需要这种表达时才选择整物和局部证据；程序验证附件存在及用途一致，不自行升级为全景图。
- 开门、拉抽屉、改变机位可以重新设计，不强制沿用源图状态；但不能借状态变化增加部件，或凭空证明未展示的内部结构。
- 真实使用关系写入现有 state：例如地插需要土壤或合适容器承接。Gemini/GPT 决定容器和环境，不由程序固定一只花盆。

### 5.2 实际附件不再获得超出用途的权威

沿用 `planning_view_inputs`、`resolve_edit_references`、`generation_reference_sources`，不另建附件准备流程。

- 产品外观输入服务于颜色、材质与产品身份；整物/局部证据服务于结构；测量附件服务于量测；设计附件只服务于已批准的样式迁移。
- 保留现有路径、sha256、source/view 与顺序验证。复核、prompt 附件编号和实际发送必须引用同一解析结果，不允许各自重选图片。
- 对已有源内产品视图优先选择证据完整、非产品干扰较少者；不能为去掉床品而裁掉床边、为去掉旧标注而裁掉测量端点。
- 没有干净产品图时，不新增强制抠图、分割模型、蒙版生成或素材包必填门槛。保留必要证据，只赋予产品/测量用途；承认仍有视觉竞争风险，并在实测中验证。
- 本轮获批设计附件为空，不将设计参考迁移写成已验证能力；保持现有允许自主设计的路径。

### 5.3 缩小复核负担，纠正失败归属

现有规划复核保留真正需要模型判断的事项，如售卖归属不明、跨视图结构整合、状态转换是否有证据支持。

- 先列出风险项到验证方的映射；ID 存在、同 child、哈希一致、数值投影等交给已有确定性校验，不重复要求模型证明。
- 替换所有角色无条件挂 `execution_contract:<role>` 的泛化复核要求；不能简单删除复核并默认 supported。
- 未采用源文案，不自动视为遗漏；在现有角色覆盖中区分重复宣传语与必须保留的独有结构/量测，不强迫每张图继承全部源文案。
- 通信 timeout/EOF 保留 `review` 责任和可恢复状态；真实矛盾才交回 observation、brief 或 shared_design。不要在 `image_tasks` 中统一改写成 brief 错误。
- 已有逐条成功结果继续保留，仅恢复缺少的复核项；共享设计未变时，不重做已通过的角色。共享设计确实改变时，按现有依赖指纹使受影响任务失效，不混用新旧成品。
- 请求仅携带受审角色所需的事实和附件，按内容身份复用相同附件，不按不同证据 ID 重复附同一文件；保留现有有限次数及总时限。
- 非法 bbox 的纠错反馈给出字段、实际数值及合法范围，只修失败项；不猜测坐标单位后强行缩放或夹到边界。

验收：当前两组局部参考不再被规划/编译当整物任务；网络复核失败不会触发无关的全 child 重新设计；观察失败仍在源图覆盖汇总里，不因没形成 role 就消失。

## 6. P2：执行语义单一，设计令牌不再互相覆盖

### 6.1 替换冲突表达，而非追加禁令

修改 `core/image_prompt_compiler.py` 的现有职责块：

| 当前问题 | 替换后职责 |
|---|---|
| `detail_only` 枚举与 quantity、自由构图同时出现 | 用自然语言说明当前输出是哪个部件细节；售卖数量是产品事实，不自动成为画面整物数量 |
| 产品类型、源图说明和设计指令分散重述同一要求 | 产品身份/结构一次；角色展示范围一次；共享视觉系统一次；显示文字和测量各在其权威块中出现 |
| 图像方向可能另写床品颜色或文字色 | 颜色、字体和图形组件引用 child 共享设计；角色方向负责机位、用途、布局，不再另设同一属性 |
| 源测量和显示文案重复表达同一标签 | 明确哪条是可见文字、哪条是对象关联；内部绑定可保留，模型端同一可见文字只列一次 |
| 字色与背景冲突时模型自行改色或加大胶囊 | 规划安排合适留白；允许既有小面积局部底衬，不恢复大胶囊系统；GPT 在统一墨色下处理排版 |

局部任务的目标表达示例：

> 设计一张磁吸部件功能信息图，产品画面由所选磁吸部件细节构成。附件中的其它产品视图仅核对部件身份。按本 child 的文字、图标系统自由设计版式。

这段替换通用 scope/数量/整物构图冲突表达，不是在现有长 prompt 后再加一段。

整物任务则表达完整商品结构与允许改变的环境；不能把局部任务的限制复制到 main/scene。尺寸图继续是参考图编辑任务，不切换为新渲染或 Pillow 排字。

### 6.2 共享设计落实到具体对象

- Gemini 决定 child 的床品、墙面、地面和图形角色；程序不恢复固定白色款色板，不用哈希随机组合颜色。
- 指令区分 text ink、icon/leader ink、环境/床品；允许它们有明确分工，但不能每图自行互换。相同 child 的对应角色统一，不要求所有像素都是同一个 HEX。
- 部件出现在画面才应用对应外观；色板不能隐含要求 size 添加床品、局部图添加整床，或让白底主图增加房间。
- 无衬线与衬线、线框与实心徽标的变化是明确设计偏离；阴影/曝光导致小幅色差不机械当成事实失败。
- 当前配色工具继续做诊断，不宣传其会自动保证美感。本次不增加自动调色循环或因色差反复重生；先证明单一设计确实传达并执行。
- func 的信息目标由 Gemini 拉开差异，GPT 自由设计层级和留白；不要在程序中规定统一的“标题+两圆框+引导线”模板。必要的小底衬保留，用户不接受的大胶囊不恢复。

### 6.3 检查最终请求，而不仅是模板文本

离线对当前错误任务核对：事实 → 规划字段 → 实际附件内容/用途 → 最终 prompt → provider 请求附件顺序。

- 每个必须保留的事实都有依据和唯一执行表达，每个新增可见命题都能追溯依据。
- 以语义职责去重，不按词语相同机械删除。数字去重不能破坏不同测量对象；删源背景样式不能删产品结构证据。
- 输出修改前后分段长度、重复职责及保留用途表。不设长度上线失败门槛，不先截断再修复含义。
- 复用现有日志记录版本和引用，不新增运行时同步器；旧 prompt 路径与对应旧测试应在替换时一起删除。

## 7. P3：只在现有恢复、调度和验收里闭环

### 7.1 恢复针对真正失败的步骤

| 结果状态 | 既有执行器内的动作 | 禁止行为 |
|---|---|---|
| 明确未受理/明确拒绝 | 按现有限次策略重试或使用允许的其它 provider | 把任何 5xx 都假定为未受理 |
| 已收到有效结果，下载/落盘失败 | 读取已保存响应，只恢复本地获取和收尾 | 新付费生成同一任务 |
| 结果不明 | provider 确有查询或幂等能力时使用；否则明确待确认，保留错误与请求身份 | 虚构 reconcile 能力，盲目重发导致重复扣费 |
| 已生成但硬事实错误 | 使用现有定向纠错/有限重试能力，修错误角色，保留其它有效图片 | 从 fetch 或全 child 重新开始，无限候选 |

查询/幂等能力必须先核实，不能在方案中假定 QC_YC、CXK 已提供。无该能力时，未知结果确实无法同时保证自动完成和绝不重复计费；这是需要明确披露的外部边界，不是再加 controller 能解决的问题。

### 7.2 调度随资源变化，但只有一个资源权威

- 现有线程池用稳定的安全上限，实际提交继续受每次动态内存准入和物理 provider 槽控制；不让启动瞬间仅一个槽永久限制整批。
- 保留跨进程资源租约及放大收尾余量；准入决定提交前完成，不把大量图片提前解码压在线程等待队列。
- 记录 available、promised、保留余量、任务估算峰值和渠道占用，区分内存等待与 provider 等待。
- 同渠道的多个模型不是多个物理 provider。根据允许且实际可用的 QC_YC/CXK 渠道调度，不重新启用 AICOST/LZ。
- func/size 在现有 routing 中优先采用已验证可用的 Sunburst 等适合复杂图的模型；保留当前允许模型范围，不额外多生成候选。可用性与实际质量要分别验证。
- 本轮没有发现 MemoryError，不能为旧内存问题扩大重写。当前 Real-ESRGAN 已真实运行，保持不动。

### 7.3 现有验收真正看成品

- 产品结构：完整商品视图检查底格、隔板、抽屉、连接关系；局部视图只检查宣称展示的部分，不因没有整物而误判。
- 量测：核对数字、比较符、限定语、对象、端点；不能 OCR 读到数字就通过。
- 调节位置、局部放大、透明示意要区分注释与实体部件，避免把示意一律判成新部件，也避免新增实体被误当示意放行。
- 现有 QA 如启用，消费本任务实际证据和事实；不重复引入源图风格要求，不新建 QA 模型调用流程。人工实图审计不能被伪装成自动 QA pass。
- 字体、色彩、美感和胶囊问题留在人工效果验收及已有设计纠错范围，不升级为无人值守硬失败规则。
- 源观察完成量、已形成角色量、已生成量、硬事实结果、人工设计意见分别汇总。仅请求 fetch 时，未请求 download 不算任务失败。

## 8. P4：先离线证明，再批准实测

### 8.1 离线验证及旧逻辑清理

用本轮真实错误记录形成最小行为测试，合并或替换重叠用例，不保留退休逻辑测试：

1. `≤6"`、范围与同值不同对象贯穿当前合同和最终 prompt。
2. 同 child 跨源事实合法，跨 child 与错误事实类型非法。
3. detail-only 的最终执行表达、实际附件与画面数量语义一致。
4. timeout/EOF 的 review 责任保留，只恢复缺项，不重做成功角色。
5. 已保存响应的下载恢复不增加 generation 请求数；未知结果不盲重发。
6. 资源由低到高时可提升并发，资源下降时停止新增准入；不越过现有租约和物理渠道容量。

最终生产测试集不超过 100 例、60 秒；不运行历史全量发现。通过只能声明程序链路验证完成，不能声明画质改善。

替换时必须物理清理：旧 source-only 第二次限制、丢测量限定语的投影、无条件全角色复核要求、局部/整物冲突模板、固定低线程上限行为以及依赖这些旧行为的测试。不删除未知计费保护、真实事实检查或有效资源保护。

沿用现有 schema/fingerprint 使受影响旧缓存失效，不读回旧合同兼容分支；不迁移、清理或重放历史 jobs。本轮审计产物只作为经授权的证据/测试样例，不作为新作业无条件可恢复的生产缓存。

### 8.2 获用户批准后才启动付费冻结测试

建议首批：本轮 White 床架和 Black 药品柜两个 child，生成其全部已确定角色，分别验证床品/文字系统和整物/尺寸结构一致性。第二批只验证已发现的 Brown 药品柜局部 func、Red 仿真树局部 func 与地插场景、White 浴室柜跨源 func；不要直接再次启动四 family 全量生成。

- 开始前确认 child、角色清单、预计请求量与允许的重试范围；先选范围，再冻结 job，避免再次发生全 family scope 后缩为两个 child。
- 冻结代码、配置和输入；测试中不修改。发现确定性错误就记录并结束该错误路径，不持续付费验证已知错误。
- 同 child 全角色一起比较；源图、实际附件和新成品对照，旧成品保留为基线，不把跨 provider/不同输入的比较声称为单一变量实验。
- 首先确认结构、测量没有回归，再判断配色、字体、版式和生活感。局部图不发明整物，完整图不丢原部件。
- 日志展示实际模型、物理渠道并发、内存峰值、请求数、恢复次数和耗时；不能用 provider 数量代替真实并行证据。
- 测试仅到用户批准范围，不默认上传或生成模板；如未运行已有 QA，继续明确标注 QA not_run。
- 失败只处理失败角色及真实依赖失效的角色，不因有一张问题重生整套，不无限续跑。

## 9. 交付判定

必须分三项报告，不用一个“全部通过”覆盖：

1. **程序一致性**：事实无损、同 child 引用正确、实际附件与计划一致、编译无冲突，离线行为测试通过。
2. **恢复与效率**：成功任务不重付费；失败归属明确；已返回结果可独立恢复；实际并发随资源变化。未知远端结果仍按真实能力披露边界。
3. **成品质量**：批准的实测中逐图检查结构和量测，逐 child 检查配色/字体/图形语言；审美改善由实际对照证明，不由测试数量和 prompt 字符数证明。

本方案本身没有修改生产代码、没有调用模型、没有生成图片。实施完成后仍需按仓库规定报告生产文件与增删行、删除的旧路径/测试、准确测试命令和耗时、尚未实图验证的内容。
