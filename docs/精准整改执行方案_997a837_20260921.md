## 1. 执行结论

**本轮修复已复现的错误及其必要调用链，不实施 A06 的完整设计扩展。**

优先闭合三件事：同一事实在各环节含义一致；合法输入和已有成果能正确使用；任务与最终交付状态如实反映所选范围。

现有生产链仍为 `fetch → copy → download → classify → brief → generate → qa → publish → template`。下面的批次仅表示代码修改顺序，不是新增生产阶段。图片测试继续遵守原有“只到生图”的范围，模板缺项不能前移成图片测试的依赖。

“不新增阻塞”以可验证的行为约束落实：合法输入原来可完成的路径继续完成；坏数据只在已有责任环节按原有失败/待处理机制处理；其它 child 和独立任务继续推进。不能用静默猜值、吞掉冲突或错误放行来满足表面上的不中断。

## 2. A06：本轮不立即执行完整改造

### 判断依据

1. `visual_design_kit_prompt` 已要求先分配不同买家问题，再选择证据、状态和文案；不是完全没有内容策划。
2. 现有规划已允许跨源图绑定事实，`product_sources` 可提供同 child 的补充证据；尺寸证据也不只来自标成 size 的源图。
3. 真正的限制是 `initial_output_inventory → task_specs → visual_design_kit_prompt` 预先固定角色、源图锚点和槽位数量，func 锚点尤其依赖 func 分类。这会限制某些新表达，但同时约束错分类、无证据重绘与恢复时角色漂移。
4. 本次双柜目标由规划明确指定；缺少第二 child 的原 Job 只形成首 child 的 DesignKit。这些证据不足以把问题归因于“没有由模型重新分配角色和图数”。
5. 全量改变分配方式会连带影响任务身份、候选复用、角色验收与模板裁剪，超出本轮最小修复范围。

### 本轮与后续边界

- **本轮立即做**：在现有 brief 事实/设计审查中消除已知数量与目标状态冲突，保留当前角色与任务身份；属于 A01/A02/A24 的正确性修复。
- **本轮不做**：让模型重分角色、重定图数、合并/拆分图库、放开 func/scene 任意互换，或新增选题/设计评分阶段。
- **重新启动 A06 的条件**：有具体样例证明“同 child 的真实功能证据已经存在、分类和事实也正确，但仅因锚点角色限制无法形成合理功能图”，或固定槽位持续造成无法在现有 brief 内消除的重复内容。先用该样例定位最小限制，不直接启动整套规划重构。
- 若触发，优先在现有锚点资格选择中做有证据的局部调整，仍保持 size/func 为原图编辑任务；不得采用无证据的新产品渲染或单图规划回退。

## 3. 第一批：事实与文案的确定性错误

### R1｜统一有效事实读取（A01，关联 A17）

**现有调用链**：ProductFamily 的原始字段/normalized_facts → 模板 `_family_specific`、Copy `_copy_facts`、视觉 `source_fact_records`。

**修改位置**：`core/product_family.py`、`core/template_engine.py`、`core/copy_polish.py`、`core/visual_semantics.py`；视觉消费端仅修改必要的事实投影调用。

**精确动作**：

1. 在已有 `product_family.py` 中提取有效事实读取函数，承接当前模板里已有的 resolved_facts 优先级，作为同一 ProductFamily 的读取规则，不新增事实文件或事实裁决器。
2. confirmed 覆盖对应原始值，conflicted 不得成为授权声明；保留明确的 false/0。只统一事实含义，模板专用字段/单位格式转换仍留在模板模块。
3. 原始文本和观察继续用于追溯；区分“观察到的原句”和“允许用于输出的事实”。冲突标题、原始五点及 OCR 也不得绕过有效事实重新授权，不能只删除一个结构化 key 就宣布修好。
4. 将已知裁决状态及有效值带入现有 Copy/规划事实输入和指纹，不增加模型调用或新审批。裁决缺失不是全局失败：未冲突且已有证据的事实继续可用。

**同次删除**：模板内被提取的重复 resolved_facts 消费循环、Copy/视觉中会绕过该规则的旧授权分支；原始来源记录不删除。

**验收**：同一 confirmed/conflicted/false/0 输入在三个消费端含义一致；无冲突普通商品继续运行；原始来源可追踪；只有依赖变化事实的现有产物按指纹失效。若现有指纹粒度只能到 child，不在本轮另造细粒度缓存系统，但必须报告实际失效范围。

### R2｜销售数量冲突不能被早返回隐藏（A02）

**位置**：`products/generic_extractors.py` 的 `explicit_item_count` 及其调用方，`core/source_fetch/apify.py` 的 `_source_sold_unit_count`。

**动作**：在确定单一销量数之前，比较现有明确数量证据；覆盖 Number of Items 与标题 Set/Pack 的直接冲突。数量收集只保留一处实现，沿用现有 status/candidates 冲突字段。包装件数、零件数、源图中同物体多状态、场景陈列数量不混作销售件数。

**删除**：未检查其它明确证据就返回“已确认、无冲突”的旧分支。

**验收**：1 对 2 标记冲突而不伪装确认；2 对 2 确认；正常单件和真实两件套不误伤。不把数量冲突变成整个 Job 新入口闸门；仅数量相关声明/画面按已有责任机制处理。

### R3｜声明和搜索词按肯定事实授权（A05/A13）

**位置**：`core/copy_writer.py::_validate_copy_compliance`、`core/backend_keywords.py`。

**动作**：替换“序列化文本含关键词即授权”的分支；对已有受控声明判断同一主体、性质、肯定/否定及适用范围。false、否定句、未知、冲突不能证明肯定声明。tempered 不等于 shatterproof；eco 不等于所有环保主张。沿用原有 Copy 错误合并修复，不增加修复轮数。

搜索词删除无条件的安装方式候选；只有当前 child 已确认壁挂/嵌入/跨马桶兼容等事实时才允许相应条件词。对竞争词、extra_terms 中同类条件词使用同一规则，不能只改静态词库却从另一个入口重新加入。不要求缺少安装信息的商品补全字段：保留普通类别词即可。

**删除**：被替代的宽泛关键词授权和无条件事实型同义词。

**验收**：waterproof=false 拒绝防水声明，肯定防水证据允许；tempered 不放行 shatterproof；落地柜不含 wall/recessed cabinet，确证壁挂柜可使用；正常无风险 Copy 不增加请求次数。

### R4｜Copy 分组、父体恢复和来源身份（A17/A18/A19）

**位置**：`core/copy_polish.py::_copy_group_key/_load_fragment` 及其调用方，`core/copy_writer.py` 的现有 repair 函数。

**动作**：

**验收**：同文本不同材料/套数不共享；安全相同事实仍共享；合法父体片段恢复时零新增远端请求；来源 ASIN 非空且属于真实成员。

## 4. 第二批：模板值和最终图片的确定性错误

### R5｜保留 0/false，拒绝非有限数（A10/A11）

**位置**：`core/template_runtime.py::template_job_with_defaults`、`core/template_field_plan.py::looks_numeric`、已有字段校验处。

**动作**：默认值仅补缺失、None 或空白；false 显式规范为现有枚举字符串，不用真值判断代替缺失判断。数值检查增加有限性；库存数量按非负整数，合法尺寸/重量小数按现有字段含义校验。缺失必填仍由现有必填规则处理。

**删除**：`value or default` 覆盖有效零值的写法、仅 float 可解析就合格的旧分支。

**验收**：数字和字符串形式的 0/false 均正确保留；空值仍取原默认；NaN/±inf 拒绝；合法 1.5 尺寸不误拒。仅在 template 责任范围校验，不影响图片运行。

### R6｜禁止非豁免多 child 共用单一商品编码（A09，复用 A20）

**位置**：`core/template_engine.py` 的既有 job contract/child ListingData 赋值，以及 `core/production.py` 的现有入口调用。

**本轮选定最小方案**：当前输入只有 job 级单一 product_id，不新增多编码配置体系。GTIN 豁免路径及非豁免单 child 保持；非豁免多 child 且仅有一个编码时，在既有 submit_ready 合同中明确该组合不支持，不能复制编码生成貌似合法的模板。

**验收**：豁免双 child 正常；非豁免单 child 正常；非法共享编码不能进入 submit_ready，错误明确指出配置组合；图片阶段不受影响。

### R7｜模板裁图保留已有最低角色覆盖（A07）

**动作**：读取现有品类 required_role_policy 的最低配额，优先保留必需角色，再按已有稳定顺序删除超额可选项；继续记录 omitted。剩余预算内不新增“重要性评分器”或选图模型。调用者传入现有配额，不能在裁图函数再维护一份品类规则。

**删除**：无条件先清空 scene 再删 func/size 的旧循环。

**验收**：1scene+7func+1size 裁为 8 张附图时 scene/size 保留；四品类常规布局、少于上限、刚好上限均正确；相同输入顺序稳定；不因可选图超额重生成。配额确实大于模板容量时只在现有模板校验给出具体冲突，不静默丢必需角色。
