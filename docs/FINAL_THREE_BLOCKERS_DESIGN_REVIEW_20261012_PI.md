# 最后三个 brief 阻塞：偶发、确定性逻辑与必要保护的区分

日期：2026-10-12。范围限于用户指定的四个原 job 与冻结代码，不修改生产代码、任务、预算、回执，不发请求、不运行 SAM 或生产测试套件。

## 一、结论

**项目确实仍有设计不合理，但不能把三个图位统统归因为“项目把正确结果卡死”。**

1. 棕药柜 scene_04、紫树 func：存在可重复的**能力合同—执行准入不一致和恢复状态缺失**。相同输入、相同合法修改、仅剩一次调用时，当前程序确定性拒绝；不是 JSON 偶发漏项。
2. 蓝药柜 size：修复后已有 SAM 区域，当前停止首先是**缺少对新结果的确认且额度耗尽**。这项保护合理；进一步看图发现其蒙版确有多视图覆盖缺口，不能简单绕过或保证“再确认一次就结束”。
3. 三项都涉及模型/分割结果质量，但不能从这些样本推算随机失败率，更不能声称该项目所有任务必然失败。
4. 73 个已生成候选是生产可达性的证据，不是画质通过的证据；本轮三个图位均不再由网络超时/未知生图回执阻断。

## 二、方法：先提出可证伪假设，再控制变量

假设：两个已有 mask 的区域修改，在当前场景中被拒绝的直接原因是最后一次调用的能力/预算分支，而非格式错误、证据矛盾或传输失败。

证伪条件：原回包不能通过其冻结 schema/完整合同；保持原补丁只改变剩余额度后仍被同一更早的身份/事实错误阻断；或同额度的真实成功对照也无差别失败。

执行方式：

- 读取实际请求、raw response、回执、journal、源图和 SAM 证据。
- 对冻结代码的真实 `_finish_image_briefs()` 做内存隔离回放，保留完整库存和已有接受的兄弟角色。
- ledger、传输和新推理边界使用内存替身；原回执先独立进行真实校验。
- 实验只改“可用额度 1 / 2”，每种条件重复 3 次；额度为 2 时在准入新 SAM 准备的边界立即停止，**不执行推理，也不声称之后会生成合格图**。
- 使用真实成功回包作为反例对照，不为失败图位捏造 accept。

证据：`test_runs/pi_logic_boundary_audit_20261012/hypothesis.json`、`controller_probe.py`、`controller_probe_results.json`。

## 三、三个图位逐项归因

### A. 棕药柜 B0DCBRXCMG / scene_04

**原始触发：**规划者看过当前工具结果，要求把正点移到柜体材料上、添加排除点，修改 query。源图和 anchor_details 显示原 P1 在护肤品上，P2 在镜面反射内容上；因此这个修改需求不是毫无依据的格式挑剔。不能据此断言新点一定正确，或新 SAM 一定更好。

**直接阻塞：**

- 原回包 `patch_plan` 完整；回执和当前输入绑定相符。
- 该 patch 通过请求 schema，替换后的完整合同也通过。
- 当前请求 `writable_fields` 包含 `region_intent`，同时 `can_modify=false`。
- 执行器发现已有 mask 且区域依赖将改变，拒绝执行。

**定性：**原始点位/措辞选择属于输入相关的模型质量问题，未测其随机发生率；对已经返回的这份合法补丁，后续拒绝是确定性控制分支。预算不能擅自突破，但程序不能一面允许提案，一面把自己的执行能力不足报成“工具协议不完整”。

### B. 紫树 B0GG3M4DL8 / func

**原始触发：**目标要求插地钉、连接树干、整形枝条等步骤；当前保护主要落在第一步的地钉/圆盘。SAM 候选中还保存着第二步部件和独立地钉的候选，但默认选择没有把这些补齐。

两次保存回包均提出区域修改，未虚构额外售卖实例。第五次与第四次的具体点位/query 并不完全相同；不能说模型“一字不差重复同一答案”。但两者都落入同一能力缺口：**有当前 mask、需要物理修改、只剩本次调用、没有后续确认额度**。

**定性：**这不是无条件永久死锁；有足够后续容量时存在合法进路。但在“每次只追加 1 次、模型仍如实要求区域修改”这一策略下，存在条件性循环：花掉本次调用，却不提交可继续的工作。

### C. 蓝药柜 B0GF2357FX / size

这里必须纠正“仍缺 region”的含混表述：

- 第五次请求已把重复 owner 的两个 target 修为一个 owner。
- SAM 已执行并保存 region.json、mask 和查看图。
- 当前 `needs_region` 实际是**需要规划者对该结果作决定**，不是没有 SAM 文件，也不是上一份 patch 因同一准入错误失败。

新看图证据使上次“一次确认”的估算必须收紧：

- 当前目标明确要求关门图展示外尺寸、开门图展示内部尺寸。
- SAM 返回两个同属 `medicine_cabinet_01` 的候选：
  - `060bc75ca580141c72e5`：关门视图，score 0.96875；
  - `3bd339a0ddea4b7034a0`：开门视图，score 0.966796875。
- 程序按每个 unit 只提议一个最高分候选，因此当前只选了关门视图。
- 在原图核对过的下方开门区域，当前保护像素为 0；纳入已经返回的另一候选后，该检查窗口内有 520,553 个保护像素。
- 两候选没有被删除；在内存中，以同一 owner 选择两个现有候选可通过现有 `validate_region_action()`，不需要伪造第二个售卖实例。

**定性：**“没有最终接受就不生成”是必要保护，不应移除。默认单候选提案对这个多视图输入不完整，是给定返回结果下的确定性选择结果；但它本来不是最终视觉验收。问题在于多视图表达、候选选择和后续确认能力没有形成可靠的完整流程，而非 SAM 一定失效。

当前样本不能证明“再问一次一定接受”。若规划者正确要求补选开门视图，而仍只有一次额度，便可能碰到前两项同类的能力困境。这是可推导风险，**不是已发生的第六次调用结果**。

## 四、控制变量结果：不是把所有失败都怪程序

| 实际回包 / 对照 | 内存可用调用 | 结果 |
|---|---:|---|
| 棕药柜 scene_04 原区域 patch | 1 | 3/3 在新区域准备前拒绝；最终 budget_exhausted / protocol_incomplete |
| 同一回包，其他输入不变 | 2 | 3/3 通过该准入点；在新 SAM 准备边界主动停止 |
| 紫树 func 原区域 patch | 1 | 3/3 同样拒绝 |
| 同一回包，其他输入不变 | 2 | 3/3 通过该准入点；未运行 SAM |
| 床架 func 真实“修 wall + 接受当前 mask”回包 | 1 | ready |
| 白树 scene_02 真实接受回包 | 1 | ready |
| 蓝药柜 size 原第五次修 owner 回包 + 已保存 SAM 结果 | 1 | 修复生效、结果保留，随后因缺确认停在 needs_region |

这里的 3/3 是同一保存输入的确定性软件回放，**不是模型线上成功率实验**。

因此，“只要 can_modify=false 就必然失败”“最后一次请求总会浪费”“所有三项都属于协议错误”都不成立。准确条件是：

```
需要改变既有区域
AND 本次之后没有确认容量
AND schema 仍允许返回该修改
AND 没有保存成待授权接续的工作
→ 相同条件下必然无法完成这条修改路径
```

不能通过无条件改成 `can_modify=true` 解决，否则会跨越既有预算和未见结果的确认边界。

## 五、已确认的项目问题与其责任边界

### 5.1 确认的逻辑不一致

- `core/visual_design_kit.py` 约 354–370 行：预算计算得到 `can_modify=false`，但有效草稿仍取得全字段可写集合。
- `core/planning_contract.py:response_row_schema()`：该 flag 限制 `change_region`，没有一致限制 `patch_plan` 的区域字段。
- `core/visual_design_kit.py` 约 307–309 行：实际执行却禁止同一物理变化。

这是同一能力的两套不一致定义。回复 schema 合法不等于应立即执行，但无法执行的合法需求必须有明确的延后状态，而不是被包装成模型协议错误。

### 5.2 合法提案没有转成可接续工作

原回包确实保存在审计记录里，**不是字节丢失**。但在抛出准入错误之前，未生成相应 `pending_action`。普通 resume 不能在权限满足后直接沿该已验证提案继续，反而重新购买决策。

是否能复用旧提案需要明确的当前输入校验和执行授权，不能因为 raw response 存在就直接套用旧接受。建议修的是提案生命周期，不是伪造批准。

### 5.3 错误被覆盖，追加额度又重置无进展记录

真实控制器回放显示消息顺序：

1. `Another physical modification or its confirmation is not authorized`
2. `Existing allowance cannot finish protocol_incomplete ...`

最后只剩第二条，前一条被预算状态覆盖。恢复时，无论是输入变化还是仅新增额度，都执行 `protocol_failures={}`。

在同输入的三次内存单笔 grant 实验中：已消费量依次为 5、6、7，但同一失败签名每次仍计为 1，均无可继续 pending_action。这里**费用计数没有被重置**；被重置的是无进展保护。两者不可混称。

### 5.4 多视图提案的完整性与规划表达

一个售卖物体可以在多幅图/多个操作步骤中出现。唯一 owner 校验是正确的，不能靠重复 owner 或增加售卖数量骗过。

当前模型把两个 size target 合并成“一个 owner、大 crop、无 parts”；默认算法按 unit 选单个最高分，于是形成只覆盖一幅视图的提案。紫树同样把多个步骤放入一个大 query，另一个 part 又重复第一步。

这说明输入到几何工具的**instance / part / view** 表达仍弱。既有 parts/候选多选已有可用能力，应首先正确使用；不能因此自动合并所有 SAM 候选，因为其中也可能包含道具、错物体或互相替代的分割。

该问题会增加需要修正的概率，但没有新的模型/分割独立重复样本，不能估算发生率，也不能证明所有多视图必错。

### 5.5 “移动锚点就能修 SAM”不能被当作保证

`ProductRegions.prepare()` 使用 semantic 模式。工作器的该分支由图像 crop 与文本 query 驱动，**不把正负点送入 semantic segmentation**；正负点用于候选诊断。interactive delta 分支才实际使用点。

棕药柜的回包也改变了 query，紫树还改变了 crop，因此不能断言它们的修改“完全无效”。但不能把“锚点换对了”与“蒙版会修好”画等号；只改诊断点的重跑不足以证明像素改善。

这是工具能力需要向规划者说明清楚的设计风险，不是本次执行被拒绝的直接原因。

## 六、不是项目缺陷的边界

- 不允许超出明确批准的物理调用额度：正确。
- 新 mask 产生后，未经实际查看/接受不生成：正确；尤其当前 size 确有缺失视图。
- source、owner、mask、回执必须绑定，不能把两幅同物体视图冒充两个售卖实例：正确。
- 明确合同错误不得自动更改事实或放行：正确。
- 旧未知图片请求按明确授权只重发一次并保留链路：与当前三个规划停机不是同一问题。

需要修正的是这些边界之间的衔接和如实报告，不是删除保护、再加审核模型或另建快速流程。

尤其要区分：**禁止未授权的后续付费请求/禁止接受未检查的新 mask**，并不逻辑必然地要求**丢弃有效提案或禁止一切本地进展**。若既有本地区域操作权限和资源预算允许，可以明确设计为准备结果后停在待确认；否则至少保存为待授权执行。是否先预留整条链是准入策略选择，不应伪装成模型协议错误。这里不构成对现有旧回包的自动执行授权。

## 七、对偶发与必然的最终分类

| 事项 | 分类 | 可以下的结论 |
|---|---|---|
| 模型初次点位不佳、重复 owner、没有拆分必要 views | 输入/模型相关偏差 | 当前样本有具体证据；无随机失败率或普遍必然性结论 |
| semantic 分割的具体候选形状/分数 | 模型与输入相关 | 只观察到本次结果，未真实复跑 SAM，不能断言换 query 后结果 |
| 对这份 size 返回只取 unit 的最高分候选 | 给定候选集合后的确定性程序选择 | 可重现遗漏开门视图；不是候选从未返回 |
| 两份合法物理 patch 在只剩一次时被否决 | 条件性确定性阻塞 | 改唯一预算条件即可越过该准入分支；不等于后续图像会合格 |
| 真正缺少后续确认而停止 | 必要预算/验收保护 | 不能自动越过；工作量需按依赖链计算 |
| 单笔 grant 后重复决策、错误覆盖、无进展计数清空 | 确认的恢复/诊断设计问题 | 可制造持续无进展，不是网络偶发 |
| 所有 76 图位都必然被项目卡住 | 不成立 | 实际成功角色与同额度控制组均提供反例 |

## 八、改进优先级（仅分析，未实施）

1. **先对齐能力合同。** 同一权限计算应同时供请求 schema、可写字段、预算预留和执行器使用。不能让模型只能在“不实接受、语义拒绝、合法但必被程序拒绝的修改”之间选择。
2. **保存合规但待授权的提案。** 分开提议、准入、执行、实际结果确认；依据输入绑定恢复，不重新购买已获得的同类决策，不自动扩额度。既有本地操作权限充足时，可讨论执行后停在待确认；无论采用哪种策略，都不能静默增加远程请求或提前接受新结果。
3. **按剩余依赖链申请预算。** 确认、选择已有候选、新推理、结果确认的成本不同；不要把“一个 pending role”机械等同于“一次调用可完成”。
4. **保留根因和累计无进展。** 预算不足是附加状态；单纯 grant 不改变内容，也不应清空同内容失败记录。
5. **先利用现有候选与 owned views。** 蓝药柜已具有开门候选，下一步不应默认重新分割，更不能强行接受当前漏视图 mask。
6. **增加缺失的定向覆盖而非扩大测试全集。** 覆盖最后一次额度的合法物理 patch、多次 +1 的恢复、两个 view 同 owner、多候选选择和未确认结果。既有 99/100 的那条旧断言错误不能用来解释或掩盖这里的状态分支遗漏。

上次“蓝药柜 size 再确认一次”的说法仅是状态路径估算。此次看到其实际蒙版后，更准确的结论是：**必须先确认覆盖是否满足；现有图明显漏了开门视图，不能承诺一次即可结束。**
