# Child 视觉协作最终整改方案

日期：2026-09-16

状态：实施前方案。本文不表示生产代码已经修改，也不表示实图质量已经通过。

## 1. 最终目标与边界

恢复原始目标：以实际产品的颜色、材质、用途、适用人群和美国市场为依据，由 Gemini 制定一个 child 的整体视觉方向，由 GPT 生图模型完成各张图片的具体设计与成像。

三个层次各有一个负责人，而不是让一个模型包办全部决定：

| 层次 | 负责人 | 保留的责任 | 不承担的责任 |
| --- | --- | --- | --- |
| 产品事实与流程 | 程序传递已确认事实；现有视觉观察负责必要识别 | 同 child 身份、来源、结构证据、功能、尺寸、单位、调用与状态 | 程序猜产品结构、判断审美、按产品颜色硬选色板 |
| Child 视觉方向 | Gemini | 人群与使用情境、核心配色、材质搭配、光线方向、字体和图形语言、各图沟通目标 | 逐图排版坐标、完整道具清单、所有图标与局部布局 |
| 单图设计与成像 | GPT 生图模型 | 布景、构图、产品呈现、光影、信息层级、留白、图标和文字的具体排版 | 修改产品事实、自选另一套核心配色、编造尺寸或卖点 |
| 现有验收 | 现有 QA 与人工实图检查 | QA 检查事实及发布硬要求；人工检查设计效果和统一性 | 自动审美评分、因风格偏好阻塞生产 |

统一性以 child 为单位，不增加 family 色板路线。同颜色不同 child 可以采用不同方案，不强制随机，也不强制重复。

不新增 stage、controller、QA 流程、候选流程、feature flag 或第二套 prompt；不增加默认模型调用轮次。不恢复固定色板表，不引入在线临时选色依赖。

不调整现有类目 main 策略：床架保持 lifestyle，其它类目按各自现行策略。不改品牌、制造商、产地、数量、履约、GTIN、模板默认值、调度、provider 停用状态或放大链路。

“不造成新阻塞”指不新增审美门槛、必需素材包、必需抠图工具或新的等待条件，不是取消现有产品事实失败，也不是保证外部接口永不失败。

## 2. 已证实的问题与整改对应

证据范围为本轮 `test_runs/freeze_scoped_20260916/B0FHD4MS3K_20260916T074232871516` 及已完成的 QC func/size 独立补测，不外推为所有历史任务的统一根因。

| 已确认的问题 | 证据与边界 | 对应整改 |
| --- | --- | --- |
| 源图样式进入整体设计 | 源图圆环抱枕、黄白条纹毯、藤编床头柜进入 Gemini 原始回复及成品；输入文字没有相应描述 | P0 改规划视觉输入，P1 重划设计职责 |
| “颜色由 Gemini 输出”不等于独立设计 | 原始回复色板与最终规划一致，程序未另行换色 | 不恢复程序固定配色，解决输入和任务定义 |
| Gemini 任务过细 | 当前写明 sole visual designer，并输出逐图构图、布局与文字坐标 | P1 删除微观设计字段，GPT 接管单图设计 |
| 同一图两套颜色指令 | scene_02 creative_brief 写 olive/beige，共享被套定义为 terracotta；两者均进入最终 prompt | P1 删除重复指令入口，P2 单一编译 |
| 核心组件漏传 | scene_02 未选择 sleeping_pillow，程序按 scene_objects 剪掉该组件要求 | P2 删除逐图组件白名单式裁剪 |
| 技术角色受到卧室指令干扰 | size 同时收到技术画布与全局暖色卧室、侧窗光线描述，实际输出加入房间 | P2 按现有环境模式投影，删除全局场景复述 |
| 生图仍继承旧图形样式 | QC size 出现棕色尺寸字、白描边；func 出现棕底白字，与规划不一致 | P2 明确事实与样式用途，P4 实图检验执行 |
| 现有检查漏掉明确冲突 | scene_02 review 只确认产品及抽屉状态，未发现两套床品颜色 | P3 保留现有矛盾检查，但先删除冲突产生入口 |
| 配色工具仅生成事后报告 | palette_diagnostics 在规划完成后写出，无选色、回写或审美能力 | 明确工具边界，不再将诊断文件当成配色改善证明 |

尚未证明：每个 HEX 都来自源图精确取色；所有问题都由源图引起；仅替换一段提示词就能保证模型脱离参考样式。整改不能以这些未经验证的假设为验收依据。

## 3. 现有链路与必须同步处理的依赖

当前链路：现有分类/联合观察 -> final source intents -> visual design kit -> image task -> prompt -> generation -> 现有 QA -> 模板。

修改落在原有链路内部，主链路与阶段顺序不变。

| 文件/职责 | 修改内容 |
| --- | --- |
| core/visual_semantics.py 的 observe_child_sources | 继续识别产品与必要事实；用现有 reference_views 选择适合整体设计的外观主参考，不恢复普通道具清单 |
| core/image_reference_context.py | 区分规划外观输入与执行事实输入的投影；共用当前证据身份、裁切和来源校验，不复制一个新参考系统 |
| core/visual_design_kit.py | 精简规划任务与输入，删除唯一设计者定位和重复场景复述，更新修复请求及版本指纹 |
| core/visual_design_kit_compiler.py | 同步删除旧字段、验证器、投影器；保留产品、功能、文案、测量证据关联 |
| core/image_task_inputs.py、core/image_tasks.py | 按环境模式投影 child 核心设计；移除 scene_objects 白名单；同步任务与共享设计指纹 |
| core/image_prompt_compiler.py | 原位替换为单一语义编译，删除微观布局与重复风格段，不增加第二份运行 prompt |
| core/visual_semantics.py 的 review/candidate_view_targets | 适配新规划字段；删除对预设设计坐标的依赖，保留全图产品事实与真实测量检查 |
| 当前生产测试及其 fixture | 替换旧字段和旧行为断言，保留事实/恢复/发布保护，不增加历史测试集合 |

注意：现有 candidate_search_regions 是位置提示，不是硬性的候选边界。这里是删除设计坐标后的接口适配，不能把现状描述成 QA 强制逐像素复刻布局。

## 4. P0：修正参考输入，而不是再加“不要模仿”

### 4.1 分类/观察仍看必要源图，规划不再默认看整套装饰场景

1. 现有联合观察保留完整必要输入，用于确认 child 身份、产品结构、功能和尺寸。
2. 使用现有 reference_views 的 appearance 选择，优先原始、清楚、产品完整且非产品干扰少的同 child 外观图。不能按白色背景简单判断可靠性，也不能混入其它颜色变体。
3. Gemini 整体设计的图片输入改为选定的产品外观主参考及确有必要的补充外观；不再把每个功能/场景/尺寸的 physical_view 默认全部作为设计视觉输入。
4. 各图功能、尺寸及证据身份通过现有事实目录交给规划。原始功能/尺寸像素仍供 GPT 编辑和现有事实核查使用，不以“减负”为由丢掉它们。
5. Gemini 在规划中只引用观察结果已建立的事实与视图身份，不重新承担全图库分类和逐张版面拆解。证据缺陷仍由既有观察纠错归属处理。

这不是新建“先设计、再设计”的两轮 Gemini 调用；仍然只有当前规划调用，改变其输入职责。

### 4.2 没有纯产品图时的处理

- 不生成一张可能改变结构的“干净产品图”充当事实，不增加必需抠图/分割服务。
- 在同一参考选择规则内，使用现有可靠外观视图，并在当前 trace 记录仍含场景信息的边界；不因背景不纯而新增失败。
- 矩形裁切只在不伤产品、遮挡关系和必要信息时使用，不自动擦除床品、补画隐藏床架或剪断抽屉/腿/测量对象。
- 没有纯图时不能宣称已经物理消除源图影响。其效果须在 P4 单独核查，而不是靠声明“事实参考”就认定有效。

### 4.3 需一次同步的修改

`planning_view_inputs`、`prepare_planning_views`、附件编号、请求中的 evidence attachment map 与 trace manifest 必须来自同一选定列表。保留完整事实目录，不把未附图的事实伪装成已附图。

执行附件继续由现有 `resolve_edit_references` 按必要产品证据生成。规划少看图不等于执行少看事实，更不能把 func/size 退化为只附一张外观图的重建任务。

验收：附件数/编号/哈希一致；同 child 身份不丢；规划不再自动看到所有角色的装饰场景；生成和现有核查仍拿到必要功能及测量像素。

## 5. P1：Gemini 负责方向，GPT 负责单图设计

### 5.1 Gemini 保留的最小设计输出

- Child 层：基于证据的人群/用途/市场、核心非产品组件配色与材质、房间基调、摄影方向、字体家族与信息层级原则、图形颜色关系。
- 单图层：role 身份、买家沟通目标、必要事实及视图关联、环境模式、func/size 的确认文案；合适且已有批准的设计参考可继续使用。
- 核心组件是影响一套图身份的主要床品、主要背景等，不要求穷举所有书本、瓶子、摆件、家具款型。
- 减少自由段落中的复述：人群字段不写灯光和颜色；环境字段不重复色值；产品颜色只来自产品事实；非产品外观只来自 palette_direction。
- 共享 photography_direction 只定义曝光、色温、反差与材质表现，不写卧室窗户位置、窗帘或房间叙事。具体光线方向由 GPT 结合本图设计，避免依赖程序事后删词来给 size 清理卧室描述。
- 不强制白色 child 配某种颜色；不加入随机抽色、固定路线或“必须与其它 child 不同”的程序逻辑。

保留当前 child 产物载体，不借字段历史名称 family_art_direction 增加 family 级权威，也不做与行为无关的大规模改名。

### 5.2 物理删除的旧设计入口

| 删除内容 | 原因 | 替代责任 |
| --- | --- | --- |
| sole visual designer 定位 | 把 GPT 降成过细指令执行者 | Gemini 管整体，GPT 管单图 |
| image_direction.creative_brief | 当前同时描述视角、布景、配色，形成第二套外观定义 | 保留 visual_goal 与必要事实，具体设计交 GPT |
| layout / target_region 目标布局 | 不应在规划中规定产品画面坐标 | GPT 构图；现有 QA 观察实际画面 |
| text_placement / 逐条 none-local 决策 | 微观排版提前锁定，且产生大量坐标/标签关联 | 共享图形语言 + GPT 按实际背景排版 |
| scene_objects 逐图白名单 | 漏列组件会漏传已确定的外观 | P2 统一核心组件按模式适用 |
| cohesion_rule 执行段 | 容易把整套房间和床品重复带入技术角色 | 用共享 palette、摄影、字体及环境字段本身表达统一性 |
| negative_visuals 中由模型重复生成的一套公共禁止项 | 与产品边界、角色规则、用户要求重复并可能相互覆盖 | 用户明确约束在现有编译器中表达一次，不再要求 Gemini 重写 |

移除字段时同时删除读写、校验、局部修复、指纹和测试中的对应旧行为，不能仅把字段改成空列表，也不能改名后继续塞相同内容。

### 5.3 GPT 的自由边界

GPT 决定：合理取景、产品在画面中的位置、非核心装饰选择与摆放、材质微观表现、自然光影、标题尺度、换行、留白、信息组织、必要局部图及引导线设计。

GPT 不决定：另一套核心床品颜色、另一套文字/图标颜色体系、产品结构/数量/材质事实、未经证实的功能、尺寸值及测量对象。

允许布局和可替换环境变化，不允许为了“设计感”拼出没有证据的接头、支撑、滑轮或局部结构。局部图不是强制组件；一旦展示，必须有对应真实证据。

## 6. P2：单一语义编译与核心配色完整传递

### 6.1 一份 prompt，五类信息

1. 产品身份、不可改变的事实和附件用途。
2. 本图沟通目标、必要功能/测量展示及现有类目策略。
3. 适用于本图的 child 核心设计。
4. 确认文案和尺寸标签，各有唯一来源。
5. 现有输出要求及用户明确约束。

这五类是现有编译器内部的信息分工，不是五个新阶段，也不是另外维护一份 prompt 模板。

同一事实/色彩组件只在所属位置完整定义一次。引用事实身份、附件和测量端点不是无用重复，不能因为追求字符数把功能或尺寸依据删掉。

### 6.2 配色的统一与自由

- designed_environment 的各图接收同一套精简的核心设计，不再由逐图组件白名单决定是否传递枕套等关键要求。
- 核心组件定义只约束实际出现的组件，不要求每张图把所有组件摆出来，也不能为放入床品遮住需要展示的排骨架或机构。
- 次要道具由 GPT 围绕核心设计搭配，不由 Gemini 穷举每件物品，不形成第三套组件配色表。
- graphic_canvas 不接收房间布置、卧室侧窗和窗帘等指令；source_setting 只保留必要安装关系；white_background main 严格执行现有类目策略。
- graphic_canvas 中必要的非产品对象可沿用核心外观定义，但条件式适用，不引入房间布置指令，不强制加床品。
- 技术图保留曝光、清晰度和材质表现要求，不机械继承整套卧室摄影叙事。

文字、徽标、箭头必须服从共享的图形角色定义；不要求所有图形角色都使用同一个 HEX。尺寸数字归文字角色，箭头归引导线角色，不能混用。局部底衬的颜色和符号对比来自共享定义；GPT 决定具体是否必要及形状，不固定成整排胶囊组件。

床品布料和墙面的 HEX 是目标色彩参考，不是对每个像素的机械等值要求。真实光照阴影允许变化，但不等于允许被套换色系或字体任意变色。

### 6.3 配色工具的真实定位

继续使用现有 colour-science/本地计算对已规划色值进行亮度、色差和对比度诊断，用于整改报告与人工实图复核。明确它测的是给定色值和可能表面，并非真实成品像素，也不证明符合美国市场审美。

本次不扩建自动选色引擎，不为诊断新增模型调用、自动回写、审美分数或重试环。整体设计由 Gemini 做，单图搭配由 GPT 做；不得再把“诊断文件存在”报告为“工具已经保证配色优质”。需要算法辅助时使用真实计算结果，不用程序自拟的好看分数替代设计。

验收：scene_02 不再有可重新定义橄榄绿床品的第二段；所有适用图均获得同一核心枕套/被套定义；size 没有卧室叙事混入；func/size 文案、数量和端点仍完整。

## 7. P3：现有验收、恢复与旧行为清理一起适配

### 7.1 现有检查只适配，不扩权

- 保留产品、功能、确认文案、单位、测量对象与端点检查，以及明确的事实/执行指令矛盾检查。
- visual_goal 与 design_transfer 等保留的自由文本仍可能出现越权描述；交给现有计划核查识别明确冲突，不能把“没有 HEX”当成“没有颜色冲突”。不增加颜色词黑名单或另一个审美审查调用。
- 不要求 source 与 target 道具、房间、镜头、标签形状、插图数量一模一样。
- `candidate_view_targets` 不再从 Gemini 的目标布局坐标构造搜索范围，使用现有全图观察与实际候选区域定位；保留必要事实清单。
- 原始图片坐标、裁切溯源、测量端点和 QA 实际观察坐标必须保留。它们是事实证据，不是待删除的设计坐标。
- 保留逐图结果和现有有限纠错归属；观察缺陷回观察，计划事实错误回规划，接口失败按现有 provider 重试处理，不能借本次改造恢复全 child 无限重跑。
- 普通书本文字不一律禁止；品牌与未知标识按证据处理，不把所有道具字样都当品牌。尽量无人及人物倒影要求保留一次，不重复堆砌。

### 7.2 必须删除的消费者与兼容行为

- 删除 `_project_text_placement` 及只服务它的旧处理；`_text_refs` 若仅服务旧坐标校验则同步删除，不能误删确认文案绑定。
- 删除 `_role_content` 内目标坐标、标签坐标的输出；删除 `_family_art_direction` 内 cohesion_rule / 模型重复 negative_visuals 的输出。
- 删除 role_art_direction、brief validation、review payload、shared repair 中 scene_objects 相关白名单和旧字段。
- 更新 schema/policy/input revision，拒绝把旧 design kit、旧 task、旧 prompt 默默转换进新生产；不加兼容默认值让旧字段继续生效。
- 同一修改批次删除对应过时测试，修改当前 fixture。保留语义级保证，不保留“必须有 layout 字段”之类实现断言。

代码阅读发现当前测试验证“选中的组件被传递”，但不能证明“所有实际需要的核心组件均被传递”；重写该测试含义，不能只把字段名删到测试变绿。

历史产物作为只读对比证据，不扫描、迁移或清理 jobs。当前运行任务如需完成应使用其原有冻结版本，不能中途接上新 schema；不得自动打断正在执行的生产。

### 7.3 精简后的行为测试清单

| 必须验证的行为 | 当前承载位置 |
| --- | --- |
| 规划附件与执行证据分工正确；同 child、哈希、编号无误 | tests/test_root_cause_remediation.py、tests/test_visual_design_remediation.py |
| 核心组件不会因某图少填列表而丢失；无第二套颜色定义入口 | tests/child_palette_regression_fixture.py 及现有调用它的生产测试 |
| 房间图、技术图、类目白底 main 的投影正确 | tests/test_image_branch_v1.py、tests/test_visual_design_remediation.py |
| 布局自由不使 QA 漏掉产品结构、功能或尺寸事实 | tests/test_qa_lite_v1.py、tests/test_us_measurement_contract.py |
| 旧规划失效且不会冒充当前；合格结果保留、修复不扩散 | tests/test_freeze_recovery.py、tests/test_status_revision_contract.py |

编辑期间按修改点运行对应模块，不反复跑全套。最后仅运行一次当前 production suite，维持不超过 100 cases / 60 秒，不做历史 discovery。示例命令：

```powershell
D:\anaconda\python.exe -B -m unittest tests.test_visual_design_remediation tests.test_root_cause_remediation
D:\anaconda\python.exe -B -m unittest tests.test_image_branch_v1 tests.test_qa_lite_v1 tests.test_us_measurement_contract tests.test_freeze_recovery tests.test_status_revision_contract
D:\anaconda\python.exe -B scripts/run_production_tests.py
```

以上命令是实施后的验证计划，本次未执行。不得用提高预算、跳过事实断言来满足测试要求。

## 8. P4：经用户批准后的冻结实图验收

### 8.1 进入条件与范围

P0-P3 必须作为一套完整替换完成并通过离线行为检查，不能运行新规划加旧编译/旧 QA 消费字段的混合版本。先提交修改与离线检查结果；真实规划调用、provider 探测、付费生图、冻结全流程测试均须用户另行批准。

首轮建议使用本次白色床架同一个 child，保持源数据快照与产品事实一致，生成任务清单中全部图片，不仅 main/scene/func/size 各一张。第二个不同类目 child 作为跨类目验证，是否加入及何时运行由批准范围决定。

开跑前列出预计图片数 N、所有角色、排除与未解决源图的原因。不能把 ready 子集当作全部图片；也不能为了凑数量使用错误颜色的变体参考。未解决的真实产品证据缺口须明确，不能隐藏。

尽可能固定 provider/model、输出规格与相同输入数据；做不到时逐图记录实际 provider 差异，不把其差异全归因于代码。新建测试目录和冻结指纹，旧结果只作对照，不复活旧运行逻辑。

### 8.2 成本、效率与停止边界

- 首轮先复用已有生成结果作旧版基线，不自动重跑旧代码；需要严格同 provider 的新旧配对时单独申请范围和预算。
- 批准前给出 N 次首次生成、现有重试上限、可得的费用估计及总等待边界；未知价格明确未知，不编造成本。
- 使用现有调度、provider 状态和有限重试，不添加新调度器、质量筛选候选或全量自动重生图。
- 冻结中不改代码。异常超出批准预算、持续同类事实失败或出现重复提交风险时停止新增付费请求，保留已完成结果；不要为了完成测试不停生成。
- 记录规划耗时、输入/输出规模、审核/修复次数、生图等待/执行/重试时间，区分设计整改效果和 provider 性能。

### 8.3 逐张检查与完整 child 检查

1. 参考独立性：检查是否仍把源图的特色抱枕、条纹毯、家具组合整套搬进“新方案”。常见中性色或木地板相同不自动判错，不设置相似率审美阈值。
2. 规划边界：只用产品及目标人群/市场解释设计，不把源图已有房间当用户需求；没有必要纯图时如实标注残余影响风险。
3. Child 统一性：床品主要颜色和材质、背景关系、字体和图形语言一致；自然明暗变化不算换色。
4. GPT 设计贡献：各图围绕不同目标形成合适构图与信息组织，不再全部只是同一模板换标题；也不以刻意求异破坏整套统一性。
5. 产品保真：逐图对照床框、板条、支撑、抽屉、滑轮和局部图；不允许主画面错误但靠正确小图“通过”。
6. 功能/size：具体功能没有退化成空泛卖点；确认文字、美国单位、测量对象和端点正确；文字、箭头、徽标按同一角色体系执行。
7. 展示质量：明亮且保留白色产品边界，无被误带入的厚重标签底衬、旧数字描边、无意人物/倒影；普通无品牌道具文字不一律消灭。
8. 流程：生成范围与清单对应；已有 QA 如实报告 pass/fail/inconclusive；继续到现有模板生成，不把 draft 文件等同于可发布通过。

以上设计项是本次人工验收标准，不新增生产自动 QA。实图失败先归因到参考、规划、编译或执行，再最小修改责任处，不能直接把失败现象逐项追加为 prompt 禁止句。

## 9. 实施顺序、交付与回退

执行顺序固定为：P0 参考输入 -> P1 规划职责与字段 -> P2 单一编译 -> P3 现有验收和旧行为清理 -> 用户批准 -> P4 冻结实测。

P0-P3 是开发和验证顺序，不是生产增加的阶段。它们完成前不投产半套接口；生产代码只保留一个实现，不设置新旧模式切换。需要回退时以完整一致版本回退，经用户确认后执行，不保留运行时兼容分支。

实施前保存当前工作区差异和证据指纹，尊重已有未提交修改；不得用 reset/checkout 覆盖用户工作。变更版本更新后旧派生产物通过现有 currentness 自然失效，只重建受影响范围。

代码体量应净收敛，优先删除上述职责和字段，不为了保持旧接口增加包装层。现有超过 2,000 行文件不增长，新生产模块低于 800 行、新测试模块低于 600 行；本方案原则上不需要新增生产模块。

完成报告必须分别给出：

- 生产文件增删改清单、近似增删行数、物理删除的旧路径和测试。
- 精确测试命令、case 数、时间、残余未验证项。
- 实际规划输入与最终 prompt 对照：删除了什么决策入口，保留了什么事实保护，不仅报告字符数下降。
- P4 未获批准前，只能声明代码和离线行为完成；不得声明配色、设计或产品保真已经改善。
- P4 后提供逐 child 拼图、源图对照、各图判断及真实流程结果，明确失败原因而不是以“模型接受请求”代替质量验收。

最终成功标准：用更少且互不冲突的设计指令，让 Gemini 制定正确的整套方向、GPT 完成有设计感的单图，同时不牺牲产品保真、child 统一性和已有生产可恢复能力。
