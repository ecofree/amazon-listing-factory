## 4. 用途错配会继续影响成品验收

[candidate_view_targets](D:/Amazon_pics/amazon_listing_factory/core/visual_semantics.py:695) 把所有非 verification 视图送入现有候选观察的必检目标。因此 integrated 整床图会继续成为局部 func 的额外整床比较对象。

本次证明的是错误要求能够继续传播的风险，没有新生成图，不能声称它已经导致本轮某张成品重绘或 QA 误判。

## 8. 精准后续处理顺序

1. **先纠正参考证据。** 在现有观察及其纠错循环内处理不可用裁切；保留其他有效观察，不整组清空。对明确异常附件走已有局部恢复，或让规划从该 child 的现有有效视图选择编辑依据。不能静默猜坐标、回退整张源海报或让局部底图冒充整床。技术可用性检查须结合实际像素与证据内容，不能给所有类目写死床架长宽比/最小面积。
2. **替换现有用途定义和示例。** 明确 verification 只核对身份/外观/结构事实，display 是实际可编辑显示依据，integrated 只用于要进入目标视图的具体产品特征。真正结构整合仍需核验，但普通换房间、床品和构图不能再被归为结构转移。不增加一段禁止句，更不按角色名称批量强改用途。
3. **统一执行与现有验收的范围。** 使用同一份用途声明；局部展示只比较对应产品部分，整合只比较指定特征，不把整床参考自动变成局部图必须完整展示的对象。保留同 child、真实结构、尺寸、卖点、实际附件的事实边界，不新增 QA 流程。
4. **最后做无损请求整理。** 在现有复核构建函数内复用相同事实/附件描述；保留所有 evidence IDs、来源、限定词、测量端点、区域、SHA 与各角色关联。不做自然语言模糊去重，不靠扩大超时和预算解决错误输入。
5. **先离线确认，再申请冻结。** 用实际异常区域、合理身份核对、真实局部结构整合替换对应测试空白，保持生产套件预算。离线检查 ready/blocked 往返和真实附件一致后，再经批准进行一个 child 全角色的新测试；冻结中不修改代码。不直接全量重跑四类目，更不能把反事实产物作为生产缓存。

本轮生产文件新增 0、删除 0、修改 0；生产代码增加/删除均为 0。新增离线审计脚本与本报告，更正前一份报告的过度结论；没有删除运行路径或修改测试。当前参考用途和裁切问题仍未修复，真实模型成功率、耗时及成品质量仍未实测。

## 9. 后续深查：为什么多次整改后仍然发生

### 9.1 排除本地截断或拼接改坏数字

独立读取首次观察的 `raw_response.txt`，逐条解析 SSE JSON 并连接非 thought 文本片段，与该次保存的 `response.txt` 对比：

- 157 个 SSE 事件，0 个 JSON 解析失败，156 个文本片段。
- 拼接结果与保存的文本完全一致；结束标记为 STOP。
- 原始上游内容已包含 source_02 的 left=0.9/right=0.903，也包含 source_04 的 bottom=551，以及 source_01 的测量端点 y=591。

因此，本例坐标错误不是本地 response 解析器丢小数点，也不是本地文件截断导致。错误至少已存在于项目收到的上游文本中；不能仅凭这些日志进一步区分模型生成错误与上游服务内部转换错误，更不能擅自补小数点。

相关解析函数：[native SSE 拼接](D:/Amazon_pics/amazon_listing_factory/core/vision_gemini_client.py:1146)。这次原始流没有触发该函数跳过错误 JSON 的分支。

### 9.2 已有纠错为何绕过真正危险的附件

实际第二次观察请求只重试 source_01、03、04、05、06、08；source_00、02、07 被列为 already_observed_read_only。其中 source_02 的物理请求计数始终为 1。

source_04 的 551 超出归一化范围，所以被拦截并重试；source_02 的两个横坐标都在 0 到 1 内且 left < right，错误特征框又恰好等于错误视图框，所以通过包含关系检查。它虽然不能提供整床像素，却进入“成功项不重做”的保留分支。

当前实现仍有同类逻辑：[几何检查](D:/Amazon_pics/amazon_listing_factory/core/image_reference_context.py:19)、[观察成功标记](D:/Amazon_pics/amazon_listing_factory/core/visual_semantics.py:416)、[成功项保留](D:/Amazon_pics/amazon_listing_factory/core/visual_semantics.py:98)、[后续请求选择](D:/Amazon_pics/amazon_listing_factory/core/visual_semantics.py:298)。

成功项复用本身应保留，否则又会浪费已完成工作。应纠正的是进入成功集合的依据，而不是删除缓存、增加整组重试或让所有图片重新观察。

### 9.3 循环自证与规划信息缺口

视图框、特征框、whole_view 标签、物理事实文字和置信度均来自同一观察回复。程序校验这些字段相互一致，不等于对照像素验证它们真实。两个错误框一致时，内部自洽反而掩盖了错误。

当前深色 source_02 的 reference_views 为空，但 physical_views 中仍保留该视图。后续规划允许从完整证据目录选择它，这项灵活性本身有用途，不应退回“只能用初始选中参考”的老限制。问题在于目录把它描述为完整床架，同时没有给规划提供这张实际裁片或其 5×965 尺寸，随后又允许它成为编辑底图。

SHA、来源路径、schema、input revision 保证可追踪和未被篡改，不保证参考内容可用。该错误不是多套实现同时运行才能产生；目前可见的这条主链路自身就足以复现。

现有测试 [窄框用例](D:/Amazon_pics/amazon_listing_factory/tests/test_visual_design_remediation.py:124) 只模拟“视图框很窄、内部特征框正常且越出视图”。它能证明包含关系检查有效，但不能证明实际产品未被截掉。

这说明测试并非在运行时造成裁切错误，也不应将其全部删除；问题是用例覆盖的错误模型比真实失败简单，却被用来支撑过大的完成结论。应修改现有对应测试，覆盖真实失败和合法细长产品/局部特写，不能只再加一个必然通过的理想输入。

## 10. 修复完成应证明什么

根因可概括为：**把同一模型返回字段的内部一致性，当作产品参考内容已经正确，并将这一判断传递给复用、规划和执行。** 上游模型可能犯错是触发条件，错误能穿过多层并被固化是项目自身的问题。

因此，第 8 节的顺序不变，但第一项不能退化为一个固定最小宽度阈值：

- 在现有观察与参考准备责任内，区分字段有效和实际参考可用；异常应携带实际原图、实际裁片和所声称产品范围进入已有局部纠错机会。不能用同一条未经核对的文字证明自己正确，也不新增独立验收阶段。
- 纠错必须改变负责该错误的观察证据及其版本，使依赖它的规划/附件重新建立；不能只改用途标记、prompt 或报错文本，让错误坐标仍被复用。
