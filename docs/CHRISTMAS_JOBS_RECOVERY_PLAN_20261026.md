# 四个圣诞树原作业：正确恢复方案

日期：2026-10-26。此文是本地核查后的方案，不代表已实施恢复。范围限于四个原作业及其原始 947 个角色，不创建新作业、不缩减原交付库存。

本次逐角色证据清单：`test_runs/trees_recovery_plan_20261026/readonly_inventory.json`。包含947个角色的候选路径、实际文件存在性、原生图回执、规划未决请求ID、现有工具额度，以及撤回“新增11条规划未知回执”的逐请求时间依据。它只是只读审计产物，不是新的生产控制器或替代账本。

## 1. 先纠正上次错误报告

上次回复所称“最新一次恢复新增 11 条规划未知回执”没有依据，现撤回。

逐条读取 B0CKDZ9SQ8 作业 planning_journal 的 request ID 和 created_at 后确认：现有 49 条未知规划请求全部创建于 10 月 20—23 日，最新一次 brief 运行期间没有创建规划请求。该轮 progress 记录只有环境记录、阶段开始、60 次规划文件写回及阶段结束，没有模型请求事件。之前将部分子体统计与整个作业统计相减，错误地报成了“新增”。

这次 brief 运行耗时 277.718 秒，其中 brief 阶段 131.328 秒；没有使任何缺图角色进入可生成状态。这是一次没有推进目标的整批恢复操作，不能描述成成功恢复，也不能描述成新增了 11 次远端失败。

## 3. 根因及责任边界

### 3.1 恢复操作范围错误

恢复前没有先确定“已有产物排除清单”和“真正缺图工作清单”，而是再次进入整批 classify/brief。现有 brief 入口按 RunScope 的全部子体执行；生成阶段的精确角色选择并不限制前面的规划阶段。这使恢复操作反复检查、写回大量已有产物的角色。

### 3.2 事实重核影响扩大到整套观察与规划

对比本轮事实重核前的备份与当前 family：44 个子体的 package_quantity 从此前缺乏明确原始依据的 1 变为未知，44 个子体的 source_fact_records 随之变化；差异集中在 package_quantity 及其 fact_resolutions。

纠正无依据的数量是必要的，不能为了恢复把它改回 1。问题是观察复用要求整个 child_facts_revision_id 一致，规划又比较完整来源依赖。局部事实变化因此可能使同一源图上的对象、功能及文案引用整体失效。当前报错已出现 tree_main/tree_01 和 feature/evidence ID 不一致。

不能把所有 ID 差异视为无害，也不能把所有旧观察判为必须重做。应检查当前角色真正使用了什么事实和哪部分源图证据。

### 3.3 恢复入口依赖当前 ready，无法充分恢复已变成 pending 的成功记录

core/visual_design_kit.py 的 _recovered_ready_role 在 brief.status 不是 ready 时直接返回；_recovered_ready_roles 同样跳过非 ready 项。后续又要求当前来源依赖、任务形成、候选请求匹配成立。

这条路径能复用仍然完整的已就绪合同，却不足以完成“当前已失效，但原候选、原请求和封存规划仍完整”的恢复。必须从原成功证据核验，而不能用当前 ready 作为恢复旧成功记录的先决条件。

### 3.4 已生成状态与当前验收状态混在恢复判断中

生成器先跳过 formation_status=blocked 的任务，随后才读取候选；当前汇总也将这些任务优先归为 planning_blocked。于是已有图片的角色缺乏清晰的“已生成、绑定待恢复”展示。

另外，current_candidate 的等价复用严格比较当前提示词和附件。无法等价复用不等于没有旧图，更不等于已经获得重生授权。必须同时保留“产物存在”与“当前可用”两个事实，不伪造后者，也不丢掉前者。

### 3.5 原额度与未知回执是真实限制，整批 resume 不能解决

123 个缺图且未找到生图回执的角色中，99 个落在未决规划请求的作用范围内，101 个所在子体的规划工具额度已耗尽；这两项重叠，不能相加。只有 1 个角色同时存在剩余额度且未被规划未决请求覆盖，但它缺少可用源证据，仍不能直接调用规划或生图。

这些数字说明：当前继续运行整批 brief 没有可执行依据。应恢复已收到的原结果、核对实际请求作用范围，之后只计算真实缺项的额度。不得把旧 unknown 改成失败、清空消费或借新修订重复提交。

## 4. 最小实施顺序

### 第一步：固定原范围，先保护已经完成的生产

- 保持四个原 job、114 个子体和 947 个角色库存；记录当前源码、配置与作业证据摘要。
- 以 job/child/role 为单位对照候选、原始返回、实际文件与回执。已有可核实图片的 792 个角色全部排出生图选择，893 个候选版本均保留。
- 在现有状态汇总中同时展示“已有图”“当前绑定有效”“缺图”“未决请求”，不新建生产账本或控制器。
- 生图前再次核对既有产物和原回执。候选损坏、绑定失效、当前合同变化都不构成重生授权。

### 第二步：恢复已有图的合同，只做有证据的本地重核

- 修改现有候选/规划恢复入口：从原 candidate manifest、原请求、原 prompt、源图 SHA、封存规划和接受记录查找恢复证据，不以当前 brief=ready 为入口条件。
- 核对原图像 SHA、子体、角色、原始附件、产品事实与可见文案。仅编号/表示变化且唯一对应可证实时，恢复现有绑定，保留旧、新证据关系；不改写原请求与原授权。
- 真实数量、结构、颜色、尺寸或对外文案发生矛盾的，只标明受影响角色的当前可用性待确认。保持原图，使用现有异常处理入口，不把整个子体退回重新规划。
- 不让旧图冒充按新版提示词生成，不单改版本号、指纹或状态为 pass，不恢复无依据的 package_quantity=1。

### 第三步：恢复缺图角色的必要依赖

- 只处理 123 个待核实缺图角色及其实际使用的源图、事实和规划字段；32 个未决生图角色保持回执恢复状态。
- 在现有来源读取器中按实际使用的事实核对观察复用。相同像素证据且依赖事实未变的继续使用；使用了已撤销数量依据的对象归属、文案或数量结论保持未决。
- 对 object/feature/evidence ID 变化，要求同子体、同源图 SHA、明确对象与功能关系且唯一对应，才允许修正引用。不能按名称相似、列表顺序或“一张图只有一棵树”的猜测批量替换。
- 让现有唯一规划器只接收确实无法本地解决的角色及相关字段，保留已完成兄弟角色和既有成套设计。该选择是原 RunScope 内的执行子集，不缩减交付库存，也不增加规划器或确认环节。

### 第四步：逐条恢复原规划回执并核清一次额度

- 优先解析已经落盘的完整响应，恢复尚未执行完的原决定；没有发送证据的预留项由原账本核实释放，已发送消费保留。
- 按原 request ID、子体、角色集合和操作核对未知请求的覆盖范围。旧未知回执继续留账；若另有完整、独立且有效的原接受证据，可恢复该角色，不把旧未知结果伪装成成功，也不重发同一未决工作。
- 对真实需要新规划的角色统计一次精确调用缺口，先用现有合法额度。额度不足如实列出，不重置、不借新 job、不反复追加，不再以全部阻塞数估算费用。

### 第五步：精确补图

- 沿用现有 --generation-tasks 的精确角色选择：只提交缺图、依赖恢复、合同通过、原请求允许提交的任务。
- 继续使用 CXK/QCYC；完成一项即登记候选。恢复前后核对已有 893 张候选的文件 SHA 和路径，确认没有覆盖与重生。
- 一条未知回执或一个角色合同失败，只保留其实际依赖范围内的待处理项；其他合法任务可继续。不能用修改任务身份绕开未知请求。

## 5. 代码边界和验收

优先检查和修改已有的 core/candidate_state.py、core/visual_design_kit.py、core/final_source_intents.py，以及 core/production.py / core/image_generation.py 的范围选择与汇总。身份比较继续由现有 planning_identity / visual_semantics 负责，回执继续由现有 planning_journal / image_response 负责；只有真实样例证明这些模块有缺陷时才修改。无新增生产模块、控制器、QA模型或生产阶段的必要。

必需验收：

1. 当前 brief 为 pending，但原成功证据完整且事实不冲突的角色，能本地恢复；不调用规划/生图。
2. 有图但绑定未恢复的角色明确显示已有图，绝不进入本次补图选择。
3. 同源、唯一对象的纯 ID 更名可恢复；数量、结构或证据含义变化不能被该修复误放行。
4. 恢复一个缺图角色，不重写已完成兄弟角色、不改变原库存、不重复确认已接受区域。
5. 未决请求保留原 ID、原消费和状态；不能因合同版本变化自动重发。
6. 汇总能对平 947 个角色，不混用角色数、图片版本数、回执数和模型调用数。

实施时先做上述实际失败样例的定向离线验收，再按仓库要求对最终冻结源码运行一次生产套件（不超过100例、60秒）。真实画质、生成完成、QA/发布分别报告。本次只做本地读取并写入本方案，没有修改生产代码、作业记录或请求账本，没有运行测试或发出模型请求。

## 6. 完成边界

本次恢复首先要保证：792 个已有图角色不重复生成；可恢复合同依据原证据本地恢复；123 个待核实缺图角色中，恢复一项合法任务就补一项。

只要32个已提交但结果未明的生图请求仍无法恢复且不允许重发，就不能承诺947个角色全部补齐。应准确报告这32个角色，不把688个已有图但待恢复合同的角色混成“还要生成”，也不为了让状态变绿制造新的付费请求。
