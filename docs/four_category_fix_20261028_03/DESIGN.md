# 第三轮：角色规则的失效范围

基线：`8dfe3dd8cdb8538b4a7839d3ab50e0df76e23063b42a36ec319fc155b5387893`。仅代码和隔离测试；不应用原作业、不付费。

## 目标与边界

只收窄两个明确按角色声明的字段：`role_specific_rules`、`role_visual_direction`。

- 共享品牌、结构、来源、测量、纠正、权限、设计引用、主图策略等关键约束仍保留原严格检查。
- 不通过删事实、猜证据 ID、忽略观察变化获得复用。
- 本轮不处理全事实观察缓存、文字规格尺寸或独立产物跨请求语义采用。

## 单权威改动

1. 在既有 policy/identity owner 中提供 shared 和 role 投影，当前性、任务形成、原规划器请求使用相同投影。
2. 初始封存记录继续证明共享 art。角色执行必须额外验证它实际消费的原 origin 所冻结的本角色上下文；修改 row 的全局上下文不能把旧批准当新批准。
3. ImageTask 的策略与 design_context_id 只含本角色规则及全部共享约束。改变 func 规则时，未变 main/scene 的实际 prompt、任务身份与候选可用性不变。
4. 仅角色规则变化不重新购买整套初始规划。原规划器收到受影响角色的当前规则及只读共享 art，作一次正常的 accept/patch/blocked 决策；没有增加第二裁判。
5. 新决策不能隐式修改共享 art。若当前规则需要改变共享设计，显式停止，待单独的共享设计输入变更。
6. 停止/重试键保持现有哈希公式，以已封存初始共享规划为稳定 epoch，只替换当前角色的规则值。这样其它角色规则变化不会重开 no-progress 工作；不试探旧哈希、不改原 accepted/content_id、不重置额度。
7. 旧未知请求依旧阻止其作用域的新 POST。待执行旧提案若本角色规则已变，不能照旧执行；其它角色规则变化则不撤销无关的已绑定提案。

## 需要删除/替换

- 角色当前性与任务身份中的全角色政策比较。
- 仅因为另一个角色的规则变化而触发全套 initial replan 的判断。
- 工具请求中重复发送未选角色规则的路径。

不保留第二规则表、旧哈希兼容分支或旧 schema 转换器。

## 先写失败测试

实际 classify→plan→task→prompt 形成四角色合同后：

- 改 func 硬规则，只有 func 阻塞；main/scene/size 的指纹和原批准保持。
- func 的旧接受不能通过仅更新共享 row/context 被升级。
- 精确选择 func 后，禁止 initial replan，只允许原规划器处理 func；真实发送的上下文不包含其它角色规则。
- 返回 accept 后 func 采用新的封存 origin，原接受文件不变；未选 journal/声明及已消费额度不被重置。
- 品牌/共享结构变化仍阻塞全部相关角色；建议仍非追溯；未知/无进展保护保留。
- 默认测试仍 ≤100、≤60 秒。新回归并入现有用例。
