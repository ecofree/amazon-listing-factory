## 3. 方案确认正确、值得实施的部分

### 3.1 已识别声明不应因 scene/main 标签而被清空

`core/final_source_intents.py:492` 仍是：

```python
claims = _bound_claims(prepared) if role in {"func", "size", "review_required"} else []
```

这会使同一条已有商品声明因来源角色变成 scene/main 而退出事实目录。E2.2 指向的缺陷成立。

但下游 `_source_manifest()` 当前已经原样接收 claims（`core/visual_design_kit.py:979`），`cleaned_source_claims()` 也没有按 scene/main 一律过滤。因此不能笼统声称这两处现在都在删除事实，更不必把它们全部重写。

最小处理是取消仅因用途标签而清空合法声明的行为，并把目前只对 func 检查的声明结构/来源绑定验证覆盖到实际携带声明的行。身份冲突、错误变体和无证据内容继续按原边界处理。证据保留不代表授权 main/scene 新增营销文字。

### 3.2 标题与标签在 Prompt 中确实丢失职责

路径为：`display_copy_contract` → `authored_text_contract()` → 字符串列表 → `_render_text_block()`。

用冻结样本 #49 的完整 task 做对照：保持字符串顺序与内容不变，只把标题改为第一个普通标签，结果是：

- 完整 Prompt 完全相同；
- `_task_fingerprint()` 也完全相同。

这直接支持 E5.2。当前指纹反映的是编译结果，但编译遗漏了标题职责，因此无法感知这种业务变更。

最小处理是在现有文本块中从 `display_copy_contract` 投影标题/标签职责；字符串依然只列一次，无标题明确表达。无需另建文案合同，也不能让生图模型自行改写已绑定文字。补上这一投影后，由现有 Prompt 指纹自然区分实际改变的要求。

### 3.3 目标状态与来源观察需要明确区分

#59 的 `presentation.state` 要求双门全开；实际第二参考 `source_00` 的事实包含“右门开、左门闭”。`core/image_prompt_compiler.py:372-378` 将目标状态和所选参考的 physical_facts 一起发送，未明确逐项说明后者是来源的观察状态。

这是竞争信息，不能简单删除原事实或按 open/closed 关键词过滤。应让现有目标字段拥有输出状态的决定权，辅助图只补它被选中的商品证据。第一编辑底图不自动由共同定调图替换。

### 3.4 主图 QA 的政策来源应收口

`core/image_qa.py:214` 使用 `main_image_policy(plugin)`，生成 Prompt 则使用 task 内的 `category_image_policy`。

离线对照固定同一个白底任务及“背景非白”的像素观察，只切换插件政策，背景 gate 从 fail 变为 pass。这证明该函数存在第二个取值点。

需要准确限定结论：完整 `run_image_qa()` 先调用当前性校验（同文件第 49 行），旧计划也会与当前政策核对。因此本次函数对照不能证明生产入口已实际接受了混版任务。最小修复仍是让 gate 读取任务绑定政策，同时保留当前性检查；不要据此全面替换 strict reader。

## 4. 执行前必须修订的方案条款

### 4.1 “单张”不能与“干净、合格”混为一谈

`planning_reference_inputs()` 当前只筛选 appearance，没有排序后的唯一偏好、干净程度或可裁剪区域字段。`prepare_planning_references()` 只验证原路径和 SHA，没有实施裁剪。观察提示还允许在必要时增加第二外观视图，以及无更干净来源时接受带背景的可靠图。

因此方案 E3 不能仅通过 `[:1]` 完成，也不能推定现有工具能移除柜内用品、床品、反射或遮挡。

建议修改为：

1. 如果采纳单图要求，由现有联合观察确定唯一合格主体参考，沿现有映射绑定一次；初次规划、repair、附件 manifest、请求身份都消费同一选择。
2. 无可靠范围时不自动裁剪。本轮可以先不实现裁剪；不能为了凑出“干净图”裁掉商品。
3. 不得仅因没有绝对无道具图就新增整批门槛。若业务确实要求该 child 必须等待素材，应明确这是一项素材约束，且写出实际恢复入口。
4. 若需要支持补充真实商品图，先确认合法来源绑定能力。现有设计参考导入用于风格，不授予商品事实，不能拿它冒充商品证据导入。

方案已承认没有入口时要报能力缺口；但第 1、12、15 节仍将整套交付写成必能完成。这两处要统一，不能一边承认能力不足，一边承诺不存在的恢复路径。

另外，两款浴室柜原规划附件都已只有 `source_00`。七个 child 计划中，确有两个使用多张外观图，但柜体的结构错误发生在已单图定调的样本里。E3 能限制输入数量，不能单独解释或证明修复了柜体连接错误。

### 4.2 “原 brief 修订入口”能力被写得过满

当前可见入口包括：

- `run --brand-brief`：修改品牌方向，再运行 brief；
- `review-source-role`：来源角色复核/重观察；
- `_finish_image_briefs()`：修复 pending 角色，按明确 shared 路径修共同字段；
- `revise`：对候选 targeted_edit/full_redraw，保留基础合同并附加 reason。

本次搜索未发现一个可直接将任意已 ready 角色的标题 A 改 B、容量目标改安装目标的通用用户入口。自动修 pending brief 不等于人工定点修改任何 ready brief；改品牌方向也不等于只修改这一张图。

E1/E5 应改成能力对应表：哪些要求变化由现有输入修改后重建完成，哪些属于候选执行纠错，哪些尚无精确入口。不能手改落盘 JSON 或靠 reason 覆盖旧 exact。若确需补接口，应明确为现有 brief 的窄范围能力补充，不能把它写成已经存在，也不能悄悄扩成本轮必需的大改。

### 4.3 跨版本未知回执不能只写“保留原机制”

`response_binding()` 包含 task_fingerprint、Prompt、附件及候选修订；`recover_response()` 按这个 binding 查目录。生成端的 `task_record_current()` 只返回同一 input_revision 的状态。

临时目录中的真实恢复函数对照结果：旧绑定存在 submitted 未知回执时，旧任务被拦截；仅改变 task_fingerprint 后，恢复函数返回 `{}`，没有识别旧绑定中的未知回执。未调用供应商。

这证明“技术版本变化也不绕过未知请求”并非现有单绑定机制自动保证。不能据此声称已经观察到新的重复扣费，但 T23 必须作为本方案的明确恢复反例，不能用同版本恢复测试替代。

最小操作边界：本次范围内的旧未知请求应先在原身份下完成明确处置，再切换相关任务版本。若实现自动保护，应扩展原回执/任务路径对同逻辑任务的关联，不能增加全库扫描服务或新恢复控制器，更不能关联错误结果为新任务候选。

### 4.4 “模型原始返回与最终图对照”当前不是自动可用

`finalize_candidate()` 读取返回字节后执行 `_finalize_candidate_bytes()`，提交最终候选；随后 `finish_response(..., 'finalized')` 删除 `.bin/.http/.partial`。

所以方案 T26 及真图记录要求里的“模型原始返回”，必须说明是可检查的原始图像字节，还是只有 hash/请求元数据。现有 finalized 回执不能保证原始图片仍可打开，与放大后的最终图逐像素比较。

建议只为本次定点验证明确取证方式，必要时在现有最终化责任内保留对应样本的原始返回；不要改成永久保存全部远端响应的项目。已删除的历史原始字节也不能从最终图还原后冒充。
