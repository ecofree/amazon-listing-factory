## 一、总体决策

### 1. 不重建系统，收敛现有链路

继续使用：

`factory → production.run_job → fetch → copy → download → classify → brief → generate → qa → publish → template → delivery_package`

- `production.run_job` 保持唯一阶段控制器。
- `ProductFamily/effective_product_facts` 保持商品事实权威。
- Gemini只负责既有观察/视觉规划职责；不能凭规划输出增加商品事实。
- `image_tasks + image_prompt_compiler` 保持唯一编辑合同与提示词编译路径。
- 图片模型执行校验后的参考图编辑合同；size/func不变成新产品渲染或本地图文拼接。
- `image_qa → qa_evidence → release_manifest` 保持唯一图片硬事实审核/放行链，不增加审美分、第二审核器或自动重画。
- `template_field_plan` 保持唯一模板字段判断权威；前置检查和最终填写共用它。
- `batch_ledger` 仅拥有订单派工、准入、预算、授权消费；不复制各阶段成功判断。
- 现有各类receipt分别拥有本类外部请求结果；账本引用receipt，不再维护一份可独立改写的“远端成功状态”。

### 2. 实施顺序与验收顺序分开

最快、风险最低的施工顺序：

```text
阶段1：测试预算恢复 → 删除危险旧路由 → 请求止损/费用准入/有效配置
                                      ↓
阶段2：事实/变体/文案/实际模板静态检查 → 完整编辑合同与请求预检
                                      ↓
                  阶段3控制机制、阶段4交付/UI可并行做离线实现
                                      ↓
              另行授权阶段2真实图片验证 → 阶段4真实整包交付
                                      ↓
                       阶段3真实异常接续 → 阶段5长跑验收
```

阶段3、4的离线实现可以在阶段2真实供应商受阻时继续，**不能据此把阶段2标为验收通过**。任何新真实付费生产必须先通过阶段1及阶段2的静态可交付性检查。

### 3. 三种完成状态必须分开

每个整改工作项使用：

1. **实现完成**：新路径生效，旧路径和对应退役测试已物理删除。
2. **离线验收完成**：指定环境、隔离网络、真实小样本/故障注入通过；套件预算合格。
3. **真实验收完成**：有绑定版本的真实回执、产物和检查记录。

缺少第3项不得写“质量已修复”“无人值守已达标”。HTTP200、收到规划、文件存在都不替代真实完成门。

## 二、必须守住的生产不变量

| 编号 | 不变量 | 由谁强制 |
|---|---|---|
| I1 | 同一订单/逻辑操作的未决POST不能因超时、重启、换批次、换模型或改配置再次发送 | 对应receipt owner＋现有账本准入唯一约束 |
| I2 | 完整收到的结果先持久化，解析/写盘/超分失败只做本地恢复 | transport/receipt/candidate owner |
| I3 | 业务事实与软件默认分开；未知不变成1、200、false或Not Applicable | ProductFamily、job输入合同、template field plan |
| I4 | 父子变体维度来自来源证据；同parent的有效变体tuple完整且唯一 | 商品提取与最终模板关系校验，共用同一关系合同 |
| I5 | 文案、图中文字、图片数量/结构、模板均绑定同子体事实版本 | 既有事实、文案、图合同和模板owner |
| I6 | 任一role失败不要求无关role重新付费；最终家族仍要求完整冻结范围 | role状态与production/release |
| I7 | 未知结果、请求预算和货币预算不能由配置/版本切换自动清零 | 原订单账本＋对应journal |
| I8 | 人工操作有准确对象、证据、授权范围和幂等ID；批准不修改原事实 | 原有处置/人审authority |
| I9 | 已交付归档保持可校验；是否仍可上架须另查当前事实、批准与URL时效 | delivery_package和publish |
| I10 | 真实完成分开报告：规划、生成、QA、发布、模板、包交付 | 各owner输出的只读投影 |

**不承诺本地系统能保证供应商内部exactly-once计费。** 可以保证的是：受控本地发送边界幂等、未知不擅自重发、全部消费可追溯；供应商内部行为和实扣必须对账。

## 三、阶段1：冻结与止损

**对应F01、F09、F10、F11、F13、F16、F19，并处理F15中明确退役部分。**

原计划阶段1曾本地通过，但本次审计发现新阻断，必须重新满足退出门。

### 1.0 先恢复测试预算，再开始功能修改

当前唯一审计套件100项、87项ok后60秒截止，不能继续堆功能/测试。

**实施：**
- 保留审计日志，先做定向计时：识别重复SAM夹具、重复生产链构造、重复模板解析、退役协议测试。
- 删除退役行为测试；同一事实边界只留一处行为测试。不能删关键风险断言、藏成skip，或用一个超大test/subTest包装来假装减少用例。
- 优先复用不可变fixture数据，不能共享可变job状态。
- 不复制历史jobs、不带凭据；继续阻断远端调用。
- 默认套件目标**≤92项、≤50秒**，保留8项/10秒余量；硬门仍是**≤100项、≤60秒**，不得延长。

**责任文件：**`scripts/run_production_tests.py`、当前18个生产测试模块及其被引用fixture。

**退出：**瘦身交付包末尾一次默认套件完整通过。失败则继续瘦身/修正，不推进新功能。这个优化不能被认定为真实质量验收。

### 1.1 删除不再支持的图片协议

**保留：**当前启用的 `openai_images_edit` 链、完整prompt/reference审计、HTTP envelope/native bytes保存、子进程硬截止。

**删除：**
- `image_provider_transport.py` 的旧async/chat-image/highway发送、异步模糊POST重试、专属poll/payload辅助函数。
- registry中对应退役api_type记录（不是继续enabled=false）、解析/验证分支、专用env键和主动说明。
- 只为这些旧行为存在的provider-smoke/回归场景。

**不删除：**当前Gemini text/vision协议、当前同步图片响应中的URL解析、Apify/OCR已知taskId的GET恢复。按实际引用做删除，不能把通用安全下载函数一并删掉。

**验收：**退役api_type入口拒绝；静态搜索无活跃引用；所有图片POST均经过当前receipt owner；没有“备用旧接口”可重新打开。

### 1.2 修来源观察的未知重发，并修正未提交的判定边界

**责任文件：**`visual_semantics.py`、`service_response.py`、`vision_gemini_client.py`、`final_source_intents.py`。

**方案：**
1. 来源观察接入现有 `service_response` 存储，不新增观察请求控制器。
2. 一个逻辑owner由订单、child、来源集合/用途确定；请求内容revision另含原图SHA、事实revision、correction、模型/协议参数。改变revision不能逃过同owner未决请求。
3. 完整响应先以原始字节原子保存，再校验JSON、观察行、视觉身份和measurement；本地校验失败不能覆盖原结果。
4. `attempts_used`不再是“允许下一次POST”的唯一依据；只在确有完整已收无效响应、允许的有界合同修复或确证未提交时，才能使用剩余预算。
5. 源观察、initial plan、tool plan分别保留现有owner；不强行把三类journal合并成一个大控制器。

**进一步核对现有存储后的必要防护：**不能原样把 `known_unsent()` 的异常类型判断扩散到新调用方。`perform_request()` 中，远端已返回后写盘也会抛 `PermissionError`；这不证明未发送。DNS/权限/连接错误只有在**具体传输阶段证明确实未发**时才能分类为not_sent。

#### 统一的结果语义（实际字段在各既有owner中实现）

| 情况 | 自动动作 | 是否允许新POST | 费用含义 |
|---|---|---|---|
| 本地预检/准入拒绝，确定没到发送边界 | 修输入/等待资源 | 条件满足且预算有效时允许 | 不是已发送；保留诊断 |
| 已提交，无完整响应／只收头／进程中断 | 恢复原receipt；有已知且受支持taskId则GET | **不允许** | 实际消费未知，保留预占 |
| 已收到明确拒绝 | 按代码/回执分类；配置/账户错误停 | 仅匹配预先许可的安全重试策略，不因402/5xx盲发 | 拒绝结果与是否收费分开 |
| 完整响应但JSON/合同无效 | 保存；本地解析或有界原owner修复 | 仅原预算包含已知结果修复时允许 | 原调用已发生，不能退款式重置 |
| 完整结果但落盘/下载/解码/超分失败 | 本地恢复／安全GET | 不允许重新购买 | 已购结果，不是模型失败 |
| 候选QA不确定/失败 | 既有异常队列 | 不允许自动重画 | 人工批准和重发授权不是一回事 |

`402`不自动等于没钱；`503`/断连不自动等于未执行；HTTP200头不等于received完整结果。

**删除范围：**未知异常后观察for循环继续发送、仅按次数余额恢复、复用`:1/:2`作为新的物理尝试身份、异常类别直接推断not_sent的宽泛路径及旧断言。

**验收：**在提交后/收头后/部分body/完整body后写盘失败/结算失败各点故障注入，重启后本地mock发送总数仍为1；完整保存body可零POST恢复；明确未提交可有界重试。包含原审计“首轮2次、恢复4次”的反例。

### 1.3 扩展现有账本为唯一生产订单/预算作用域

**不加第二个全局账本，也不让每个batch持有独立可消费额度副本。**

**选定架构：**把现有 `BatchLedger` 演进为单个配置明确的生产工作区账本；batch变为该账本中的分组。派工、订单唯一性、SKU占用、预算预占均在同一SQLite事务域。当前 `--state` 不再可任意创建新的可付费生产域绕过同订单计数。

- 单机先使用本地SQLite＋现有进程锁，不引入Redis、消息总线或网络共享SQLite。
- 现有独立 `batch.sqlite` 在切换前维持暂停，切换后只作只读证据；不进行目录扫描/全量迁移。
- 独立run、revise、provider-smoke、auto分类等凡可能产生外部收费的入口，都必须绑定显式授权的订单或诊断预算；不能用production=false绕过。
- offline preview/本地检查不要求收费准入，也绝不能暗含探测请求。

#### 身份和数据约束

| 数据 | 目标含义／约束 |
|---|---|
| `order_id` / `idempotency_key` | 业务订单稳定身份；同seller/site/源商品/上架意图重复登记返回原订单，不含时间、batch、配置hash或模型名 |
| `execution_revision` | 当前源码、有效行为配置、事实、模板/合同版本；改变它不创建新订单或新额度 |
| `batch_id` | 仅分组，不重新拥有一份该订单的可用预算 |
| `logical_operation_id` | stage/child/role/操作语义；unknown锁定与之相交的owner，即使prompt改变 |
| `attempt_id` | 每次物理提交边界的唯一ID；账本admission与owner receipt使用同一个ID，禁止各自生成无关联UUID |
| `receipt_ref` | 指向唯一owner的回执及hash；ledger不重复宣布远端成功 |
| `authorization_id` | 绑定订单、owner/具体旧request、用途、最多次数、金额/时间边界；消费有唯一约束 |
| SKU绑定 | seller＋marketplace＋SKU绑定同一listing身份；另一个订单冲突先阻塞，不创建第二份可售listing |

来源parent/child在fetch之前未知时，不能保证“两个不同seed其实同家族”完全不产生发现成本。入口优先接受明确family key；发现阶段确认同family后禁止双生产并提示合并归属；已经发生的两次发现费用不能抹掉。不能宣传超出证据的全域exactly-once。

#### 文件回执与SQLite的崩溃协议

不假设文件系统和SQLite可做一个分布式原子事务：

1. owner在锁内持久化准备记录和attempt ID，核查未决owner。
2. 账本原子预占预算/校验lease与授权；之后只允许一次claim发送许可。
3. durable发送标记/许可消费必须在HTTP之前；任何已claim但无法证明确切结果的中断都保守按unknown处理。
4. HTTP完整响应原子写入原receipt；其后本地结算失败重启只核对同attempt，不申请新钱。
5. 两边不一致则冻结、对账；**“receipt文件缺失”本身不能证明没发送**。
6. 原准入记录、已发送计数、旧授权消费均不删除；只有有证据的未发送准备可释放未发生的预占，unknown绝不自动退款。

#### 预算

- 六个当前入口全部纳入：fetch、copy、OCR、planning（含观察）、image、QA。
- 订单上限＋本工作区内共享供应商账户/批次总上限在同一事务检查；模型别名不能倍增同物理账户并发额度。账本不能约束其他项目或人工在同账户的消费；存在外部共用时须明确成本归属与剩余额度不确定性，不宣称供应商账户全局硬限额，也不擅自修改账户设置。
- 金额采用明确币种和整数最小单位；单次upper bound需绑定服务/模型/输入输出上限及可靠依据。缺可靠价格时不得声明货币受控。
- 可以显式允许小额**只限次数的试验**，但须单独承认金额未知；不能据此准入长期无人值守。
- 存储PUT/GET/流量费用另列可核实上限或独立获准的存储预算，不把六类模型准入数冒充全系统成本。
- unknown预占保留；“确认未计费/收费”要有供应商结算证据。实际金额与调用结果为两个独立维度。
- 风险接受只允许绑定的替代尝试，不增加planning allowance或货币cap；补额度是另一个显式操作。
- 删除 `unknown_result_policy.automatic_authorization` 及 `authorization_source=policy` 的全局自动风险接受路径；保留替代次数硬上限，但每次替代必须有绑定具体旧request的有效授权。过去operator授权也要核对是否已消费、是否过期和scope，不能仅凭旧状态长期有效。

**责任文件：**`batch_ledger.py`、`production_batch.py`、`scripts/factory.py`及六类现有提交点。

**删除范围：**生产无ledger直接return、按config hash复制新订单、跨batch新目录变成新预算、随机admission与receipt脱节、全局自动授权未知重发及对应测试。旧账本文件保留为证据，旧可执行读取/派工路径删除。

**验收：**并发同key只创建/提交一次；换batch/配置不重置订单；相同授权重复回调无新增提交；金额未知准确显示；六入口预算拒绝时远端mock调用0。

### 1.4 统一有效配置、截止、请求体预算

**责任文件：**`production.py`、`io.py`、`template_runtime.py`、`vision_gemini_client.py`、`planning_feedback.py`、`visual_semantics.py`、`image_qa.py`及入口。

**配置决策：**由现有生产入口解析一次，冻结运行上下文。建议优先级为：显式本次参数 ＞ 已选job/profile配置 ＞ 项目配置 ＞明确允许的环境注入 ＞有文档的代码默认。敏感值可由环境注入，但不把全进程任意环境混入业务参数。batch与standalone使用同一规则。

- NO_PROXY只影响项目worker子进程；不得修改系统/全局网络设置。
- 记录实际egress策略、超时、并发、模型/协议语义指纹；密钥/上传PAR不落日志或包。
- 认证凭据版本、网络行为版本、会改变产物语义的模型/合同版本分开；轮换key不应单独使已归档包不可下载。
- 观察/初始规划/tool/QA的单请求deadline都从上下文取得；移除调用点120秒覆盖。不是把全项目统一改成更大的timeout。
- 单次有效截止为：`min(scope单请求上限, 当前作业剩余时间减收尾余量)`。队列等待、上传、收头、错误体、正文、解析/保存按其责任共享明确剩余截止。
- 预计剩余时间不足完成一次请求及落盘时，不启动新POST；保存待办，按阶段3规则接续，不靠超时再来一次。
- 保留HTTPX绝对截止及生图/本地收尾的进程硬截止。

**实际body预算：**
- 发送前编码一次，按**真正要发送的bytes**校验；同一bytes传给transport，不能校验估计体后又重编码另一份。
- 校验参考图数量/顺序、单图尺寸/字节、总body bytes、输出token/pixel上限；记录全部绑定。4MiB等标明本地保守政策，不宣称供应商正式限制。
- tool只按完整role拆；保留共享子体设计、原图、区域证据、文字和事实约束。
- 来源联合观察/initial若完整必要证据超预算，明确异常；不新增单图fallback、不降采样到丢失文字、不摘要替代原事实。
- 只允许已验证的现有图像编码变换；编码失败或超限不能“返回原大图继续发”。

## 四、阶段2：自动验收可行性

### 2.1 把来源事实、售卖数量与变体关系修正确

**责任文件：**`products/generic_extractors.py`、`core/source_fetch/apify.py`、`core/product_family.py`、`core/image_task_inputs.py`、`schemas/product_family.schema.json`、相关品类manifest。

### 2.2 文案和关键词保持事实约束，不建第二审核器

**责任文件：**`copy_writer.py`、`copy_polish.py`、`product_family.py`、`backend_keywords.py`、`template_field_values.py`。

**实施：**

- 绑定包含输出字段/文本区段、fact_id、owner、property、value、unit、scope；程序验证证据归属与数值/范围一致。

### 2.3 同一模板字段计划用于三次就绪检查

**不是增加另一模板控制器或第二QA。** 在 `template_field_plan/template_engine` 现有权威中给每个字段显式数据依赖，让不同阶段调用同一校验。

## 五、阶段3：持续生产控制

**对应F08、F11、F12、F15、F17、F20。**

### 3.1 常驻派工，单job阶段执行权不变

**责任文件：**`production_batch.py`、`batch_ledger.py`、`process_lock.py`、`status.py`。

- `run_batch`的服务模式持续等待队列和决定，不因暂时无ready任务退出；一次性drain为显式模式，不暗示会持续接续。
- 由操作系统进程管理器托管一个现有CLI进程；部署时才配置自动启动/重启，此方案不修改Windows服务/任务计划。
- `serve`只管UI，不再让运维误以为打开页面等于worker运行；页面必须显示dispatcher heartbeat、worker lease和pause原因。
- 保留SQLite事务领取、job锁、PID＋创建时间校验；旧lease不能提交候选状态或批准新POST。
- pause停止新准入，允许已收结果本地收尾；强制终止会留下unknown，不能显示“已取消且零消费”。cancel与pause明确区分。
- 在共享总上限内分配image/provider/GPU槽；当前参考并发先1，后续扩量须阶段5证据，不把软件最大8当供应商能力。

### 3.2 事件驱动接续，不扫描所有trace猜变化

- 由现有source review、receipt resolve、human review、business input更新入口在决定成功后产生明确revision事件。
- 事件只用于唤醒，不拥有业务批准权；worker仍从原authority核对决定。
- 同一`order + decision revision`只接续一次。
- 先持久化authority决定，后登记唤醒；若两者间崩溃，dispatcher对**已登记job的有限authority文件**做revision补核并补登记，不能永久漏唤醒，也不做全目录trace扫描。
- 来源事实本地重验、模板业务资料修正也有事件；仅修改一份诊断日志不触发付费生产。
- UI不能直接编辑job_state/stage success；所有操作走原owner并校验当前hash，过期页面409类拒绝。

### 3.3 将“运行次数、重试次数、授权次数”分开

在现有账本中清楚定义：
- `lease_sequence`：每次派工的序号，不是可消费额度。
- `automatic_retry_used`：明确可自动恢复的失败次数，受预设cap。
- `authorization_used`：具体人工风险授权/增加预算的消费，单独唯一记录。
- 订单累积时间、调用数和金额上限：对全部lease有效，人工修改决定不能清零。

worker在剩余时间不足时保存待办并正常yield，可在总时间/预算内接续；不是一次新的失败重试。不能把“换lease”当获得新7200秒/新模型额度的办法。

### 3.4 部分失败独立性与统一健康状态

- `production.run_job`继续阶段顺序；各owner只处理就绪/未决可恢复任务；失败child/role不抹掉成功子任务。
- batch不以“任何任务blocked”一刀切认为其余无可做工作；由原阶段状态计算有无可运行工作，账本只派工，不复制角色判定。
- 最终完整包仍全家族原子门；单role失败不能靠删role放行。
- provider健康判定收敛到现有 `model_call_health`：传输/账户/模型配置/内容拒绝分开；同物理账户或网关别名共享相应资源上限。
- 删除success/quality ledger作为第二路由决策依据及人工审美分；保留必需的真实请求审计。
- 半开探测只能占用已获授权的正常待执行任务，不能自动新增付费“健康检查”；未知原任务不因换健康provider重发。

### 3.5 版本切换与原家族的显式接续

- worker启动绑定固定源码/有效配置。源码在运行中变化时暂停新准入，不混用两个执行版本。
- 订单不变；通过明确的execution revision切换记录新版本、变化原因、需要失效的artifact集合；不把整个repo每次变化等同全部产物重跑。
- 产物复用由原owner按实际语义依赖验证；认证key轮换、无关品类或测试文件变化不自动重生成。
- 某个schema真的退役就删除旧执行reader和旧测试；不能保留隐形兼容fallback。**只有明确授权的当前J**可以做一次受控本地重验/切换，输入、输出和原hash留档；不是通用历史迁移器。
- 当前15账本53条记录只读核对；若要迁入新订单工作区，只对明确列出的scope建立不可变历史费用/unknown约束引用。新账本必须先继承这些约束才能准入；任何费用归属不清先冻结，不推断金额0。

### 阶段3退出门

- dispatcher退出/重启、worker崩溃、重复回调、来源修正、QA人工决定均能接续一次。
- 至少一个role未知时，无关role/family能继续；未知role无新POST。
- 同一成功candidate/已收响应不会再次购买。
- 订单总预算对所有lease/revision有效；原记录数量与unknown不减少。
- 本地机制可不付费验收；真实人工异常到真实交付的接续必须后续有证据，不能用100个synthetic completion替代。

## 六、阶段4：整包提交与界面

### 4.1 发布与URL时效

**责任文件：**`publish.py`、`delivery_package.py`、`batch_console.py`。

**验收：**远端内容错/hash错、返回HTML、部分body、到期/撤销、PUT后落账失败都不能假完成；恢复仅重传缺失对象；本地mock不当真实URL证据。

### 4.2 正式模板

- 使用阶段2同一field plan，最终必须没有missing_required、invalid_numeric/enum、unknown conditional、awaiting_upstream。

### 4.3 自足且不可变的交付包

复用 `delivery_package`，不新建批准层。建议交付内容：

```text

```

- 不复制整个job历史，不把上游所有trace塞进包；每条实际放行/事实主张可找到必要证据即可。
- 稳定外部证据库可替代部分源图，但必须有明确长期可读引用和保留合同；不使用本机临时绝对路径。
- 包内manifest排除凭据、上传PAR、无关私有账户信息。
- 暂存→校验ZIP清单/成员SHA→原子commit→current指针。任何步骤失败无delivered。
- 定义两种验证：
  - **archive integrity**：这份历史ZIP仍完整，允许下载审计，不依赖原源码/凭据文件存在。
  - **current delivery eligibility**：当前事实/批准/模板合同/URL时效仍有效，才显示“当前可上架”。
- 真正依赖变化使current失效并生成新revision；无关代码变更/凭据轮换不毁掉历史包。
- `delivered_at`是过去实际交付事件，不因过期抹去；另显示expired/revoked/superseded等当前可用状态，避免“交付过”和“现在可用”混成一个布尔值。

**每条异常必须显示：**
`stage、reason_code、当前状态、相关order/child/role、原始receipt/证据链接、影响范围、已消费/预占/实际费用未知、合法下一步、何时可自动继续`。

**动作分别绑定原authority：**
- 查看/恢复已保存响应；不默认重试未知。
- 具体未知请求风险接受：默认不选中，必须显式次数/期限/金额，和补预算分开。

- 批次pause/resume/cancel、查看heartbeat、包下载。

## 七、阶段5：持续生产验收

**不是新增功能阶段，是以真实结果决定生产范围。**

### 5.1 验收阶梯

| 顺序 | 样本与操作 | 通过条件 | 失败去向 |
|---|---|---|---|
| 5.1 单家族整包 | 优先当前精确J；保持2子体17槽；必须先解决真实变体合法性 | 六里程碑分别成立，事实/模板/URL/包内容逐项正确，实际可下载 | 按原因回阶段1/2/4；不换小范围掩盖失败 |
| 5.2 小规模多家族 | 建议至少5个完整家族、覆盖至少2个拟准入品类；新增样本路径/预算另申请 | 同单家族门＋批次部分失败隔离、重复提交无重复消费；真实正常任务无维护命令 | 阻断该品类/服务准入；不宣称4品类都通过 |
| 5.3 24h混合运行 | 固定最大订单数、次数、金额、并发；正常/异常混合，期间有实质处理和恢复 | 无假完成/无授权重发/无事实错误误放；全部订单和消费可对账；异常可见且有处理入口 | 暂停新准入，保留receipt，不自动加预算跑满24h |

“五家族”是建议的初步工程验收量，不是证明零缺陷的统计样本。准入只覆盖真实测试的品类、来源类型、输入规模、模板版本、服务配置；其余保留未验证。

### 5.2 故障覆盖

至少覆盖：
1. 重复提交、两个dispatcher并发领取、重复人工回调。
2. 预算准入前中断、提交后丢回复、完整响应后本地落账失败。
3. worker/dispatcher崩溃或重启，过期lease fencing。
4. 某child/role来源不足或合同错误，无关任务继续。
5. QA未知/不确定/明确事实失败，不能自动批准或重画。
6. 对象存储上传成功后本地记录失败；URL失效/内容不符。
7. 模板类型/必填/变体冲突；ZIP中断/成员变更。
8. 金额/次数/时间额度耗尽、服务熔断、人工处置后接续。

**收费风险边界：**丢回复/部分body等危险情形优先用离线注入或已保存真实回执证明，不能为了测试故意新发付费请求再杀连接。真实故障注入若可能造成未知费用须单独授权；记录每项是离线还是live，不互相冒充。

### 5.3 生产准入阈值

- 已实际测试的正常订单：创建后人工维护命令/改JSON/常规approve次数=0。
- 全部已发送请求：订单/attempt/receipt可追溯率100%；unknown无授权重发=0；成功结果无意义回购=0。
- 验收样本：硬事实错误自动放行=0；缺证据/不确定全部明确异常。没有真实样本时误放/误拦率写不可计算。
- 正常与异常定义在试跑前按事实/输入合同冻结；不能把所有未自动完成任务事后改名成异常来满足“正常100%”。
- 每个异常有cause/evidence/impact/action，覆盖率100%；建议异常发现/告警本地可见≤60秒、处置生效后可调度≤2个轮询周期（资源不可用时准确显示等待）。阈值是工程目标，不是保证供应商响应速度。
- 24h有真实处理，不以24h空队列待机作为成功；尚未到终态的请求继续unknown/waiting，不截止即报完成。
- 金额未对账或无可靠上限时，不批准长时间无人值守；只可另行有界试验。
- 默认套件≤100/≤60秒；真实图片/包验收独立于套件。

## 十二、实施边界、回退和需要确认的业务输入

### 12.1 工作区与回退

- 开工前对实际待改文件做独立备份和hash，记录既有脏改归属；不reset整个分支，不覆盖其他工作。
- 一次实施包只替换一个责任范围，删除旧path与测试；新增生产模块<800行、新测试<600行；大文件优先净删，不因方案借机全面重写。
- 出现风险先暂停新准入，不清空队列/unknown/费用。
- 需要回退代码时只恢复本包自己的文件变化并核对基线；数据库/receipt不回滚到旧消费计数。
- 如果新schema已写而旧代码不能理解，旧worker禁止启动；用前向修复或明确版本停机处置，不能加永久兼容reader维持运行。
- 所有原始证据保留；正常结果或immutable package不覆盖。迁移范围只允许明确授权的当前订单，不延伸历史jobs。

### 12.2 业务与外部依赖清单

已确定：safeplus、US、仿真树GTIN豁免。**不再重复询问或编造GTIN。**

真实执行前尚需明确：
1. 当前数量变体是否有正式模板支持的合法主题/建模依据；无依据则保持阻塞。
2. 适用于对应SKU的库存、制造商、产地、履约、价格字段策略、包装层级、电池与危险品声明及来源。此前“其他默认”可作为配置授权线索，但须明确具体值/范围，不能自动当事实证明。
3. 上架包交付URL最短有效期、对象保留政策和下载交付定义。
4. 供应商可核实计费上限/币种；本次诊断、生产、QA及存储费用分别的授权边界。
5. 两笔unknown逐请求处置；如果用户不接受重复费用且供应商查不到，就继续冻结，不承诺可强行完成。
6. 阶段5新增样本的准确路径/用途、并发、总次数、总金额、长跑时长。原授权不复用。

这些不影响先完成免费的源码整改/隔离验证，但会决定何时可以开始真实生产。

## 十三、推荐的首批实施范围

**第一包（阶段1）**：恢复套件预算、删除退役图片协议、观察unknown停止再发、修正not_sent分类、绑定准入/receipt、统一有效配置与deadline。目标是“修复过程中不会继续重复花钱”。

**第二包（阶段2离线）**：原raw数量变体、统一事实/claim约束、错误关键词/default删除、实际Count、模板条件与业务档案前置检查。目标是“在任何图片付费前证明这个订单具备完整交付的静态条件”。

**第三包（阶段3/4离线）**：常驻接续/订单revision、统一异常入口、URL时效、正确模板/自足ZIP/下载状态。目标是“有了合格图片即可自动交付，无需手工维护”。

**第四包（阶段2/3/4真实验收）**：另行有界授权，按原家族完整范围跑六里程碑并复核图与包；未获授权继续只做离线，不卡住其他独立整改。

**第五包（阶段5）**：小规模多家族后24h混合运行。只有金额、质量、恢复、交付四个门同时有真实证据才扩大规模。

**最终策略：先止损，后修事实与模板，再恢复规划，最后以真实整包证明无人值守；不靠重试、默认值、删槽或降低审核门槛制造成功。**
