# 产品主体保护实际链路核查

日期：2026-09-22。核查生产代码与本次冻结证据，并用刚才的床架子体 `B0DSSKTXXW` 做隔离遮罩能力测试；未修改生产代码、未覆盖已有候选。未使用旧图像技能作为判断依据。

## 1. 明确结论

用户确认的保护范围：只保护可见床架本体的结构、颜色、纹理和材质，包括部件数量、比例、间距、连接关系与固定入口。床品、摆件和房间布置允许改变；栏杆间隙中看到的背景也不属于床架。验收对照床架本体，不能把床品或背景变化计为产品失真，也不以整张图片逐像素一致作为通过条件。更换床品时不能借遮挡隐藏原本需要核对的结构；移除遮挡后露出的结构应有对应产品源图依据。

**当前正常生图主要采用“原图参考 + 文字保真要求”。存在可选遮罩的传输能力，但没有在正常任务构建链中生成并绑定产品保护区域，因此本次没有执行产品区域保护。**

真正负责保护生效的环节应是既有 generate 阶段中的请求准备和编辑执行。规划负责决定编辑哪张产品图、哪些内容允许改动；事实和观察负责说明产品是什么；生成后的 QA／人工检查负责判断结果是否被改变。

把事实描述得更详细、让规划看到更多图、增加保真提示词，可以提高正确率，但不等于建立了产品区域保护。上一份方案 M1–M4 主要修正前者，尚不能单独称为完整的主体保护实现。

## 2. 目前各环节到底做了什么

| 环节 | 当前实际行为 | 保护能力边界 |
|---|---|---|
| source observation | 记录对象、可见部件、状态、归属、颜色、尺寸；当前 objects 并不提供产品像素分割 | 确认产品事实，不能锁定图像区域 |
| visual planning | 选择 product_sources、目标状态、展示范围、环境和文案；规划输入目前仅一张 appearance 原图，其余为事实目录 | 约束设计意图，不能强制模型保留产品 |
| ImageTask | resolve_edit_references 将第一个 product_sources 设为 edit_base；_edit_contract 列出 preserve／replace／forbid；绑定 SHA | 保证引用哪个输入、要遵守什么规则。源文件 SHA 校验不是生成主体保真校验 |
| prompt compilation | 将合同和可见事实编译成文本，与原图一起提交 | 文字约束，仍依赖模型遵守 |
| generation executor | 校验引用文件、选择线路；有 protected_mask 才读取和传输，没有则传 None | 本次实际走无区域限制的参考图编辑请求 |
| provider transport | 编码／限制输入尺寸，发送 image 或 image[]；有 mask_bytes 才加入 mask 字段 | 可传递区域约束，但接受字段不代表实际保护效果合格 |
| candidate commit | 检查图像格式，执行超分辨率，保存不可变候选和指纹 | 保护文件一致性；不会把发生变化的产品像素恢复为源图 |
| QA／人工检查 | 检查结构、数量、颜色、尺寸等；QA 有 product_fidelity 等门禁 | 检测和验收结果，不负责在生成时保护。当前按用户要求未运行自动 QA |

## 3. 三个容易误解的代码事实

### 3.1 soft_lock 是标识，不是锁像素算法

`core/image_task_inputs.py:360` 定义 reference_edit_soft_lock、source_size_visual_restyle、reference_infographic_design。`core/image_generation_executor.py:110` 只校验名称是否合法；没有依据这些名称执行区域冻结、产品抠图、几何约束或恢复源像素。

因此不能把这些名字解释为“主图已软锁主体”“尺寸图已锁原产品”。

### 3.2 有遮罩读取器，但正常任务没有遮罩生产者

- `core/image_reference_context.py:85` 的 source_reference 返回来源、SHA、用途和可见事实，不创建 protected_mask。
- `core/image_reference_context.py:138` 的 resolve_edit_references 组装这些引用，不生成遮罩。
- `core/image_reference_context.py:228` 的 generation_reference_mask_bytes 只是读取已有遮罩并检查 SHA、RGBA 和尺寸。
- `core/image_generation_executor.py:96` 仅在引用自带 protected_mask 时启用。
- `core/image_provider_transport.py:615` 仅在 mask_bytes 非空时发送 mask。

当前缺少的是把“应保护的具体产品区域”绑定到编辑底图并使之在执行中生效；不是缺一个 mask 参数名。

### 3.3 接口能力声明和 smoke 不证明保真

`core/api_registry.py:118` 依据配置里的 api_type 和 protected_mask 能力标签筛选线路，不对保护结果做验证。

`core/provider_smoke.py:187` 的图像测试使用 32×32 浅灰图和全透明遮罩，只检查是否返回非空、可解码图像。没有包含需要保留的真实产品区域，也没有比较被保护内容。因此即使 smoke 成功，也不能声称该网关／模型已经证明能够保护主体。

另外，targeted_edit 把上一张候选作为第一附件并加“保留正确像素”的文字。它会移除原图遮罩，避免把旧坐标错误套在候选上，但没有生成候选坐标系的新保护区域。其名称同样不代表强制局部修改已经实现。

## 4. 本次九张床图的实证

目录：`test_runs/freeze_4asin_2var_20260922_fast2/recovery_jobs/B0DSRTM3HX_minimal_fix/reports`。

- 9 个任务，带 protected_mask 的任务：0。
- 9 个 finalized 请求回执，非空 mask_sha256：0。
- revision_mode 全部为 initial。
- 9 张规划的 design_review 均为 supported，包括 main 和全部 scene。
- 主图／场景标识为 reference_edit_soft_lock，功能图为 reference_infographic_design，尺寸图为 source_size_visual_restyle；三类都出现产品重绘表现。

这证明本次主体区域保护没有启用。没有遮罩不是所有结构错误的唯一原因，但“当前有可靠产品像素保护”的说法不成立。

### 4.1 用同一 ASIN 做的遮罩能力实测

隔离目录：`test_runs/subject_preservation_20260922/mask_test_B0DSSKTXXW`。测试线路为 `cxk_gpt_image_25_sunburst`，网关回报模型 `gpt-image-2.5-sunburst`，编辑端点为 `/v1/images/edits`。三次请求均绑定同一张有效源图和各自非空 `mask_sha256`：

| 对照 | 预期 | 实际结果 |
|---|---|---|
| 全不透明遮罩 | 整图不可编辑，源图应保持不变 | 输出改成蓝墙儿童房，床体、床头屋顶、护栏、床脚、木纹和床品全部重绘 |
| 产品区域不透明、背景透明 | 只改背景，产品区域保持 | 遮罩内床体仍整体重绘；受保护区超过 10 级通道差异的像素约 87.9%，可编辑区约 83.3% |
| 全透明遮罩 | 整图可编辑 | 整图重绘；表现与全不透明样本同类，但细节随机变化 |

全不透明样本中，约 83.5% 的像素出现超过 10 的最大通道差异；全透明样本约为 89.0%。由于返回图尺寸为 1254×1254、源图为 1500×1500，数值比较包含缩放误差，不能把百分比解释为原生逐像素精度；但输出尺寸变化和肉眼可见的整床重构已经足以否定“保护区域保持不变”。

全透明和全不透明得到同类整图重绘，不支持“只需反转透明度即可实现保护”的解释。当前实证是：**本地请求记录了遮罩，返回结果未满足严格的保护区域不变要求。** 仅凭本地回执和输出，无法确定是网关忽略遮罩、上游转换，还是模型仅将遮罩作为软约束；不能把内部原因直接定为“模型没有收到遮罩”。因此不能通过给现有正常任务补一个 `protected_mask` 字段，就宣称主体保护已经完成。

用户明确保护边界后，对本次实验作如下限定：产品区域遮罩使用了覆盖床架、床品及部分背景的宽多边形，提示词也要求床品不变，范围超过实际要求。上述像素差异比例只能用于遮罩能力探查，不能解释为床架失真比例；床品、摆件、房间变化本身均允许。实际质量判断仍须逐项核对可见床架的结构、颜色、纹理、材质。后续代表图验证应允许环境和床品变化，并按这个范围验收；全不透明控制图只用于诊断接口能力，不作为正常图片任务或必经门禁。

全不透明请求首次返回 HTTP 524，按现有已授权规则在同一绑定下重发一次后成功；原未知回执保留为 `superseded`，最终回执为 `finalized`。这不影响遮罩结论。

## 5. 保护应该在哪里执行

### A. 规划确定边界——决定要保留什么

在现有 product_sources 和 presentation 内选择匹配目标状态的编辑原图，区分产品与可换背景、床品、道具、文字和图形。不能一面要求保留源产品，一面要求没有证据的新角度、新开门状态或重新露出隐藏结构。

这一层是保护的前提；补全规划附件用于减少错误理解，不是最终的保护执行。

### B. generate 请求准备落实边界——核心执行责任

在现有生图入口将所选底图、编辑范围及真实可用的图像编辑控制一起绑定和提交。若采用现有 native mask 通道，需要：

1. 区域必须对应实际第一附件及其 SHA、尺寸与坐标系；更换底图后不能沿用旧区域。
2. 保护真实产品部件，正确区分围栏之间的背景、床垫、可换道具与产品，不用一个大矩形替代产品区域。
3. 编辑／缩放／裁切与该区域一致；不能使用原位置遮罩同时要求产品随意换机位或移动。
4. 核验当前实际线路的保护效果，而非只核验字段是否接受；已有候补线路也不能被自动视作保护能力相同。

这是待评估的执行方案，不是已完成能力。当前项目没有可靠区域生成实现和效果证据，不能把它压缩为“开启一个配置即可”。也不应先把未验证能力设为所有任务必须满足的新门禁。

### C. 输出检查验证边界——判断有没有守住

原有 QA／人工检查对照结构和产品外观。小样应核对模型原始输出与最终放大候选，避免把输入正确、请求成功或超分后的清晰度当作主体保真。

原始返回在 finalized 后会被当前 finish_response 清理；如需做放大前后归因，应在针对性验证中保留该实验原始返回。不能用现有最终文件臆断所有纹理变化发生在哪个阶段。

## 6. 对整改方案的收口

1. 先解决当前规划／编辑目标的矛盾，明确产品视图与可改区域。
2. 在现有 generate 环节做小样能力验证，确认哪种请求控制真正保持主体；未通过前不全局强制、不新增阻塞。
3. 根据验证结果确定保护实现，再更新最小实施范围。仅改提示词或扩大规划输入，应诚实称为保真约束改进，不能称为强保护完成。

用户要求的是可见床架的结构、颜色、纹理和材质保持一致，允许更换床品、摆件和房间布置。严格像素保护只是待评估的实现手段，不应将其扩张成整图不变或全不透明测试必须通过的生产要求。是否需要遮罩或其它执行控制，应由按上述边界核对的实际输出决定。

**最终分工：事实／观察定义产品；规划定义编辑范围；generate 执行保护；QA／人工检查验证结果。主体保护的执行责任明确落在 generate，而不是让视觉规划、提示词或后置检查单独承担。**

## 7. 精确保护边界复测结果

后续用同一子体 `B0DSSKTXXW` 对 main、scene、scene_02、func_02、func_03、size 共 6 张做了真实生成。提示词明确只保护可见床架的结构、颜色、纹理和材质，允许床品、摆件与房间改变；GPT Image 2 与 GPT Image 2.5 Sunburst 的六张输出仍全部重新生成床架，具体表现包括栏杆数量或间距、固定入口边界、床头储物格比例、屋顶连接、木纹与紧固件位置改变。床品和环境变化没有计入失败。

详见 `docs/床架主体精确保真复测_20260922.md`。再分析发现，本次追加保护段但未删除旧的自由构图与首图参考措辞，六张都没有区域控制，并且均经 subrouter.ai 网关；不能说文字合同已经完全排除歧义，或把两个模型配置名称当成独立官方模型实测。明确成立的是这组请求的床架保真失败。修订后的执行建议统一维护在 `docs/主体保真问题清单与最小整改方案_待审核_20260922.md`：评估源产品区域保留与模型编辑区域合入，先验证准确分区、坐标对齐和自然融合，不再以叠加提示词代替执行机制。
