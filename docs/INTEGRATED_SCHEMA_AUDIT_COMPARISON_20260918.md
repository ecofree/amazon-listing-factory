## 4. 新报告需要修正或补齐的部分

### 4.1 P0参考纠错必须成为实施项

不能仅在验收列表写“窄框不得冒充整物”，却不指定谁判断、谁纠正、何时作废旧判断。

现有责任点是 `observe_child_sources`、`physical_views/_extract_view`、参考目录投影和已有局部观察纠错。需要明确：

1. 坐标形状合法、文件SHA匹配只证明数据可解析和来源未变；模型的whole_view标签及同一回复里的特征框不能自证像素完整。
2. 技术上异常的裁片进入现有纠错处理时，携带实际原图、实际裁片、坐标及声明的产品范围。几何异常用于触发核查，不能写死床架比例去裁决所有类目的事实。
3. 裁片实际包含什么由视觉证据判定；程序不能猜小数点、偷偷扩大框、换成整张源海报，或把异常裁片仍列为可用底图。
4. 修正后的观察版本使受影响的参考、规划、prompt和审核记录失效，其他有效结果继续保留。局部纠错应接入已有 `_local_evidence_repair` 所需的来源修订绑定。
5. 既有纠错预算耗尽后，只保留依赖该证据的未决项；同child有合法替代证据时允许在原规划内选择。

两份报告都没有实现这一过程。异常触发条件与正常输入调用开销还需在具体补丁中明确，不能把“再让模型检查”当成已经闭环，也不能据静态检查保证任何错误裁片都能自动发现。

### 4.2 用途语义应细到产品事实，不能机械删除第三个枚举

普通同child身份参考无需承担出现在目标画面的义务。若确需从另一个视图引入结构，应说明已有证据中的哪个特征、要在什么输出范围体现，而不是把整张view都变成必显对象。

建议复用当前 feature_id、物理事实ID和任务的presentation范围表达这种依赖；由模型做证据选择和设计判断，程序校验引用有效。目标视图包含的文字、背景、枕头及普通道具仍属设计自由。

`_image_direction`、`design_binding_request`、参考附件投影、prompt和候选比较必须在同次替换中一致。删除“非verification视图全部就是必检展示目标”的旧规则，同时保留对候选中额外产品、虚构结构的观察。不能仅把全部integrated改名，也不能删除所有源证据纠错权限。

本次还复现了一个同类残留：仅含 `text_spec` 的视图被作为 integrated 时，`_image_direction` 仍报 `Selected measurement views need visible endpoint geometry`。当前已经区分文字规格与物理箭头，但这一消费点仍按“测量所在view必须display”处理；文字规格无需虚构两端点，真实箭头则仍需物理对象依据。该项应与用途替换一起处理。

### 4.3 局部接纳不能变成随意忽略坏行

实际编译器已经能保留缺失单行之外的其他ready项，也能接受返回顺序变化。需修复的是未知/重复role进入局部循环前抛整份异常。

同一明确role重复，应隔离该输出并保留其他唯一、有效的输出；未知role应保留原始诊断，不猜它属于哪个缺失角色。缺失输出继续按既定交付清单显示待处理，不能默默减少任务。完整JSON无法解析时，不凭截断文本伪造成功行。

共享设计本身失败与单行失败不同，确实依赖该设计的输出不能被伪装成ready。对于不适用字段，应在现有合同中定义清楚；不能由程序临时创造字体、色板或品牌风格来补缺。

### 4.4 固定交付身份需要明确保存位置和唯一读取路径

本次实际函数返回：

| 同一source_05 | 修改前 | 插入func来源或将已有scene来源改为func后 |
| --- | --- | --- |
| role | func_02 | func_03 |
| logical_task_id | generate:CHILD:func_02 | generate:CHILD:func_03 |

因此“复用现有逻辑ID”只是一项目标，不能直接解决身份变化。也不能绕过现有指纹，让改变过的任务复用旧候选。

当前RunScope固定的是child与原始来源清单，未持久化输出角色清单；规划、任务、验收多次调用task_specs重新计算预期输出。修复应将交付范围保存在现有权威产物中，并删除后续按来源排序重新推导同一清单的行为。例如在现有RunScope中保存确定的输出集合及其初始对应关系，ImageTask记录该输出的当前输入和状态，所有消费者读取同一集合；不要再创建第二份输出清单及同步器。

这项涉及首次建单、分类纠错、恢复和当前候选关系，不能在只改task_specs后就宣布完成。原始来源新增已受到RunScope库存指纹限制；合成插入实验没有证明线上已发生错误发布。本次同源清单重分类实验说明，现有库存冻结也不能单独解决角色身份问题。

报告举例的N=1不是当前四个类目完整生产的合法默认范围，它们要求main/scene/func/size。数量灵活性应服从用户批准的交付范围，不能为了通过实验取消必要角色。

### 4.5 多个尺寸来源不等于多个互相冲突的权威

正常分类 `_finalize_child` 选出size_winner，其余尺寸资料可能转为func或review_required；多个人工size指定会在更早处拒绝。应从这里判断测量资料是否互补，不能只删除task_specs的多size报错。

保持一个输出的测量合同，可以引用多份真实来源，但必须按测量对象、属性/轴、数值、单位和限定条件合并。整床宽度与抽屉宽度不是竞争读数；同一对象属性的不同数值才需要解决冲突。测量事实可互补不意味着自动新增或删减size输出。

按依赖收窄text_gaps/measurement_issues时，不能把“规划没有引用”当成删除必要事实的许可。应先保留该输出承诺表达的功能和尺寸，再判断未决项是否影响它。

### 4.6 配色与共享设计不能全面放宽

本次复现：共享 graphic_direction 少一个backing_color会使整份设计编译失败；同一个towels组件描述两种hex也会被拒绝。后者使“白色底、深色细条纹”等合法组合难以精确表达。

但共享组件的颜色归属和func/size图形颜色合同承担了用户反复要求的child一致性。不能改成每张图自由写颜色，也不能删掉字体/徽标/箭头的共同权威。

可采用的方向是：同一组件允许在共享设计中明确主色、纹样和点缀，单张只选择组件；同一图形用途只有一份已确定的颜色定义。无需所有图形元素一个颜色，更不能让程序替Gemini选颜色。这个变更若扩大到配色schema，必须同步所有消费者并移除旧格式，不能作为解除本次5像素阻塞的前置大改。

报告建议取消“模型填写路径、SHA”的义务，需要先辨明当前是否存在：当前核心规划schema并不要求模型填写实际文件路径或SHA，程序已经负责它们。模型选择source/view/feature涉及证据决策，不能全部当机械索引自动填入。

## 5. 修正后的实施顺序

以下为同一生产链中的工作顺序，不是新增生产stage。

| 优先级 | 具体修改 | 完成证据 |
| --- | --- | --- |
| P0 参考与纠错 | 明确裁片可用性；将实际原图/裁片缺陷归还现有观察；作废受影响版本并保留有效同级项 | 真实5像素样本不会成为有效整床依据；正常细长产品和合法局部可用；局部修正后成功同级项不重跑 |
| P1 用途传播 | 区分身份参考与应呈现的特征；同步规划、复核、附件、prompt、现有QA；修正text_spec被按实体箭头处理的残留 | 多参考不强制多面板；局部图不承担整床覆盖；真实结构转移和额外错误产品仍可被发现 |
| P2 接纳与输出范围 | 在原编译器隔离单行异常；冻结既定交付集合；纠错换证据不会偷偷重编号；允许合法跨角色参考 | 未知/重复行仅影响对应未决输出；顺序变化与缺行原有行为保留；来源重分类不错误复用/丢失候选 |
| P3 事实依赖与请求 | 按输出必须表达的事实处理测量/文字缺口；澄清互补尺寸；缩小现有复核权限及所携事实；最后无损去重 | 不丢尺寸、限定词或具体卖点；scope外缺口不阻塞；实际附件与审核证据一致；请求减少来自减少无关工作 |
| P4 冻结验证 | 经用户批准后，先一个child全部既定图片，逐张看实际附件、成图与角色间一致性，再扩大品类 | 有真实请求耗时、重试次数、恢复记录、图片检查结果；冻结中不改代码 |

共享设计的多色纹样表达可作为后续质量修正，或在P3有明确实际输入需求时同步替换；不要与解除参考错误的最小补丁强行捆绑。

现有100例/60秒生产测试预算保持。优先改已有相应测试，使用真实失败形态加合法反例；不把本次诊断脚本添加成第二套默认生产测试。

## 6. 旧行为清理清单
