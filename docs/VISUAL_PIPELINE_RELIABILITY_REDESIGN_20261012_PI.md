# 视觉流水线可靠性设计复核与完整改造方案

日期：2026-10-12。状态：**设计方案，尚未实施**。

依据：当前源码、`FREEZE_PENDING_ROOT_CAUSE_AUDIT_20261012_PI.md`、用户指定四个续跑 job 的已保存证据，以及本轮只读设计探针。没有修改生产代码/原 job，没有增加预算，没有请求模型/SAM/生图，也没有检查 41 张新候选的画质。

## 0. 核心判断

**不是每一次运行都必败；但当前设计会把正常、可预期的模型误差，确定性地放大成长期阻塞。因而这是一组系统性设计缺陷，不是靠碰运气重试就能消失的偶发事故。**

必须区分：

1. 模型哪一次漏角色、错字段、误认物体，是概率事件。本轮样本相关，不能拿 29/76 当成未来通用失败率。
2. 给定同一不完整回包，解析器如何拒绝、何时扣修改名额、恢复时是否跳过，是确定的程序行为。
3. 一些问题在特定输入结构下是必现的：空对象证据同时被分配输出又排除附件；外观源同时保留 func 导致增加图位；无关输入进入全局接受 key；提示词修订改变预算目录。
4. 生成模型是否忠实执行蒙版，是另一个需要真实输出验证的能力边界。修复流程不能替代这个验证。

反例也已检查：原木浴室柜 `B0H1VSH5GM` 在同样四次工具请求中达到了 10/10 ready，四个批次都完整返回了所请求的角色。这说明现有链路可以在模型恰好严格遵守协议时工作；缺陷在于它不能可靠承受正常偏差。

上一轮“删除重复审查”的方向可以保留，但把协议错误与语义拒绝合成 stopped、过度压缩修复合同、保留过宽的失效依赖，确实没有形成可靠的纠正闭环。不能继续把责任归给 SAM 或模型随机性。

## 1. 偶发触发与确定性后果

| 问题 | 触发是否偶发 | 当前代码的确定性后果 | 设计判断 |
| --- | --- | --- | --- |
| 五角色回包只返回 main | 模型漏项有概率；三个同构批次实测发生 | 其余四项转为 blocked，再写 stopped | 缺少部分成功后的有界补齐，不是证据不成立 |
| 完整修正方案缺顶层 reason | 有概率 | 即使动作和内部证据说明完整也整项拒绝 | 解释字段不应拥有业务授权字段同等否决权 |
| wall 与 room.wall | 模型选择哪种写法有概率 | 只要给 wall，当前规则必拒 | 生产者和消费者没有共用可枚举 ID 合同 |
| 修正字段错层 | 有概率，且工具请求未给原 schema | 整份 replacement 拒绝，角色停住 | 修复输入不足，又要求全对象再生成 |
| 校验失败前 modifications 已为 1 | 错误输入有概率 | 必然记成用过修改机会 | 提议、准入、执行、成功被混为一事 |
| phase=stopped 且仍有工具余额 | 一旦进入该状态 | 普通 resume 必然跳过 | 状态分类错误；增加次数也不会自动恢复 |
| whole_view 但对象/feature 全空 | 模型漏登记有概率 | 可显示成功/分配图位，却不附原图并禁止选择 | 上下游可用性谓词冲突 |
| appearance 源保留 func 角色 | 取决于分类/选图 | 当前分配可同时增加 main 和 func | 一源多用途没有明确目的与覆盖合同 |
| 源图多个实例超过售卖数量 | 图像输入的常见结构 | 不应直接判整图无效；先选目标实例 | 源陈列数量、售卖数量、目标数量必须分开 |
| 同一商品在多幅细节图出现 | 常见图像结构 | 重复 owner 或把步骤建成新 owner 会失败 | 实例身份与视图/部件索引没有被正确表达 |

统计事实仍是：76 图位，47 ready、29 pending；28 个 pending 在 SAM 之前被挡住；24 个还有子体工具预算；12 个修改名额在实际执行前已经消耗。

这不能证明某个问题每次模型调用都会出现，却足以证明它们不是值得忽略的异常边角。

## 2. 本轮设计复核新增发现

探针见 `test_runs/pi_design_review_20261012/design_probe_results.json`；全部只读。

### 2.1 不相关源图可以使已接受角色失效

`visual_design_kit_compiler.plan_key()` 哈希整个 sources 和 product_claims 列表，不仅是该角色真正使用的依赖。

探针保持 main 的草稿、实际 source_00、蒙版、事实、共享设计完全不变，只在内存中改未被 main 使用的 source_01 的路径，main key 发生变化。

**后果：局部证据修复/文件重定位可能扩大成兄弟图位重新接受，甚至连带阻止候选复用。** 不能把“所有东西都进 hash”误当成更好的真实性保护。

### 2.2 内容修订与费用预算共享同一个身份

`_kit_input_revision()` 包含提示词 SHA；`build_visual_design_kits()` 把预算文件放在该 revision 目录下。探针只给提示词增加末尾换行，revision 就改变。

这证明预算寻址依赖内容/提示词修订。当前代码在新目录没有账本时读空预算，存在把内容修复变成新计费额度的结构风险。

**本轮没有实际创建新预算或观察到重复收费；不能把设计风险写成已发生的账单事实。** 正确原则是：内容可以修订，已授权费用账本不能因此清零。

### 2.3 改失败兄弟项的诊断文字，也能破坏成功回执

`verified_tool_decision()` 用当前 `parse_decisions()` 重算整个历史批次，然后与旧 canonical decisions 比较。

在内存里仅让一个失败兄弟项的报错文本多一句说明，main 的原始响应、上下文和接受记录完全没变，main 验证仍失败：`Planner decision projection changed`。

**这意味着只改解析器错误说明，也可能使正常接受失效。** 必须先修证据校验的粒度，不能直接放宽 parser 然后把旧账本当新结果。

### 2.4 项目已有可以复用的正确模式

- 源图观察保留成功行，只补失败源图，且记录真实请求预算。这比规划器把遗漏项直接判成终止更合适。
- `image_response.py` 区分 prepared/submitted/received/finalized，实际提交边界在锁内记录；恢复先用保存响应，未知结果不会因为本地重试自行获得重发授权。
- `image_tasks._task_fingerprint()` 已主要基于实际编译 prompt、事实、参考图语义和测量内容，而不是所有调试字段。规划接受也应采用这种依赖分层。

方案应扩展这些现有责任，不再建一套备用控制器。

## 3. 改造目标与不得牺牲的约束

目标不是“把 pending 全改成 ready”，而是：

> 可修复的协议/合同问题能在明确边界内推进；真实证据不足有准确停止原因；成功结果不受无关变化影响；每次付费与工具执行均可追溯且不重复。

必须保持：

- 一个生产控制器，一个规划责任方，一个事实权威；没有第二套兜底流水线。
- 当前八变体、76 个图位不删、不改分母；47 个已接受角色和 41 张新候选作为回归保护基线。
- 不因请求措辞、错误说明或无关来源变化重生成成功候选。
- 不重置已发生的规划/工具/生图消耗，不自动扩大重试权限。
- SHA、原图/mask 几何、实例归属、确认过的商品事实、测量归属与发布 QA 保留。
- 不让程序靠数量词正则或像素点命中猜视觉事实，也不让模型覆盖已确认商品事实。
- func/size 继续是参考图编辑，不改成凭空渲染、局部拼图或像素粘回兜底。
- 不新增人工逐图前置审批；真实不可核实事实仍不能假定通过。

## 4. 目标流程：原有阶段不增加，内部责任明确

```text
classify：源图证据提取 + 同一阶段的有界缺项补齐
    ↓
程序确认来源覆盖、可用引用和图位目的
    ↓
brief：一个规划者，使用完整、当前、分角色的合同
    ├─ 缺草稿/合同不完整 → 只创建缺项或修指定字段
    ├─ 当前 SAM 结果 → 接受 / 有效局部修改 / 明确拒绝
    └─ 修改产生新内容 → 确认该新内容
    ↓
单一 canonical 执行规范 → ImageTask / ImagePrompt
    ↓
已有候选/付费响应优先复用 → 必要时生成
    ↓
实际像素 QA → 人工审核 → 发布/模板
```

其中分支是现有 brief 的工作类型，不是额外三层模型审核。

## 5. 改造包 A：源图证据和图位分配先一致

### 5.1 可用性只定义一次

在现有观察/引用模块里定义唯一的 source usability 判据，分类、规划附件选择和任务构造共同调用：

- 声明有可见完整/局部商品且承担商品图交付时，必须有可引用的商品实例，或明确的未解决对象索引问题。
- whole_view + objects=[] + features=[] 不能同时被当成完整成功、可交付源图。
- 没有独立功能 feature 不等于没有产品；外观图允许只有有效商品身份。
- 纯文字/图表、真实无商品、错变体等情况要显式区分，不能统一用“空列表”代替。
- 只在已有观察阶段、已有预算内补必要缺项，保留其它已验证行，不重读整个图库。

源图三株而售卖两件，不等于整图商品身份错误。观察如实登记源中实例；规划决定保留哪些，商品事实决定允许多少。

### 5.2 源图未解决不能让库存悄悄变小

修正可用性以后，不能因为来源变成 pending 就从输入列表中消失、连带删除输出要求。

必须核对：

`冻结来源 = 已解决来源 ∪ 待解决来源 ∪ 有明确依据的排除来源`

三者互斥，未解决项保持可见。当前 76 图位原样保留；若新任务尚未能确定全部角色，报告未分配的必要来源，不把已知角色数量当作完整分母。

### 5.3 明确一个图位的目的，不强迫每图发明新事实

库存项至少明确：稳定 role/slot 身份、来源覆盖要求、目标用途、必需事实/动作/测量以及允许的编辑底图范围。

- 同一事实可以支撑 main、scene 和 func 的不同表达，不要求每张必须发现新的卖点。
- 同一原图兼 main/func 可以合法，但必须有两个明确交付目的，不能仅因分类标签就隐式多出一张任务。
- 选择其它编辑底图不改变原槽位的覆盖义务；需要显式记录哪些必要证据被哪个输出满足。
- 不能为了“已覆盖”而漏交固定图位，也不能为了凑图位发明功能。
- 当前白浴室柜 9 源图/10 图位保持不变，先把 main/func 双用途说清楚并补齐。未来任务的分配策略如要改变，必须单独注明新旧分母，不作为本轮通过手段。

这是 `final_source_intents`、`image_task_inputs` 和 Kit.output_inventory 的同一次分配责任，不增加库存审批模型。

## 6. 改造包 B：一份合同同时供生成、验证和修复使用

### 6.1 删除“提示词一份 grammar、Python 另一份规则”

将现有字段定义集中为一个可生成以下内容的合同描述：

- 分角色初始响应 schema；
- 当前工作项的修复/工具响应 schema；
- 允许的 source/object/feature/measurement/component ID 枚举；
- 本地字段校验与具体错误描述；
- 单一 canonical 执行表示。

这属于从现有编译器提取并删除重复职责，不新增控制器或兼容解释层。

`room.wall` 等 ID 由程序给出可选清单，模型只选择，不自行推断字符串路径。不要靠事后给任意词补 `room.` 来做模糊兼容。

已验证支持结构化输出的现有路由可使用原生 JSON Schema 约束；无论运输方式如何，本地验证都相同。不能把“API 能返回 JSON”当成“支持严格 schema”，也不能失败后静默换一套合同。

### 6.2 每次请求自包含，不假定聊天记忆

工作项明确区分：

| 工作类型 | 必须提供的内容 | 允许结果 |
| --- | --- | --- |
| create_draft | 固定角色、完整当前 schema、相关原图/证据与 ID 清单 | 完整草稿或明确证据问题 |
| repair_contract | 当前草稿、全部可确定错误、可写字段及取值 schema | 指定字段修改；不能另改产品语义 |
| decide_region | 当前有效草稿、原图、SAM 当前结果/候选、已声明所有者 | 接受、合法局部动作、设计修订需求或证据问题 |
| confirm_region | 已执行的变化、当前内容身份、受影响视图 | 接受或明确不能接受；不能继续无限修改 |

可以在同一请求中混合，但必须有显式 work_kind、逐项 schema 和逐角色覆盖校验；不得再让所有工作看起来都是“检查 SAM 结果”。默认优先合并同类工作，不以机械拆批增加调用。

### 6.3 返回集合必须与请求集合结算

若请求 A/B/C，返回 A：

- A 校验合格则保留；
- B/C 进入 protocol_incomplete，记录 missing_roles；
- 不给 B/C 编造一个 blocked 决定；
- 下次只处理 B/C，并受原预算约束；
- 重复/未知角色按具体行拒绝，不能覆盖合法角色。

初始规划也按同样方式结算，缺少草稿不能伪装成“商品证据 unresolved”。

### 6.4 执行数据与说明数据分开

接受/修改的合法性取决于 action、绑定、操作数据与约束，不取决于重复的顶层自由文本。

- 修改数据完整且证据绑定有效时，缺少第二份说明不应阻止解析该提议。
- 真正的语义拒绝需给出问题类别与证据位置，不能只返回泛化“unsupported”。
- 诊断文字不进入内容身份，不因措辞变化失效接受或补发请求。
- 保留原文和缺失情况，不伪造模型说过的理由。

### 6.5 文字表达按用途形成联合类型

- main/scene：无新增营销文案，空声明采用稳定的批准前表示。
- size：数值从 measurement IDs 投影；display copy 不再重复数字量值。
- 普通性能 badge：证据绑定 + 无引线，不强行要求物理 feature。
- 部件 callout：必须选实际 source/feature/视图关系，不能只给半个 target。

不是把所有 target 改成 null，而是把两类合法表达明确交给模型。

## 7. 改造包 C：修字段，不重写已经正确的方案

错误应是结构化记录，例如：

```json
{
  "role": "func_02",
  "code": "invalid_reference",
  "path": "/image_direction/presentation/components/0",
  "actual": "wall",
  "allowed_values": ["room.wall"],
  "owner": "planning_contract",
  "repair_class": "field_update"
}
```

规则：

1. 一次收集当前可安全判断的错误；父字段类型错误时标记其依赖项未检查，不崩溃或编造下游错误。
2. 返回完整错误列表，而不是先修 wall、下一次才告诉模型有数字文案冲突。
3. 程序提供允许修改的字段 ID/路径及完整取值范围；仅机械字段错误，不授权重写状态、实例或尺寸。
4. 修改绑定当前 base revision；对同一字段相互冲突、越权路径、陈旧版本、未知来源全部拒绝。
5. 在内存副本上原子应用，重新验证完整结果；有效才提交新内容。无效提议不能覆盖旧有效草案。
6. 只有确实需要改变目标视图、保护意图或相关动作时，才开放对应的依赖闭包；不是所有修复都开放整个 image_brief。
7. 不添加错层/别名/拼写的无限容错表。未来请求使用一套明确 grammar，程序维护一套 canonical 内容。

当前 4 份缺外层 reason 的完整修正和 4 份仅字段错层的回包，可以作为离线修复候选证据；但不能改写旧回执为 accept，也不能跳过随后必要的 SAM/内容确认。

### 7.1 按依赖推进，不能让 wall 的格式错误阻止 SAM 准备

当前 `prepare()` 先验证整份 brief，之后才调用 SAM。因此即使源图、owner、crop 和分割意图都已有效，文案/配色字段一个错误也会让本地工具结果完全缺席。它进一步制造“只有 main 有 SAM，其它角色只有合同错误”的混批，放大漏回风险。

应由同一合同验证器返回各操作的最小就绪依赖，而不是增加另一套校验：

- SAM 准备需要当前原图/身份、合法 owner、region_intent/几何及资源许可；不依赖墙色 ID 的拼写或字号说明。
- 存在明确商品事实矛盾、错误来源、缺少区域输入时，仍不能执行这项工具操作。
- 最终生图必须要求整份有效执行规范和必要接受，不能因为 SAM 已准备就提前放行。

这允许先获得可用局部工具结果，而不是让模型先修一轮 wall，再买一轮确认图。

### 7.2 一个工作项可以原子结算无关字段修复与已有蒙版接受

未来合同应表达受限事务，而不是无条件坚持“只能接受，或者只能修改整份草稿”二选一。例如同一角色同时返回：

```json
{
  "role": "func_02",
  "field_updates": {"presentation_components": ["room.wall"]},
  "region_decision": "accept_current"
}
```

这里 `presentation_components` 是程序提供的字段 ID，不是模型自造路径。角色、当前基础版本、允许字段、枚举值和 inspect 过的 mask 都绑定在请求上下文里。

程序先在副本上应用字段修改、验证有效结果，再检查区域依赖是否变化：

- 只改不影响区域的表达/样式字段，mask 和区域依赖完全不变，模型又明确接受，则可一次原子提交最终内容。
- 只要改了源图、owner、几何、必要可见状态或实际 mask，就不得顺带批准模型没看过的新结果，仍需新内容确认。
- 任何一项越界或冲突，整个该角色事务不提交；其它有效角色不受影响。

这不是程序猜测视觉内容正确，也不是增加一个审查环，而是让同一个规划者在已经提供的真实工具结果上完成明确的、有边界的决定。新 wire 必须完整定义并通过第 12 节切换验收，不能把旧回包套入新含义。

## 8. 改造包 D：区分状态、计费和工具副作用

### 8.1 不再使用一个 stopped 表示所有失败

在现有角色 journal 中分开 phase、issue_kind、next_action；JobState 只投影该状态，不形成第二份控制权。

| 事件 | 状态含义 | 下一动作 |
| --- | --- | --- |
| 请求未回到某个角色/JSON字段不完整 | protocol_incomplete | 有额度时只补缺项 |
| 已明确定位的合同错误 | contract_repairable | 只修允许字段 |
| 源实例/测量证据缺失 | needs_source | 回到同一取证责任的有界缺项修复 |
| GPU/接口暂不可用 | waiting_resource | 条件恢复后继续原工作 |
| 明确证据矛盾或无法完成的目标 | blocked_evidence | 需要真实证据/目标变化，不自动重试 |
| 当前 allowance 不足 | budget_exhausted | 请求明确预算处置，不伪装成证据问题 |
| 同一输入同一协议错误没有进展 | blocked_protocol | 修请求合同/工具，不能无限 resume |
| 合法修改已执行，内容变了 | needs_confirmation | 只确认新内容 |
| 当前内容已被接受 | ready | 不再重审；执行/复用候选 |

错误是否 retryable 是程序基于失败类型和账本派生的，不由模型随意返回。

### 8.2 三本计数不能再混淆

| 计数 | 消耗边界 | 不得发生的事 |
| --- | --- | --- |
| 物理模型请求预算 | 实际提交，提交前预留，未知结果保守计入 | 不能因修提示词/换 revision 归零 |
| 协议修复机会 | 针对一次已识别的 protocol/contract 问题 | 不能伪装成 SAM 已执行 |
| SAM 修改操作 | 输入校验后，执行前预留；记录 started/result/commit | 校验失败不得占用已执行次数，启动后失败不得轻率退款 |

在具体副作用之前完成校验。操作一旦准入则原子保留唯一 operation_id，再执行。中断后先恢复保存结果，不能只靠“执行次数未加”再次调用。

同一次明确未发送可释放预留；已提交、状态未知或本地结果待提交，都不能凭超时自行退回额度。沿用现有锁/账本机制，不引入数据库作为第二状态权威。

### 8.3 只接受可度量的进展

进展包括补齐缺角色、消除具体合同错误、获得新的有效源证据、真实修改区域、接受当前内容、形成明确不可行结论。

只改 reason、换 request UUID、移动文件、换错误文字或重复相同无效提议不是进展。自动协议修复对同一输入/同类错误最多一次，且计入原物理预算；再次无进展即明确停止。

## 9. 改造包 E：预算、内容、审计身份拆开

### 9.1 三种身份

- **content_id**：真正执行的内容、所用图片/蒙版、事实约束、目标关系和相关策略。用于接受与候选复用。
- **request_id / wire_revision**：本次请求、schema、提示词、provider、响应。用于审计，不能单独使图像内容失效。
- **budget_grant_id**：本次用户批准的 scope 和费用额度。用于原有账本；不从 prompt hash 或临时内容目录推导。

内容变了不等于获得新钱；审计信息变了不等于内容变了；上一个请求失败也不等于可以再次提交图片请求。

### 9.2 接受依赖使用真实依赖闭包

借鉴现有 `_task_fingerprint()` 的内容投影。角色接受绑定：

- 稳定槽位/范围身份；
- 实际编辑底图、选定辅助图及测量来源的内容 SHA；
- 使用的对象/部件/动作、必要商品事实与明确全局约束；
- 实际使用的共享设计部分；
- 当前 region content key；
- 当前执行策略。

保留商品身份、颜色、售卖数量等必要全局约束，不是把全局事实全部排除。真实依赖改变，必须失效；不相关路径、未用证据说明、无关组件风格变化不应使本角色重新接受。

### 9.3 验证历史事实，不用今天的错误文案重算昨天的批次

回执验证区分：

1. 原请求/响应/已封存 canonical 记录是否完整、SHA 是否匹配；
2. 本角色确实消费了哪个决定，作用于哪个内容；
3. 当前业务依赖是否仍满足。

不能把“整个历史批次用当前 parser 再解析一遍完全相同”作为成功兄弟项的必要条件。错误消息、未消费的无效回复应保留为证据，不是成功角色的语义依赖。

这不允许把历史原文改写成新的授权。新解析结果不能覆盖旧回执。已有接受保持其原绑定；新增修复决定拥有自己的父引用和新内容身份。

### 9.4 预算必须与修复版本分离

预算仍由现有控制器的唯一账本管理，但地址按 job/child/已授权 scope 稳定，内容修订只是账本记录的维度。

切换前需对当前明确范围做可审计的消耗核对；无法确定已提交的调用按已占用处理。不能因为新目录不存在就假定未花费；也不能把计数搬迁写成“恢复额度”。

## 10. 四次调用不可能保证任何输入都完成

必须承认容量下界，而不是用新策略包装无限承诺。

以十图位、每批五项为例：

- 若结构都正确：两批 SAM 决策；都需修改再两批确认，共四次。
- 若十项都缺少可执行的区域输入/完整草稿，必须先用两批模型请求补齐；再两批 SAM 决策且全部还需修改，再两批确认：至少六次，超过四次。即使混合调度，30 个有依赖的角色工作项、每批最多 5 项，也不能压成四次。
- wall 这类与区域无关的合同错误不应被人为加成上述第一轮：应按第 7.1/7.2 节并行准备工具并原子结算，减少本可避免的请求。

因此“固定四次 + 任意错误 + 必定完整成功”三者不能同时成立。

默认仍保持原四次工具请求上限、不自动增加次数。改善方式是减少机械错误、复用已有合法信息、精准安排工作，而不是许诺无条件完成。

调度在发送前输出：剩余授权、已预留调用、未完成工作、最低确认需求、下一批 work IDs。每项修改必须留出其需要的确认能力；没有余量则标记真实 budget_exhausted，不能发出注定无法确认的修改。

同类工作优先合批；确需混批时用显式 work_kind 和逐项响应合同。不要求机械分成更多阶段来耗尽预算。预算仍不足时，必须由用户明确批准额外 allowance，不能改 prompt/输入版本、重开 job 或换别名获得隐含新预算。

## 11. 改造包 F：SAM 和生图保真保留为不同责任

### 11.1 实例不等于步骤或视图

在现有 targets/parts 责任里明确：

- object_id：被观察的物理商品实例；
- 同一商品不同视图、步骤中的必要物理部件：该实例下的 part/视图范围；
- display callout：指向具体可见部件/视图，不只是一个泛化功能词；
- SAM query：具体物理对象/材料，不是“安装步骤圆圈”“作用演示”。

优先复用现有 parts/crop 与 feature 绑定，不建立第二套组件审批图。只有现有字段确实不能区分同一部件的多视图端点时，才补最小视图身份；不得把它算成额外售卖实例。

紫树 func 应补足 tree_assembly_01 下各实际部件/视图，而不是放行 assembly_step_1/2/3 三个假 owner。

### 11.2 本地运行必须能定位卡点

记录 launcher PID 与解释器 PID、启动/导入/权重/GPU/ready/请求/结果/退出阶段。非协议输出进入有界诊断日志，不影响协议解析。

使用既有 deadline 区分无启动握手、资源等待、加载中和推理中；不是简单给所有初始化加一个很短的固定超时。退出只处理本次拥有的进程树，保留 GPU lease 的正确释放次序。单个请求失败不应导致其它角色无限重复冷启动。

像素算法与进程监控的版本职责分开：日志改动不应自动作废既有 mask；但几何/权重/图像预处理的真正变化必须失效。现有全文件 hash 不能未经验证就删除，需先建立明确的行为版本和变更测试。

### 11.3 不能把 mask 支持字段当作保真证明

先检查已有 41 张候选，按角色记录结构/实例、比例位置、动作、尺寸端点、文字授权。它们目前没有画质通过结论。

若需要验证 provider 区域约束，另行批准同源图/同目标/同实际接口模型下的小规模重复对照，改变的变量只限已验证 mask；记录实际物理调用与原生输出。单次结果或模型别名不能证明独立失效域。

如果合法蒙版仍不能稳定约束执行端，调整该执行路线的能力准入；不要继续堆 SAM 前置审查，也不能默默回退到无蒙版生图或局部粘贴。

## 12. 现有成果的安全切换方案

本方案不承诺通过一次 schema 升级自动把所有旧记录变成新批准。必须先设切换验收闸门。

### 12.1 冻结当前基线

只针对明确的四个当前 job，保存只读清单：76 槽位、47 接受记录、41 新候选、6 个本轮未请求的 ready 角色、所有源/mask/task/prompt/candidate SHA、消费预算及未知/替换回执关系。

### 12.2 先证明等价，再切换

- 对未改变执行内容的成功角色，接受、ImageTask、prompt、候选和人审绑定必须保持有效。
- 只改变未来请求协议、诊断格式或调度，不能要求重生成成功候选。
- 修改依赖投影时，不给旧接受记录重算一个“新批准 key”。保持原证据封存，逐角色核对真实依赖的当前性。
- 如果某项改变实际执行内容，就按该角色新内容处理；旧审批不能自动授权它。
- 如确需不可兼容的 canonical/schema 数据转换，必须先列出具体影响并获得一次性、明确授权；不能自动迁移旧批准。无法证明等价则停止切换、保留只读证据，不偷偷重新购买输出。
- 不保留双控制器、多版本 fallback 或默认关闭的旧流程。新请求只有一套合同，旧失败记录是审计证据，不是备用执行器。

### 12.3 29 项按真正状态恢复

- 12 漏回：保留对应 main，只处理缺项，不伪造否定。
- 4 缺顶层说明、4 错层：先保存现有有效修正内容作为待准入提议，经过新明确合同/原始证据检查后才推进；不直接改成 accept。
- 2 wall：修协议给出的合法 ID，不重写其它产品字段。
- 2 空对象来源：在已有来源观察责任内纠正，并仅失效真正依赖这些来源的角色。
- 尺寸、scene 文案、badge target、安装 owner、白柜多图位分工各按具体要求修复，不能一概放宽。
- 已耗尽的预算不能通过更改状态恢复。能本地恢复的不重新付费；确实还需模型确认的额外消耗必须明确申请。

## 14. 可验收的测试和指标

### 必须通过的离线断言

1. 本批漏四项不能否定已经返回的 main，也不能伪造四个模型 blocked。
2. 修改提议本地校验失败：实际工具执行次数为 0；LLM 已发生的物理请求仍计入。
3. 缺少非授权性说明，不得丢失其完整、可校验的操作数据。
4. 给出明确 field/path/actual/allowed 错误；修 wall 的请求不能改写商品结构。
5. 合同补齐包含所有必要字段与分角色约束；不能依赖上一请求的隐式记忆。
6. whole_view/可见产品与空对象索引的矛盾在源阶段被处理；来源和输出分母不缩小。
7. 未消费源图路径、失败兄弟的报错文字变化，不使成功 main 的接受/候选失效。
8. 提示词措辞、代码监控变化和内容 revision 不会创建新的费用额度。
9. 改变真实引用图、mask、商品事实或目标内容必须使受影响批准失效；不能为了复用跳过 currentness。
10. 在请求预留、提交、保存响应、解析、校验动作、SAM 启动、保存 mask、提交 kit 等边界中断，恢复不重复提交已完成副作用；未知付费状态不自动重发。
11. same input / same error / no progress 有明确上限；无限调用和“一次格式错永远不能处理”都不是允许结果。
12. 当前 47 个已接受角色和 41 张候选的保护基线不得因无关变更回退；原文、SHA、授权与来源可追溯。

变形测试应覆盖字段缺失、缺一个列表成员、字段顺序、合法空值、无关诊断变化、错误 owner、源图部分可用、请求成功但语义不完整，而不是只模拟完美 JSON。

### 真实验证顺序

1. 先用保存的 29 个失败回包及正常浴室柜批次做离线对照；本地结构通过不能直接算 ready。
2. 对已有 41 张图建立质量基线，优先检查多实例、功能动作/硬件、尺寸端点三类风险。
3. 另行批准少量代表性 pending 场景做闭环：漏角色、四格细节图、尺寸标签、三株/二件装、跨步骤部件、main/func 双用途。
4. 每次声明逻辑工作范围以及**分类型物理请求上限**；“选六图位”不等于“最多六次请求”。生成未知立即停在原回执处，不自动补发。
5. 小样显示合同完整、没有无效循环、商品事实/实例/动作/尺寸通过后，才继续当前完整冻结范围。

指标至少包括：返回角色覆盖率、本地合同错误率、重复输入请求数、有效执行修改数、每就绪/验收图位实际调用成本、成功结果复用率、按原因分组的 pending、原生图事实失败率。不得只看模型请求 success 或单元测试通过数。

**不承诺任意输入都能在固定四次内成功，也不以删除失败图位或放宽事实来达到 100%。** 可以严格承诺的是：确定性工程错误可用测试消除；每个停止都有正确责任和恢复条件；每个额外费用都有授权；已成功内容不会被无关改动反复推翻。
