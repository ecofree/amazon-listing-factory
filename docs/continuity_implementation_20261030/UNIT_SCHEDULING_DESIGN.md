## 根因与替换

现有完整运行逐阶段处理全家族：全量 fetch/copy/classify/brief 可在第一组图片形成前耗尽预算。只改 generate 排序不足。原阶段 owner 是唯一事实/缓存/规划/QA/发布权威，本次不另建控制器。

替换 progressive 完整、非 dry-run 生产运行的横向全家族开销顺序；显式 strict 即时交付预检及指定阶段维护合同保留，不自动降级策略：
1. 获取父子目标清单，但可先只取得一个子体事实。未请求成员是 deferred，不伪造事实、不从目标删除。
2. 在原 `production.py` 中按子体贯通必要阶段，优先已有成果的单元。每个阶段接受工作选择，合并写回其原工件；冻结 RunScope 不变。
3. 先完成每个目标成员的必需角色，再消费额外图库预算。未完成/未选项保留，不将其当作整单已完成。
4. 正式模板/订单完成仍检查完整家族。单元阻塞不否决其它安全单元；共享结构/身份损坏不能被跳过。

## 原预算内的收口预留

在 `BatchLedger` 内保存当前租约的阶段额度分配，不增加授权预算、不生成新费用域。预留与真实 admissions 分开：前者是未消费容量，后者永不因重试/租约变化退款。

- 当前单元为 copy/brief/必需生成/QA/publish 留出容量；额外修正不能抢走其后续阶段保留部分。
- 分配只使用原工作区/订单剩余额度；多 worker 在同一 SQLite 事务域计入其它有效预留，不能超额承诺。
- 无法覆盖估算时优先保护后续收口并记录缺口，不把它伪称精确费用或保证完成；已有缓存/已收字节的零费工作仍可继续。
- 阶段成功后的未用容量、单元结束/暂停以及过期租约的未消费预留可归还可用池。原消费、unknown 与总上限不变。
- 真正的模型调用仍由原 receipt + transport admission 核证；预留不是请求、事实或发布批准。
- 新建临时/合法新账本使用 schema 3，旧 schema 不自动迁移；当前项目固定账本未创建。各子体仅写单元进度，外层写完整汇总，避免为每个单元反复核全家族。

## RED / GREEN 验收合同

- 三子体、只抓取一个时，预期目标仍为三；第二次补取另一子体不重复抓第一子体或遗失第三个。
- A 的 download/classify/plan/task/prompt/QA/URL 保留；处理 B 不覆盖 A 的成果，真实漂移仍拒绝受影响对象。
- 有限预算下一组必需资产先收口，不能先付完全部家族前置阶段；额外角色与待办仍在目标。
- 两个并发租约不能把同一剩余额度重复预留；超额修正不能偷用 QA/发布份额。
- 已收数据本地处理在预算耗尽时可继续；未知 POST、同 SHA/异 SHA、失效 lease、实际消费不退款等反例保持。
- 默认 <=100/60，测试只追加到相应现行合同；先目标、隔离行为回退，再冻结默认验收。
