## 三、23 项阻塞：深层原因与最小处理位置

### 3.1 规划锚点没有稳定落在所声明的材料与部件上

真实例子：

- 白床 main 修订后 P3/P4 仍在栏杆缝内床品；scene_02 有点在栏杆后的墙面，scene_03 有点在立柱旁地毯。
- 原木床 func 的 P3 在板条间白色空隙；不是一块应该保护的木面。
- 蓝药柜 scene 系列和 func 有点在瓶罐、纸巾盒、毛巾或人身上；func_02 的 P4/P8 在清洁布上。
- 蓝药柜 main 的旋钮虽然可以属于柜体，但不能当成 `mirrored_door` 玻璃材质的正点。整件归属和局部部件归属不是同一个判断。

**责任：现有规划给出的 region intent，加上初审漏诊。** SAM 命中错误点后生成错误区域，并不能证明它错误理解了一个正确的产品目标；反过来，SAM 不覆盖床品点也不应该被当成漏床架。

最小处理：在当前规划/审查请求中用同一源图、对象、部件和点坐标判断实际可见材料，一次列全错误点。只修该点所属的既有 intent 字段；不要连带移动正确木面点，也不要新增识别阶段或品类词库。

### 3.2 审查把错误意图当成分割缺口，导致有害纠正

**已证实的反例：原木床 `func_02 / source_05`。** P1/P3=(.288,.218) 位于竖栏缝内条纹床品。初审和第三审将其解释为上护栏漏选，第三审给 `add_product` 同点。SAM 真实执行，新增 **59,324 像素、删除 0**，把这片床品保护起来。之后仍被评价为木条漏保。

另一个相反错误：棕药柜 `func_02 / source_07` 的 P3/P7=(.22,.80) 确在圆角底板，整块左下柜板没保护；审查却把 `unmasked` 绑定到 `positive_points` 并派 `revise_plan`。这会让正确木面锚点被反复修改，责任应先落到现有区域缺口。

安装件也存在范围混淆：棕药柜 `func_03` 初审称膨胀件为 non-product，但同源观察与目标状态已经包含金属件、螺钉、膨胀件。是否随售仍需既有事实证据，审查不能直接用“非柜体木面”替代安装演示的保护范围。

**最小处理：修正当前审查的归责条件。** 错对象/错材料/错点先修 intent；合法产品点且目标可见区域确实缺失才进入当前 SAM 纠正。返回的动作必须与同一 finding 的材料和关系证据相符。几何命中只能用于定位，不能自己判断材料；不再加一轮 Gemini，也不把所有 miss 自动涂绿。

### 3.3 白床修订后的新合同没有轮到确认

白床先审核 5+3 项，另一项因非法 crop 点未进远端；第一次 repair 涉及全部 9 项。随后第 3、第 4 次 review 却审核了完全相同的前 5 项，`func_02/03/04/size` 的当前新合同一次都没有审核。

当前 `confirmation_roles()` 用非空 `design_review` 筛选一些 pending 行；刚修订的新 binding 恰好 `design_review={}`，被漏计。既有 retry 排在新合同确认之前，前批又占满下一次 5 项窗口。此前离线复现的容量问题，**本次在真实白床上发生了**。

定位：[容量集合](D:/Amazon_pics/amazon_listing_factory/core/visual_design_kit.py:469)、[重审排序](D:/Amazon_pics/amazon_listing_factory/core/visual_design_kit.py:640)、[修复前容量](D:/Amazon_pics/amazon_listing_factory/core/visual_design_kit.py:731)。

最小处理：按当前合法且具备输入的 binding 统计所有待确认角色；先确认尚未看过的新合同，避免失败前批重复占满窗口。修复前的容量统计与实际审核排序用同一集合。保留现有调用上限，不能把未审行改成 ready。

**排序修好也不能保证白床全过。** 已有 8 初审+9 修后确认=17 项；如果四项区域纠正还需再确认，会超过 4×5 的容量。必须同时消除错点、漏诊和协议浪费，不能靠加预算掩盖它们。

### 3.4 蓝药柜是另一个容量原因，不能套白床结论

蓝柜第 1 次 5 项审核发生 60.172 秒 timeout；第 2 次同批成功；第 3 次审核 main 与后四项。最终 8 项 pending、review=3、repair=0。

现有容量检查判断 8 项修订至少需要两批确认，只剩一批，因而没有发送全量 repair。这是保守容量判断，**不是全部 review 额度已经用完**，也不是服务一直失败。scene/scene_02 的 supported 被程序所有权几何冲突拦下，但最后剩余的审核槽没有继续诊断这两个可审的现有合同。

最小处理：不允许闭合不了的全量修复，但不应因此提前结束所有有输入且仍可审核的诊断；在现有循环内处理尚未获得有效诊断的角色。不能承诺一批能完成八项，也不能清预算重跑。

### 3.5 F3 删除双哈希回显后，部件字段仍有误导

本轮没有再发生漏抄 `input_key/content_key` 的同类重试，但 `component_ids` 实际要求填写候选的 `candidate_id` 哈希。模型按字段含义返回了 `headboard/footboard`、`door_hinge/interior_shelving`、`mounting_hardware_callout` 等语义 part 名。

造成 **4 条 region 回执被拒**：白床 main 两次，棕药柜两个 role 各一次。供应请求已有候选信息，因此不是未提供 ID；当前绑定仍拒绝错误归属，没有错误放行。

最小处理：在现有审核合同与 `bind_region_review()` 边界彻底替换误导字段及例子，让语义选择与冻结候选的程序绑定职责一致。保留唯一匹配、所属实例和当前内容校验；不猜陌生 ID，不保留两套旧新协议，不把空 ID 自动当通过。

定位：[现有绑定](D:/Amazon_pics/amazon_listing_factory/core/product_region.py:221)、[审核返回合同](D:/Amazon_pics/amazon_listing_factory/core/visual_semantics.py:969)。

## 四、真实成图：改进与仍失败的地方

### 4.1 两种浴室柜仍输出双柜：程序传递已修，执行尚未收口

- White：crop `.15,.15 → .49,.86`，目标写明 single freestanding cabinet。

已重新生成实际上传的 alpha 保护图：两张都只保护左柜，右柜各 351,900 像素的检查窗口中保护像素为 **0**；本地重建 mask SHA 与真实 request audit 一致。**可以排除本地蒙版误包右柜及实例合同丢失这两个解释。** 剩下需要区分网关消费和图像模型遵从；本机组装和上传正确不能直接证明服务端应用了 mask，也不能单凭这次结果把网关或模型中的一个宣判为唯一根因。三个 provider 名称仍经过同一个 SubRouter，不构成独立网关对照。

### 4.2 Begonia `scene_03`：保留两株不等于保留正确两株

原图实际 3 株，观测 catalog 有 `front/left/back`；合同选中右前景大株和左株，排除描述却只写 lawn/villa，没有显式写出未选的 `obj_07_back`。源定位与输出数量已经传出，未选同品实例的排除仍过于依赖自由文字。

实际 alpha 也只保护 right-front 和 left，中后株检查窗口的保护像素为 0。原生图虽然只有 2 株，但所选源图的前后/左右与大小关系没有保留，违反原位、原比例编辑约束。输出没有实例 ID 标记，不能仅凭近似花叶反推输出每株确切继承哪个源 ID。

最小处理方向：在当前源观测对象目录和选中集合中表达哪些同品实例不属于本次目标，用现有参考合同完整投影其身份；保留同品并不等于保留每个源实例。不要把 source crop 变成裁切/重新拼接产品命令。

此项可确认只检查数量不足；当前提示已写排除其他副本及 exactly 2，不能称完全没有排除语义。具名排除是表达精度缺口，**未证明它就是本次位置/尺度变化的根因**。实际网关与模型对原位比例的遵从仍需受控验证，不能宣布以上程序表达补齐就一定消除重绘。

### 4.3 白玫瑰 `func_05`：源事实过度推断，生图执行了错误的具体性

证据链已经串起：

```text
source_05：地钉穿过圆盘 → 旋转 → 用布擦花
源观察：disc base connects to spike via screw-in threaded joint
文案绑定：physical:source_05:assembly_steps:0
批准文案：Threaded spike screws easily into base plate
原生图：画出具体螺纹连接示意；清洁布演示被替换
```

原图能支持穿盘、旋转、清洁，但不能清楚确认“螺纹就在底盘连接孔”等具体机械结构。**并未证明实物任何位置都没有螺纹**；已证明程序将不充分的具体推断作为事实授权，随后模型把它实体化。

当前 visual goal 同时要求 screw-in assembly、branch shaping、wipe-clean；显示文案却只列连接和调整枝条，native 也只有这两项，没有清洁演示。目标、可显示合同与必要功能证据没有闭合，不能简单判为模型随机忘画。实际 mask 只保护主植物，盆器和步骤圆圈不保护，与 editable 设置一致；主要 tree 实例保护并不能约束 inset 中实际连接关系。

最小处理：在现有源观察中区分可见动作、可见接触关系与未证实的连接机制；现有规划只使用有证据的具体关系，并为目标要求保留必要功能演示，不能用泛化新示意替换实际动作。删除过度具体的原推断和对应文案，不追加一个机械结构猜测器、审核阶段或提示词补丁。

证据：[源观察→合同→成图链](D:/Amazon_pics/amazon_listing_factory/test_runs/post_pi_audit_20261009/freeze_recheck/source_relation_chain.json)。

### 4.4 功能重排与原实例保留存在解释张力

白玫瑰 `func` 源图为错位、不同高度的两株，native 变成等高并排，枝叶呈近似复制。规划 state 写 `side-by-side`，编辑提示又要求原位置/比例。

此处既有功能图的版式重设计权限，也有主体位置约束，应在当前规划状态中只留下一个清晰目标：允许重新布置文字/非产品版面，不由含糊的 side-by-side 触发产品等高化。**这只是有证据的合同解释风险，不是已证明的唯一生成根因。**

## 五、SAM 的实际价值与边界

SAM 保护了许多主要产品区域，并提供了当前源实例/部件的定位证据，这使本次能够追到错点、漏选和实际执行合同。但仍有两种完全不同的现象：

1. **真实产品漏保**：床头白木面、深棕屋顶、烟囱、部分侧栏/板条示意仍缺。白玫瑰 func 的说明写保护 stake hardware，实际两处地插检查窗的保护像素却均为 0；不能根据 reason 文字宣称已保护。某些已生成图即使这些部位未被完整保护，GPT 仍保留了它们，支持“近似蒙版与模型能力要综合考虑”。
2. **非产品误保**：错误床品/陈设点会推动保护区包含床品、布、瓶罐或镜中旧场景。药柜镜中场景即使被保护，输出仍改变了反射，说明蒙版不是像素硬锁；也不能仅凭这一事实证明网关剥离了 mask。

不能把所有漏保归因 INT8。本次没有重新做量化数值对照，错点、错部件语义、query/crop 与真实分割缺口混在不同任务中；INT8 对全部漏选的贡献仍未知。**本次证据首先要求修正已有调用语义与审查归责，而不是更换权重或追求 100% 分割。**
