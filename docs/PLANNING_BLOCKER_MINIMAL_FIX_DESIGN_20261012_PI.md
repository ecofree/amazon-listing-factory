# 最后三项规划阻塞：最小修复方案（待实施）

依据：`FINAL_THREE_BLOCKERS_DESIGN_REVIEW_20261012_PI.md` 的真实回包、蒙版与控制变量回放。本文件是解决方案，不是实施或调用授权。

## 目标和不变项

- 消除“合法修改每次被最后一次额度否决、下次又重新购买相同决策”的循环。
- 保留唯一规划控制器；不新增审核模型、备用流程或自然语言规则裁判。
- 保留当前 76 图位、73 候选、接受记录、执行指纹、所有已消费额度与付费回执。
- 当前三个停点不是同一类错误：两项缺少合规的修改接续，另一项缺少对不完整多视图提案的正确处理。
- 未接受新结果不得生成；预算不足不能自动增加付费请求。代码修改会形成新冻结版本，不能冒充仍是原来的冻结指纹。

## 1. 源修复：分开“提议、执行、确认”的能力

在现有控制器中计算一份能力描述，同时提供给请求合同和执行器，不再让 `can_modify` 同时表示本地操作权限和后续模型预算。

分别判断：

1. 是否有权提出当前范围内的修改；
2. 当前源、owner、几何和本地区域操作额度是否允许执行；
3. 是否有额度发起下一次规划者确认请求。

第一项不自动赋予第二项，第二项也不自动赋予第三项。对于受控的合法提案，允许“当前不能执行但可保存”；不能再报成字段错误。

默认进度规则：

- 本地操作已授权且资源可用：执行、保存结果，进入 `needs_confirmation`；没有规划调用额度就停在这里，不能自动发请求。
- 本地操作未授权、次数已用完或资源不可用：保留为待执行工作，明确缺的权限/资源。
- 最后一次规划调用可以提出有用的修改，不必把已购买的决策丢掉。

权限不足时可以拒绝执行，但回复协议必须存在真实可表达的延后结果；不得强迫模型在错误接受与错误“证据不支持”之间选择。

受影响位置：`core/visual_design_kit.py` 的调度、consume、execute_pending；`core/planning_contract.py` 的响应合同；`core/planning_feedback.py` 的能力描述。

## 2. 扩展现有 pending_action，而非增加新队列

有效提案先在副本上完成以下检查，再写入现有角色 journal：

- 原回执、role、请求上下文与当前内容绑定；
- 可写范围、完整合同、source/owner/几何；
- 是否真的改变执行内容；
- 操作身份与待应用内容。

通过后保存原回执引用、before-content、修改内容、operation_id 以及准入状态。是否执行由同一控制器决定。

恢复顺序：

```
已有接收结果恢复
→ 已验证待执行动作
→ 已生成但未确认的结果
→ 确实还需要新决策时才发模型请求
```

每个副作用在执行前原子预留，已保存的局部结果按原操作身份恢复，不能重复推理/重复应用修改。失败提案不能覆盖旧有效内容；新结果在接受前不能变成 ready。

旧回包虽然保存着，但原上下文曾禁止执行，不能因为换了代码就自动赋予新权限。当前两项若要复用，需明确授权采用具体修复提案，重新校验绑定后进入待执行工作；不改旧回包、不伪造 accept、不迁移旧接受。

## 3. 保留工作阶段、根因和无进展记录

- 工作阶段与阻塞原因分开：例如“待执行区域修改，缺本地权限”或“已有新 mask，缺一次规划确认”。
- 预算不足不得覆盖真正的契约/区域问题，不能统一显示“工具协议不完整”。
- 追加额度只改变额度；同输入的无进展记录保留。
- 有新的内容、已执行结果或请求合同发生有意义的变化，才创建新的工作签名；不把错误文案重写当作进展。
- 仅真正的无效协议/无进展操作进入重复失败计数。合法动作等待预算不是模型错误。
- 摘要从当前任务账本生成，明确区分历史快照；避免顶层旧数组与当前 continuation 状态冲突。

受影响位置：`core/visual_design_kit.py`、`core/planning_journal.py` 及其既有状态投影。计费计数和累计 grant 不重置。

## 4. 多视图与几何工具：利用现有能力，不盲目合并

使用现有 owner + parts/crops/candidate_ids 表达一个物体的多个必要视图：

- 一个售卖实例可以有多个展示状态，不为每幅图新造 object_id。
- 必要视图分别给出明确的物理 query/crop；不得将多个操作步骤都压成一个模糊大 query。
- 默认最高分候选只是提案。规划者应能看到需要的候选清单/查看图并选择多个候选；程序不自动将所有候选相并。
- 选择已有候选不需要重新运行 SAM，但改变后的实际保护仍需明确接受。
- 明确工具能力：semantic 用图像 crop 和 query；正负点在此阶段是诊断。interactive delta 才使用点约束。只改诊断点不应被承诺为像素修复。

这些要求进入同一规划合同和工具反馈，不新增视觉审核责任人。不能用“所有正点必须命中”等旧代理规则代替对必要视图的判断。

## 5. 当前三个图位的定向处理

| 图位 | 修复后的处理路线 |

| 棕药柜 scene_04 | 检查已保存 query/区域修改与当前绑定；明确授权采用后继续局部处理。若要利用正负点做真实修正，使用对应 interactive 工具；不能把点移动本身当作修复。保存新结果后由原规划者确认。 |
| 紫树 func | 给规划者完整候选及操作视图信息；优先选用已经返回的第一/第二步等有效候选，缺失部分再按 owned part/view 有界补充。已有提案若不足以落实必要步骤，只请求具体缺项，不能照搬一个笼统 query 后宣称完成。 |

不预先承诺固定 N 次就完成：已有合规提案可能省掉一次重新决策，已有候选可能省掉推理，但后续是否接受仍取决于实际结果。执行前分别列出规划请求、本地 SAM 操作和生图请求的硬上限；遇到未获授权的下一步就保留工作、停止并说明，不自动续费。

## 6. 先写失败行为测试，再修实现

将以下断言合并进现有测试，默认仍不超过 100 例/60 秒：

1. 最后一次调用返回合法区域 patch：提案持久化，不进入假协议错误。
2. 本地执行权限充分而无确认额度：可保存结果并停在待确认，不发额外模型请求。
3. 之后获得一次确认额度：直接确认已有结果，不再购买同一修改决策、不重复 SAM。
4. 连续追加一次额度不清空同输入无进展记录。
5. 请求 schema 与实际执行能力一致，仍拒绝越权/陈旧/重复动作。
6. 中断发生在预留、执行结果落盘、确认回包落盘之间，恢复不重复副作用。
7. 同一 owner 的两个必要视图可选择多个候选；无有效接受不可生成。
8. 普通无关字段修复 + 接受当前 mask 继续一次完成，成功兄弟任务不重审。
9. 当前 73 张候选及其任务/提示/回执绑定保持不变。

定向测试开发，默认生产套件在实施结束时只运行一次。之后先做隔离任务副本验证，再单独授权这三个图位的实测。真实候选仍需 QA/逐图质量检查，不以 ready 或 HTTP 成功代替验收。

## 7. 实施边界

- 不先提高默认预算，不新建 job，不缩减 76 图位。
- 不删除原候选、旧回执或原始回包。
- 不需要重建 73 个已接受角色的内容身份；若任何新合同调整影响旧接受，应先停下出具差异，不能静默改写。
- 同一次改动删除被替代的 can_modify 混用、异常分类和计数清空路径，不能保留第二套兼容调度。
- 实施与离线验证完成前，不直接继续充值试跑。
