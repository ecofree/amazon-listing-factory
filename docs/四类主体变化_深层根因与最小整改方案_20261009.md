# 四类主体变化：深层根因与最小整改方案

日期：2026-10-09。范围：当前 `freeze_4asin_2var_20261002` 中床尾入口、镜柜侧格、仿真树地钉和白色双柜四类问题，共五个角色。本文是核查与方案，尚未实施代码修改。

批准后的实际代码修改、测试及实测进度见：[整改实施与实图复验记录](四类主体变化_整改实施与实图复验_20261009.md)。本文保留审批前的证据与方案。

## 一、结论

四类问题有共同的职责缺口，但不能归结为同一个已证实的生成原因：

1. **规划目标与产品执行状态的边界没有稳定传递。** 买家问题、场景用途、产品排布和真实装配状态混入同一执行语境。
2. **必要的源图结构关系没有完整进入本图的执行状态。** 当前通用保结构要求已经存在；缺的是与当前编辑目标直接相关的入口、储物格、连接和实例归属关系。
3. **现有审查有输入却误判 supported。** 选区正确、目标可执行、最终生成保真是不同判断，不能相互代替。
4. **生图端确有合同不遵从。** 床尾和地钉已经在保护范围内，原生输出仍改结构。修正上游确定缺陷是必要工作，不能宣称它必然解决全部重绘。

双柜有明确的相反指令；床尾、镜柜有同源近对照支持目标语义竞争；地钉已排除大面积漏保护，但具体远端执行原因仍未知。将四类都解释成 SAM 不精确、INT8 权重问题或模型随机，均不符合现有证据。

## 二、床尾被改成入口

### 已确认的链路

- 样例：Natural 床 `B0DSSKTXXW / scene_03 / source_03`。
- 原图入口位于右侧护栏末端，床尾横梁和竖条连续，原图没有人物。
- 观察已经识别右侧入口，规划和最终 prompt 也提到 right rail，并非完全没识别入口。
- `visual_goal` 是“侧入口如何方便进入床”的买家问题。规划规则规定它用于沟通，编译器却直接输出 `Image goal: ...`，没有传递这一语义边界。
- state 主要写高角度展示、右侧入口和三面护栏，没有决定本图的人物动作，也未落实连续床尾与既有入口的关系。
- 新原生图新增女孩从床尾进入，并删除了原床尾部分横梁、竖条；不是仅被人物遮住，也不是放大造成。
- 被删除的床尾上梁三个采样均处于保护 alpha=255。前后源图、原蒙版、provider 和请求模型相同，prompt 差异只有新增目标行；旧图没有床尾新入口，但仍有其它细节偏差，不能称全面成功。

### 深层原因与证据边界

**确定的程序缺口是沟通目标的身份在编译中丢失。** 执行模型可能把“回答如何进入床”扩展成“新增人物进入动作”，再为动作重构产品。该解释与输出及前后差异一致，但各一次输出不能排除随机性，也不能证明目标行是唯一原因。

通用保结构条款原本已经禁止这种修改；输出仍违反合同。不能说程序明确要求删除床尾，也不能说只要再加一句“不要重绘”就一定解决。

### 最小修复

- 替换 main/scene 现有目标投影，明确它承载买家问题、环境与沟通目的；产品状态和人物动作由批准的 state 决定，问题本身不授权新增动作或改变结构。
- 保留目标中的环境用途，避免再次丢失餐厅、厨房等已批准场景。
- 本图的必要 state 应表达：既有右侧固定入口，原床尾及对侧护栏连续；本图没有批准人物进入演示。仍用现有字段，不将“所有产品禁止人物”写成统一规则。
- 人物条款已有 approved state 条件；优先修复目标边界，不重复叠加人物禁令。

可用的状态示例（180 字符，非固定模板）：

> Existing fixed side opening at the right rail end; the original footboard and opposite guardrail remain continuous. Preserve original assembly. No person or movement demonstration.

## 三、镜柜新增层板

### 先明确正确结构

Coffee 镜柜 `B0DCBRXCMG` 的两个出错场景，每侧应为 **三格开放储物空间：两块中间分隔板加底板**。不能修成“三块中间分隔板”，那会再次得到四格。

中央门内四个储物层、三块可调板，以及整件十层的营销计数，属于不同计数对象和区域。实际两张出错请求没有把这些数字传给生图，也没有附带门内四层图，因此没有证据证明“程序把内部四层套到侧边”。

### 已确认的链路

- `scene_02/source_03`、`scene_03/source_04` 的观察主要描述浴室、厨房和摆件，没有记录该场景图的侧边格数。
- planner 输入看得到主参考的侧边三层信息；初始及最终 state 却只描述壁挂、闭镜门和陈设。
- 最终 prompt 有泛化的部件数量、间距、连接保护，未明确侧边三格与两块中间板，也未错误指定四格。
- SAM 原始及实际上传蒙版前后相同，两张没有本轮纠错增删；层板新增已在 native 中。
- scene_02 在原图、上传蒙版、provider、模型相同且仅新增目标行的近对照中，由三格变四格。scene_03 也有此变化，但模型变化，因果判断更弱。
- 同子体其它角色在没有数字 state 时仍保留三格，说明缺少数量文字不是必然失败的充分条件。

### 深层原因与修复

**必要局部拓扑没有被规划压缩进执行状态，陈设目标却被明确执行。** 模型可能为陈设重新分配储物空间；这与结果一致，仍属于有证据的推断。

修复应让陈设适配原有结构：在原 `presentation.state` 中继承本图必要的区域、空间与实体板关系，由原审查核对。不要拼接全量观察或全商品数字，也不要新增镜柜数量正则。

可用示例（166 字符）：

> Wall-mounted cabinet with closed mirror door; each side has 3 open bays, separated by 2 intermediate shelves above the base. Retain their spacing, supports and frame.

金色固定板变色/漏面是并存问题；必要时在本图 state 保留其源材质。镜面反射又存在 mask 保护与文字允许编辑的不一致，应在原 region_intent/review 修正；当前不能把它认定为新增层板的唯一原因。

## 四、地钉比例变化

### 已确认的链路

- 样例：Begonia `B0GG3TVW6R / main / source_00`。
- 原图是两套树冠—主干—圆盘—尖地钉装配，未证明地钉可作为硬地面独立支脚。
- state 混入 `freestanding`、`upright side-by-side` 和 `remove inset`，同时承担安装解释、布局与图形编辑；不符合现有 state 职责。
- 现有审查判 supported，编译器原样投影。最终 prompt 同时要求保留各自原位置、尺度、结构；生成结果未遵守这些要求。
- 圆盘/地钉深色像素固定 ROI 约 99.0%–99.4% 受保护，只有约一像素边界漏保。此数不是全产品 IoU，但足以排除地钉大面积未选。
- 原图上传未变；蒙版 PNG 优化前后 RGBA 完全相同，优化后 SHA 精确匹配上传回执。
- 原生图中地钉高度/圆盘宽度的图像比例由约 1.25–1.27 变为 1.54–1.64，约增加 23%–30%。这是图像比例对比，不是测得的真实物理尺寸。
- 旧主图已经重排两株；因此新增目标行不是这类问题首次发生的原因。前后 provider 也不同，不是单变量因果试验。

### 深层原因与修复

**可以确认状态职责混杂，以及生成执行未保持同一实例内部比例；不能证明 side-by-side 一词直接导致地钉拉长。** 两株平移和地钉相对比例变化也应分别记录：平移违反当前位置合同，但本身不等于零件重绘。

- state 只描述源图已有装配、连接和安装关系；去掉未验证的 freestanding 解释、排位及去 inset 命令。图形编辑回到已有图形/可编辑对象字段。
- 将 main/scene 现有泛化保留段替换为完整实例及其部件相对尺寸、间距、连接、朝向共同保持，删除被替代的重复泛化表达。不增加地钉专属禁令，不将 SAM crop 当作尺寸，不把 size 数值复制到 main。
- 同一次原审查核对布局是否越权成为产品状态、支撑关系是否有证据。
- 本案没有证据支持继续提高 SAM 精度或更换 INT8 权重作为主要修复。

**仍未解决的边界：** 上传文件正确后，远端是否处理蒙版与模型是否不遵守，当前不能区分。现有多个 provider 都通过同一 SubRouter 入口，换标签不能算独立网关验证。清理输入后若仍拉伸，必须保留生成端违约结论，不能继续无限叠加提示词。

## 五、双柜目标矛盾

### 明确的相反指令

- 样例：White 浴柜 `B0H1VZX3WZ / scene_04 / source_05`。
- 原观察明确左、右两柜都是同款销售产品；已确认销售数量为一。
- 规划 targets 只选左柜，SAM 也只保护左柜，右柜属于可编辑区。
- state 却要求与 matching modular cabinet 并置，最终 prompt 同时要求“移除未选同款副本”和“保留配套第二柜”。
- 原生图保留两个同款柜。现有两个审查操作均判 supported。

这是**已证实的规划目标自相矛盾**。机械数量校验只验证选中对象数量，无法由合法的一条 target 证明自由文本没有另留第二柜。该场景不是 SAM 将两柜误合并。

### 最小修复

- planner 和原 product_depiction 审查共同核对：state/goal 明确保留的同产品实例，必须对应 `region_intent.targets[].object_id`。
- 本图保留左柜已有装配及门状态，删除右侧同款柜与未验证的 modular 目标。不同款且有证据归为普通环境家具的柜体仍可保留。
- 用已有 `instance_ownership / presentation.state / revise_plan` 返回矛盾；不新增 excluded_instances 同步字段，不扩大 mask，不把售卖数量改为二，也不因源图有两柜而拒绝源图。

## 六、建议的最小修改边界

修改集中在三个现有生产文件，不新增模块、服务、分割步骤、审查阶段或控制器。

| 文件 | 替换现有职责表述 | 不扩大的边界 |
| --- | --- | --- |
| `core/visual_design_kit.py` | 初始规划及 repair 一致：state 承载本图必要源结构关系；环境/布局/图形不变成产品状态；目标实例对应选中 ID | 继续使用 state≤300 字符；不输出完整零件清单，不新增字段或品类分支 |
| `core/image_prompt_compiler.py` | main/scene 的 goal 恢复沟通上下文身份；替换现有保留段，明确实例内相对关系 | 删除被替代行，不叠加第二套目标/禁令；固定 task 的 func/size、targeted_edit 投影不随此分支修改 |
| `core/visual_semantics.py` | 原 product_depiction 核对实际目标必要关系、计数对象/区域、演示授权及选中实例一致性 | 同一次审查、原 typed finding 与 repair；不新增字符串禁词检测或全局闸门 |

精确位置：planner 当前 1051、1060–1071，repair 743–748；compiler 当前 229、378–384；review 当前 893–913。行号只对应本次核查版本。

这些规则中已有部分存在；本次应合并、替换为具体职责，不能把“已有规则却误通过”处理成再追加一长串同义句。现有语义审查仍可能误判，是否改善必须用固定真实样例验证。

## 七、修订与验收的实际边界

### 不能假设“改 state 后 resume 就行”

当前 ready 合同有缓存和原规划审查绑定。只纠正 compiler、保留已批准 state，可沿现有单图 revise/full_redraw 验证当前结构合同，不需要新 Gemini 规划额度。

真正修改 state 必须形成真实规划修订并通过原审查。当前用户设计输入入口 brand_brief 是家庭 job 级，不支持直接设置单个 child/role 的新 goal/state；不能用 revise reason 偷改设计，不能手工 ready、迁移旧审批、清空预算或假 reobserve。

已核实：实际 planner prompt SHA 进入 input revision，current 检查会用当前模板重新计算。真实修改 planner 的 state/实例规则后，正常运行原 brief 即会产生新规划修订，不需要额外提交 brand_brief，更不需要清预算。共享模板修改会使四家庭八个子体的旧 kit 失效；一次运行某个现有家庭 job，实际重规划粒度是该 job 的两个子体，不能承诺只改一张 ready 图。旧账保留，新合同必须经过原审查；不为刷新预算伪造设计偏好。

[现有入口与预算核查](../test_runs/region_root_causes_20261009/bed/真实goal_state修订入口_只读核查.md)

### 固定样例验证，避免重新扩大测试

1. 在原行为用例中核查目标只出现一次、场景用途保留、state 正确投影、实例不矛盾、func/size 固定 task 输出不变；不增加重复用例。生产 suite 仍遵守 100 例/60 秒上限，实施后最后运行一次。
2. 优先实际验收上述五个角色：床一张、镜柜两张、树一张、双柜一张；固定源图、原始及上传蒙版、请求模型与 provider。规划粒度不等于生图验收范围；不能声称只需五次全部模型调用。
3. 按原生输出检查：床尾与原侧入口、左右三格及固定件、圆盘/地钉相对比例、单柜归属。环境陈设可以变化，不以新风格代替结构验收。
4. 若组合修改成功，只能证明这次组合在固定样例改善，不能分解成某一句的唯一因果。若干净合同仍改变保护部件，记录生成端未遵从，停止扩大冻结试错，再针对剩余执行原因给出结论。
5. 新规划可能改变同子体其它角色合同。不能因 compiler 保持 func/size 分支就宣称整批 func/size 输出一定可复用；是否复用仍按真实合同指纹判断。
