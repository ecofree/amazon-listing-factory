# `--generation-tasks`流程影响复核

## 结论

**不传该参数，当前实现没有给正常生成流程增加新的名单准入条件；显式使用时会增加调试调用的拒绝条件。**

这个参数仅用于限定一次验证调用可执行的当前任务，不解决规划阻塞，也不是新的审批阶段。它不应成为正式生产必填步骤。

但不能宣称“完全没有新增阻塞或误用风险”：实际检查发现校验时机、状态表示、dry-run和空名单语义仍有需要完善的边界。本轮只复核，不修改生产代码。

## 1. 实际调用链

```text
factory.py读取JSON
→ JobRunRequest.generation_tasks
→ 控制器检查：非production，且只能单独运行generate
→ 现有完整图片分支currentness检查
→ 全部名单条目校验
→ 选中任务沿原回执恢复／provider准入／候选提交路径执行
→ 原全范围完成统计
```

入口：`scripts/factory.py:240–246`、`core/production.py:88–89`、`core/image_generation.py:58–104`。

## 2. 哪些行为是不变的

- 不传参数：选择当前RunScope内原本要处理的任务，未增加“先准备名单才能运行”的要求。
- 不修改ImageTask、prompt、source/mask、candidate fingerprint或RunScope库存。
- 已有当前候选仍复用；已有付费响应仍先恢复；未知回执仍须处置。
- 未选角色保留在完整inventory中，不被标成已完成。
- 正式production模式不接受该参数，不能靠它绕过完整家族要求。
- 新增参数不导致JobState升级；本轮协议实施的JobStateV8升级是另外一项变更。两者不能混为同一种阻塞。

## 3. 有意增加的拒绝条件

| 情况 | 当前行为 | 判断 |
| --- | --- | --- |
| JSON文件不存在、格式错误或CLI明确提供空数组 | 拒绝调用 | 合理的输入／限域保护 |
| 名单条目过期、未ready、重复、跨RunScope或含越权字段 | 整次限定调用不发送 | 严格快照策略；会连带取消同名单中的合法项，不是逐项跳过 |
| 与production或`brief,generate`等组合使用 | 拒绝调用 | 合理：禁止把调试过滤变成生产范围变更 |
| 名单内一个角色因合法规划修订换了fingerprint | 需要更新名单 | 合理：旧许可不自动授权新内容 |

因此它会增加**使用限定模式时的输入维护和调用中止机会**，但这不是新增模型审核层。不要通过忽略过期指纹、自动替换任务或静默跳过条目来“减少阻塞”。

## 4. 实现边界和实际风险

### 4.1 名单校验太晚，会把输入错误记成生成阶段失败

控制器先执行`begin_run/start_stage`，之后才进入`select_generation_tasks()`。名单错误会走stage异常路径，写入生成阶段错误及失败摘要。

合成探针：一个合法条目＋一个过期条目，记录到begin_run=1、start_stage=1、add_error=1；不发生provider准入。

这是**运行状态污染／误报风险**，不是已经证明任务永久锁死。应在任何运行状态写入、brand brief改动之前做无副作用名单预检；错误只拒绝该debug调用，不冒充生成模型失败。

### 4.2 单角色过滤并不是完全独立的小任务

`require_current_image_branch()`在名单过滤之前运行，仍检查整体DownloadManifest、FinalSourceIntent、ImageTask和ImagePrompt是否current。

- 其他角色只是合法blocked，不应因此压住已ready角色；这是原有防线。
- 但其他部分造成全分支artifact过期／损坏时，限定单角色仍会被挡住。

这是继承的全分支一致性依赖，不是名单又增加一次审核；不能宣传成“完全不受其他图位影响”。不建议为了绕开它直接调用provider。

### 4.3 限定调用成功与全量完成仍易混淆

- 全范围候选未齐时，summary仍可能是partial_success；这是正确的全量统计。
- 但生成stage可以因本次选中任务无失败而标success。
- `_stage_input_revision('generate')`未包含名单；限定与全量调用使用相同的stage输入版本。run_environment另有名单及其SHA，但stage记录不能单独表达二者差别。

当前生成入口仍遍历当前任务／候选，没有证据证明因此自动跳过未选任务；**外部脚本只看stage success或completed_through_stage却存在误判风险**。

建议增加明确的invocation结果：requested/completed/failed/not_run及selection SHA，和job整体完成结果分开。若区分stage调用身份，仅加入调用级标识，不能改变任务fingerprint导致已付费候选失效。

### 4.4 Python API显式空名单会扩展成全范围

CLI会拒绝`[]`，但底层`if not selection: return scoped`使显式传入`[]`与不传参数相同，都会选择全部scope任务。已用合成数据确认。

这不是阻塞，而是**范围扩大／额外请求风险**。应使用明确的“未提供”值区分正常模式与显式空名单；显式空名单统一拒绝，不得解释成全部。

### 4.5 resume不会自动沿用上次名单

名单是一次调用参数，不是持久化输出scope。下一次调用若忘记参数，会回到RunScope内的正常全范围执行。

建议明确显示此次执行范围；从上次限定验证切换为全量执行时必须有明确的操作意图。不能擅自把上次名单变成永久job过滤，否则会制造另一种“其他角色永远不跑”的问题。

### 4.6 当前dry-run不验证任务名单是否current

控制器在调用实际选择器前就返回dry_run。探针对含过期条目的名单仍得到dry_run结果，任务校验调用数为0。

因此当前dry-run只能说明stage组合可解析，**不能作为名单就绪证明**。建议复用无副作用预检，预览实际选中图位、指纹匹配、恢复／未知状态；绝不调用会改变回执的恢复函数来做预览。

## 5. 推荐处理方式

保留其“有界验证工具”定位，不加入常规生产必经流程。优先补齐：

1. 无副作用预检前移；dry-run使用同一检查。
2. 不传与显式空名单分开，避免空名单变成全量。
3. 区分本次限定调用成功与全job完整性，保留清晰的范围切换提示。
4. 对真实控制器路径补测试：名单错误不写stage失败、限定成功后普通resume不漏掉其他角色、成功候选不重复生成。

名单限制的是**逻辑任务集合**，不是物理请求次数或金额的绝对上限；原路由、已知失败处理和明确授权仍独立约束请求。不能把“选3图位”直接说成“最多3次模型调用”。

## 6. 本轮验证范围

- 只读当前代码，未访问历史jobs。
- 合成任务＋mock持久化探针：默认全范围、混合过期名单拒绝、Python空名单、stage版本相同、阶段失败副作用、dry-run未校验。
- 证据：`test_runs/pi_generation_selection_review_20261010/probe.py`及`results.json`。
- 首轮探针漏mock异常摘要写入，因假的plugin无category_id失败；补齐测试隔离后成功。没有把探针自身错误归为生产缺陷。
- 生产文件新增／删除／修改0/0/0；未运行生产套件、真实模型、QA、上传或回执处置。

**最终判断：默认生产流程不必依赖该参数；限定验证模式确有新增拒绝条件，当前实现也有边界缺口，应完善后再纳入自动化验证脚本，不能承诺零阻塞风险。**
