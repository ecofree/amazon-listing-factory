## 结论先行

不能把这次故障概括为“剩余 170 项需要更多规划额度”。已确认的问题横跨证据身份、候选有效性、规划回执和验收门禁：

1. **766 个复用槽位会被 QA 入口全部静默跳过。** 上次只修了发布读取器，生成、QA、发布三处仍使用不同的候选有效性判断。
2. **旧图复用对当前源证据的检查过宽。** 实验中，把当前观察改为失败、删除对象归属，甚至把当前尺寸从 7.5 ft 改为 8 ft，历史复用判断仍返回 True。没有证据表明 766 张图全部有事实错误；这里确认的是安全边界缺陷。
3. **44 个当前失败草稿，在初始封存证据目录下可以通过同一个现行校验器。** 至少这部分不能归咎于规划器凭空编造 ID；证据目录换版、对象/功能/测量 ID 漂移是直接原因。
4. **“32 项规划回执未知”不是完整影响范围。** 四个子体账本集合实际有 161 笔未决规划请求，其中 98 笔按当前阻塞谓词影响这 170 个槽位中的 121 个。请求数和槽位数不能混算。
5. **19 笔 HTTP 402 明确错误响应被历史分类枚举锁在 unknown。** 同一错误文本，仅把事件类型从旧 `transport_failure` 换为现行 `configuration_failure`，现有结算函数才肯结束等待。不能把历史分类字符串当成请求事实。
6. **当前生产测试准入失败：101 > 100。** 之前 100/100 的结果属于新增回归用例之前，不能代表当前工作区。

正确顺序：**修代码与准入门禁 → 冻结证据目录 → 逐请求处置回执 → 逐槽位修合同/确认 → 复用旧候选 → 唯一 QA → 发布。** 不是加额度后重跑全家族，更不是放宽校验或全量重生。

## 3. 已确认根因与源头修复

### F01｜P1：只修发布读取器，QA 仍然拒收所有复用候选

**代码链：**

- `core/candidate_state.py:287–363`：等价恢复返回原 `task_prompt_fingerprint`，另给出 `reuse_evidence`。
- `core/image_generation.py:228`：生成复用分支考虑当前复用提示词。

- **`core/image_qa.py:58–59`：只接受原 `task_prompt_fingerprint == prompt_sha256`。** 不匹配时既不排入 QA，也不记录失败。

**实证：**

- 全部 766 个旧候选满足发布读取器的当前提示词判定，但不满足 QA 入口条件；新 3 个不受此特定问题影响。
- 使用真实 `B0CH38H17T/main` 的任务、候选和提示词，在隔离环境调用现有 QA 调度函数：`0 个 evaluate、0 个任务、0 个失败`。
- 对照组只把候选提示词字段改为当前值，evaluate 立刻被调用。本实验的 evaluator 故意抛异常防止任何真实 QA 请求。

**真正修复：**

把“经验证候选是否属于当前执行请求”的判定统一在现有 `candidate_state` 权威内；生成、QA、发布消费同一结果。移除三处重复/分叉的提示词比较，不再在发布模块补第三个兼容分支。

原请求指纹、原模型回执不可改写。等价证明必须同时绑定当前 task、当前 prompt、候选 SHA、引用字节与原始请求。判定失败必须产生明确 task failure，不能静默少一项 QA。

**验收：** 766 个旧槽位和新 3 个槽位均能进入 QA 调度；其中每个槽位明确复用当前 QA 证据或实际评估或返回失败。不能直接继承过期 QA/人审批准。

### F02｜P1：历史复用绕开了当前观察语义，存在错误放行风险

**代码：** `core/visual_design_kit.py:660–702`，`core/image_tasks.py:256–268`。

`_role_basis_matches_current()` 检查事实集合、源路径/图片 SHA、共享设计以及“存在一个同源候选”，却不核对当前 observation 的可用性、对象归属、功能事实、测量含义和纠正状态。随后任务形成改用历史 `basis['sources']`。

**反例：**

对真实可复用的 `B0CH38H17T/main`、`size`：

1. 正常输入，返回 True。
2. 内存里把被消费源的 observation 设为 failed、清空 objects，仍 True。
3. size 的当前测量从 `7.5ft / length_mm:2286` 一致地改为 `8ft / length_mm:2438.4`，仍 True。

`_saved_candidate_matches_role()` 也只检查候选文件和保存提示词各自的 SHA，并不证明该候选与此 brief 的实际请求等价。这会让“历史材料可保存”与“当前任务可执行”混在一起。

**事实边界：** 本轮没有发现已 ready 任务直接引用 status=failed 的当前源图；反例证明的是缺陷，而非断言 766 张图都错。

**真正修复：**

- 在现有 `planning_identity` 中统一定义被该角色实际消费的源证据依赖，复用判定使用同一投影。
- 比较内容不仅限于图片 SHA，还要包括观察状态、对象销售归属/实例数量、特征及其拥有者、测量对象/轴/端点/值/单位、有效纠正记录。当前明确纠正不得被历史接受覆盖。
- 显式、可证明的同义 ID 换版只能产生一次可追溯的恢复证据；不能靠名称相似、相同数值或更早 accepted 自动放行。
- “仅复用保存图”的恢复路径必须找到**精确等价且有效的现存候选**；找不到时停在当前权威的明确阻塞状态，不能顺势按旧 basis 再发一次生成。
- 保留旧文件和旧授权作为历史证据；不要为了当前运行伪造新 content_id、accepted 或 QA 通过。

**必须删除的旧行为：** 仅凭同源 SHA/同源候选存在就允许当前执行的分支，以及未证明当前依赖等价就使用历史源目录编译执行任务的分支。不是增加一个“更宽松”的旧版本校验器。

### F03｜P1：源证据换版导致 ID 漂移，规划草稿没有和同一目录一起恢复

**代码：**

- `core/visual_semantics.py:176–230`：观察缓存受整套事实/输入修订影响，object/feature/measurement ID 由观察结果给出。
- `core/visual_design_kit_compiler.py:453–469`：物理证据 ID 包含 `source_id + feature_id + 序号`。
- `core/final_source_intents.py:617`：`source_occurrence` 来自观察的 measurement_id。
- `core/planning_identity.py:38–87`：这些目录进入角色依赖；依赖算法曾变更而 `CONTENT_POLICY` 仍为 `role-content-v1`。
- 前次操作脚本 `test_runs/trees_repair_20261023_01/recover_offline.py:observations()` 逐源选可验证观察；`restore_plans()` 对已有候选做历史恢复，未解决所有 pending 草稿与目录的成套绑定。

**反事实对照：** 44 个当前草稿用当前校验器、初始封存 basis 可通过，换到当前 basis 就失败。不能把这 44 项全部称作模型乱填字段，也不能据此承诺全部可以零调用修好。

实例：

- `B0FNRPVSC1` 的初始对象为 `xmas_tree_01`，当前同 SHA 原图对象为 `tree_01`；8 个非 main 槽位在初始 basis 可通过、当前失败。main 另有真实 1/2 件冲突，不可以用别名修复顺带放行。
- `B0FNRNX1RY/size` 的草稿选 `source_06:height_01/width_01`，当前目录是 `tree_height_180cm/tree_width_100cm`。
- 物理文案如 `physical:source_04:branch_tip_density:0` 依赖 feature_id；观察改名、分组或序号重排都可能破坏绑定。

这些差异有一部分在前次恢复开工快照中已经存在，**不能把所有漂移归责于最近一轮恢复脚本**。已确认的是跨版本、跨观察快照的输入混用。

**真正修复：**

1. 一份原子、不可变的源证据快照同时供规划、修复、区域和任务形成使用。观察 ID 必须有明确快照身份，不能把同名 source_XX 当作永远同一份对象目录。
2. 对事实的本地重核，先判断消费语义是否改变；仅新增不相关事实不应自动重做观察并生成一套新 ID。
3. 真正需要重新观察时生成新的显式修订：旧方案不被悄悄换底，受影响角色进入当前规划器的定向修复。
4. 本地 ID 对应只允许原始证据能证明的一一对应。测量要核对同一对象/端点/轴/单位/值，不能因两个位置都是 6 ft 就合并；功能视图分拆/合并必须让规划器决定。
5. 明确改变内容身份算法的版本，不能一面改变哈希输入，一面仍把同一 policy 标签理解为同一身份合同。历史授权仍封存，不自动迁移。

### F04｜P1：明确拒绝响应被当成丢失回执，现有恢复入口不能远端查回结果

**代码：** `core/planning_journal.py:165–190`，`core/model_call_health.py:244–262`，`scripts/factory.py:468–486`。

账本计数：

| 范围 | 笔数 |
|---|---:|
| 四作业未决规划请求 | 161 |
| 其中 tool_calls / plan | 135 / 26 |
| 按现行阻塞谓词影响本次 blocked 槽位的请求 | 98 |
| 受影响的 blocked 槽位 | 121 |

未决请求的最后事件：91 transport_failure、68 timeout_failure、2 无已保存末次事件。原错误中有 19 条 `HTTP Error 402 ... insufficient_balance`。

现有 `settle_attempt()` 只在事件类型恰为 `configuration_failure` 时识别这类拒绝，历史 `transport_failure` 无法结束等待。离线反例中，同一拒绝仅切换枚举后，unknown→received；两组消费都仍为 1。

19 笔关联 42 个 blocked 槽位，其中 18 个槽位的回执阻塞全部来自这些 402；其他槽位还叠加其他未知请求。**这不是可以直接解锁 42 项的承诺**，字段、额度与接受记录还要分别过关。

`resolve-planning-response --action recover_received` 当前只查本地 `attempts.json`/保存响应，不会向供应商查询原请求。不能给运营一个实际上没有实现的“继续查询即可自动恢复”预期。

**真正修复：**

- 在既有传输/回执职责中保存结构化事实：是否开始提交、HTTP 状态、供应商 request ID、完整/截断响应、响应字节摘要、解析结果、明确拒绝与未知结果。业务 outcome 不依赖易变的异常分类字符串。
- 明确拒绝、收到但 JSON 不合法、内容截断、真正未知必须分开。已发送请求不因失败退款或清零；账本额度也不是供应商美元账单。
- 对这 19 笔只做有证据的显式历史处置，保留原记录及消费，追加理由和证据摘要。不批量改 `unknown` 为 `received`，不把所有 5xx 都认作未执行。
- 对真正未知：优先恢复本地完整字节或供应商原请求回执。供应商不支持查询/幂等时，技术上无法保证安全重发；只能继续封存，或由用户逐请求明确接受重复费用风险并给出有限新请求授权。
- 指定的 21 条未知生图回执继续禁止重发；规划回执处置不能自动授权图像重发。

### F05｜P2：错误归类与额度报告掩盖了叠加阻塞

此外 7 项在当前目录下已无字段错误，却仍携带保存目录的旧诊断：

- `B0CH394T82/func`、`func_02`、`func_03`、`size`
- `B0CLP674GV/func_04`
- `B0CKDZ9SQ8/func_02`、`func_03`

**修复：** 让既有状态/诊断输出独立列出字段错误、源缺口、未决 request IDs、当前确认状态、子体余量和下一步；不要靠 `formation_reason` 文本作互斥根因分类。额度估算以明确 child/role 工作集合、可发送批次、确认步骤和字节预算为基础，绝不重置消费或无进展计数。新增授权也不应让任意兄弟角色抢先消费。
