## 1. 总体流程

唯一命令入口为 `scripts/factory.py`；唯一生产控制器为 `core/production.py`。完整执行、指定阶段和恢复执行共用相同阶段处理函数。

控制器顺序仍为：

```text
创建任务
  → fetch：抓取家庭与各子体事实
  → copy：生成 Listing 文案
  → download：下载源图
  → classify：图库联合观察、源图分类、外观选择
  → brief：固定图位 → 子体整套视觉规划 ↔ SAM 分割工具
           → 规划者确认 → 确定性任务/提示词编译
  → generate：模型编辑 → 回执保存 → 原生图校验/尺寸处理 → 候选提交
  → qa：实际生成像素的硬事实检查
  → 现有人工审核命令
  → publish：发布已批准图片并生成可访问 URL
  → template：编译父子体字段并写 Amazon 模板
```

`copy` 在命令顺序上先于 `download`，但文案和图片是两个依赖分支：文案的任务级失败不再让可用图片工作作废；完整可提交模板最终仍要同时满足两支的要求。当前控制器没有把这两个阶段改为同时运行。

用户指定“只到生图”的冻结测试，在 `generate` 后结束。人工看图记录、候选生成成功、正式 QA、人工批准、URL 发布和模板可提交分别有各自证据。

## 3. 源图分类和最终图位如何形成

当前分类按原图的主要表达用途决定，而不是仅看是否有房间、是否开门或是否出现数字：

- `scene`：主要展示日常使用或空间。开门柜体展示收纳，也可以属于场景。
- `func`：主要说明功能、安装、部件或操作。安装细节包含墙面，也可以属于功能图。
- `size`：主要回答尺寸/适配问题。容量或操作说明中的数量不会自动把图分为尺寸图。
- 完整外观图是供主图与整体设计使用的证据选择，和原图用途分别登记；尺寸页中的可靠产品照片也可以提供外观证据。

首次形成图位库存时：

1. 用已选完整外观证据建立 `main`。
2. 对可用 scene/func 源图登记 `scene`、`scene_02`……及 `func`、`func_02`……。
3. 选择一张主要 size 输出，其余测量图保留为证据。
4. 缺少某个基本类型时仍登记缺项，不通过删除该图位缩小完成分母。
5. 已有库存恢复时沿用身份，不因源图修复自动重编号、改锚点或删图位。

所以当前生产不是每个子体固定只生成 `main + scene`。图量来自完整库存，并在 brief、generate 和汇总中保留。

## 4. brief 内部的完整逻辑

### 4.1 一次子体整体规划

规划者收到商品事实、可用源图证据、固定库存、有效品牌 brief、类目政策（包括 visual_context/role_visual_direction）和授权设计资料。品牌/有效设计输入变化使受影响的旧规划、任务和提示词失效，并由同一规划者在原预算内真正重新规划共享方向，不能重新盖章旧 art 或重置预算。它输出该子体的共享视觉方向及全部图位草稿：

- 机位/照明、背景/场景、床品或其它允许更换的陈列；
- 目标产品状态、必要人物动作、操作展示及必须可见的关系；
- 功能图的准确文字及文字对应的目标；
- 选择哪些已观察的测量 ID，并保留测量对象和端点含义；
- 哪张源图是实际编辑底图、辅助图仅用于哪些证据；
- 哪些物理实例和部件需要保护；
- 对所用证据明确给出 supported 或 unresolved。

这里的 supported 是规划者的证据判断，不等于生成结果已经通过质量验收。没有另一个前置文案裁判、描绘裁判或共享风格裁判重复审批同一计划。

### 4.2 SAM 在原 brief 中作为本地工具执行

SAM 3.1 根据当前第一编辑底图、目标实例、query/crop 和部件定义生成候选蒙版。每个分割单元先选择最高分的非空结果作为提案，规划者继续看到原图、合成蒙版、候选和局部放大。

- 初始 semantic 分割使用 query/crop；正负点在这个模式下是诊断，不是额外输入语义开关。
- 局部 interactive delta 实际使用正负点，执行明确的增加保护或删除误选。
- 同一实物的多个视图、步骤和放大细节归属于同一个 owner，不自动算成多个售卖实例。
- 可以显式选择同一 owner 下多个已有候选，无需再次推理；程序不会自动把全部候选并起来。
- SAM 继续保存原图同尺寸 RGBA 保护区。生图提交时由现有引用模块将其 alpha 转成不透明 RGB 黑白分区图：白色请求保留商品，黑色只允许合同已授权的修改。分区图作为最后一张普通图片附件提交（只有原图时即第二张），不再提交独立 `mask` 参数；原有商品、尺寸、设计附件编号不变。请求记录保存原蒙版哈希与实际附件哈希、尺寸和顺序。它是模型指导，不是像素锁定；漏选不授权改变商品结构。
- 各品类沿用同一观察和规划责任：区分整件、局部视图、材质样本及其归属；整件/包装数量不能要求补全局部构件。保留选定视图的可见范围与连接关系，文字在可编辑空间内换行或缩小，不为排版挪动商品。局部修复仍以当前候选为第一附件，不把原图坐标下的分区图套到已变化的候选上。
- 蒙版提供区域引导，最终仍由图片模型执行保留产品的合同。蒙版不保证保护像素一定不变化。

该工具位于已有 `brief` 内，用户不需要逐图涂蒙版或增加一个独立分割阶段。

### 4.3 只针对未完成图位的结构化工作

规划工具请求区分四种工作：

| 工作 | 规划者当前要解决的事 |
|---|---|
| `create_draft` | 补齐该图位完整草稿 |
| `repair_contract` | 修改程序定位出的具体合同字段 |
| `decide_region` | 对当前分割提案作接受、选择或局部修改决定 |
| `confirm_region` | 对已改变的真实内容作确认 |

响应动作使用 `supply_plan / patch_plan / accept / change_region / blocked`。请求携带该角色实际可写字段、schema 和 source/object/feature/measurement/candidate ID，不依赖模型记得上次对话。

每批至多 5 个角色。同批有效角色立即保存；遗漏或错误只保留在对应角色，不让其它接受结果一起丢失。同内容同协议问题连续两次无进展时停止该工作，保留具体原因。

默认每 child 的初始规划额度为 4 个物理请求，工具工作额度为 4 个物理请求；这是恢复上限，不是每次必发 8 次。每角色最多一次区域修改，修改后需要确认新内容。改变提示词或内容版本不重置额度。

### 4.4 最新的待执行动作修复

`planning-work-v3` 把三项能力分开：允许提出修改、允许执行本地修改、剩余多少确认请求。

因此最后一次模型请求仍可给出合法修改提案。程序先保存提案和前置内容，在本地修改次数允许时执行、保存结果，等待确认；缺确认额度时不会丢弃工作，也不会偷偷发下一次请求。

恢复时先处理已保存响应和待执行动作，再考虑新模型请求。操作使用副本，结果持久化后才替换草稿。资源等待不会覆写已提交内容。

规划状态分别保留：`phase` 是当前阶段，`issue` 是真正根因，`pause` 是预算、资源或授权原因。这样“缺额度”不会掩盖“缺视图/协议错误”等具体问题。

### 4.5 确认后编译任务和提示词

程序把接受后的计划编译为 ImageTask，检查事实、来源、目标、文字、测量、实例和蒙版绑定。随后编译最终提示词，不再调用模型设计第二遍。

提示词固定由 `[ROLE] / [REFERENCE] / [STYLE] / [TEXT] / [OUTPUT]` 构成，硬长度上限为 8,000 字符。角色状态/动作、产品保留范围、源图权限、样式和授权文字来自当前任务。

- 第一附件是实际编辑底图，辅助图证明事实/尺寸，不能授权重建另一套产品几何。
- main/scene 不额外授权营销文案；显式空文案声明在草稿和编译结果中原样保留。
- func/size 仅输出授权字符串和被选择的测量，其他源营销文字要移除或替换。
- 未授权标题或正文时，不额外投影对应排版要求。
- func/size 仍为参考图编辑任务。

## 5. 生图执行、资源和回执

当前注册启用的图片供应商组为 CXK、ModelShare、bilinkai-fixed，各有四个模型。它们的启用配置不等于本次核查已经完成实时连通性测试。

| 图类/用途 | 当前配置的模型安排 |
|---|---|
| main、scene | `gpt-image-2.5`、`gpt-image-2.5-flare`；sunburst 也允许参与 |
| func、size | 正常路线为 `gpt-image-2.5-sunburst` |
| 候补 | 三组的 `gpt-image-2` 均标记为 fallback-only，不把正常空闲工作优先派给它 |

路由先检查能力、角色、配置和健康状态，再按资源组已分配负载/容量选择模型。全局配置的图片供应商并行上限为 4，实际并行还受本机内存、供应商容量、GPU 和当前队列限制。

执行顺序为：

1. 核对任务、提示词、源图和蒙版 SHA；当前有效候选直接复用。
2. 检查原生响应是否已经保存；存在可恢复结果时先本地完成。
3. 没有可恢复结果且获得准入时，发送真实图片编辑请求，底图/蒙版同步处理尺寸。
4. 保存提交记录、原始响应和结果来源，先保留付费返回的证据。
5. 检查原生图：可解码、非空、非纯色/全透明、正方形、1024–4096 像素及字节上限。
6. 小于发布尺寸的合法原生图默认用官方 RealESRNet x4plus 权重，经既有 NCNN 超分环节放大至发布尺寸；本机固定 NCNN GPU 1（NVIDIA RTX 2060）、tile 256、线程 1:1:1，与 SAM 共用排他 GPU 锁。已足尺寸图片保留或缩小，不做无必要的模型放大。只有确认选定候选存在超分伪影时，才用 `revise --mode publication_reprocess --upscale-artifact-confirmed --candidate-sha256 <SHA> --reason <伪影说明>` 对保存的原生响应执行 Lanczos 兜底，创建新的不可变候选；缺模型、GPU 故障、超时或解码错误不会触发兜底。该确认由操作者作出，不是自动伪影检测或批准；不发送新的图片请求、不继承旧审批。
7. 先写 CandidateManifest，再原子发布候选文件；核对最终 SHA。QA、发布和模板引用同一份最终候选。

远程请求线程与本地回执完成线程分开。等待本地内存/GPU的已返回图片不会再进入远程提交队列。一个图位完成即保存，不必等全批完成才提交。

当前未知远程结果默认不自动重发；按具体回执处置和已授权替代继续，整条替代链上限为 3。共享网关发生连续传输故障时执行冷却，避免只换模型别名就反复撞同一故障。

## 6. QA、人工审核、发布和模板的关系

QA 检查实际生成像素。它不以“规划已 accept”或“mask 已上传”代替主体保真观察，也不自动进入修图循环。

人工逐图确认采用同显示尺度下的人眼大体一致：产品类型、数量、结构、连接、颜色/材质身份、尺寸端点和文案归属必须正确。单独的重采样、轻微边缘柔化、光照及细纹差异可接受，不要求像素相同；明显结构、比例或商品表面材质改变仍需处理。不新增相似度阈值、QA 模型或自动重试。床架关注栏杆/板条/入口，柜类关注门覆盖/层板/脚垫/安装关系，树类关注实例/枝叶主体/地钉及地面关系；共用规则不等于其它品类已经通过实图验收。

- `pass`：当前观察覆盖了要求，未发现硬事实矛盾。
- `fail`：有明确事实或发布要求矛盾，不能通过人工简单批准绕过。
- `inconclusive`：证据不完整/观察不可用，需要定位复核和对应处置。

人工审核负责审美、重复卖点/重复场景、引线可读性及尚未明确的细节；记录绑定具体候选 SHA 和 QA 指纹。换候选后旧批准失效。

publish 可以发布当前批准的行并记录部分结果；完整可提交模板仍要求完整家庭、必需图位和可访问图片 URL，以及当前 Copy 与卖家必填字段。模板字段/下拉问题在 template 阶段由同一字段计划处理，不提前挡住图片规划。

最终 XLSM 是可上传文件。当前流程没有把模板写出或 R2 发布称为 Amazon/Seller Central 已接收。

## 7. 最近改造为什么会改善运行

| 近期内部变化 | 对运行的具体影响 |
|---|---|
| 删除独立前置文案/描绘/风格审查及自动返回 classify 的循环 | 避免多套责任方重复裁决、互相推翻和大量重复视觉调用 |
| 图库联合观察，保留合法源行；必要缺项才补观察/OCR | 不为每张源图反复重新购买相同证据；局部失败不抹掉整套取证 |
| 角色级 schema、字段补丁及同批独立结算 | 一条非法字段或漏角色不再让其它合法 brief 全部丢失 |
| SAM 只依赖必要来源/owner/几何，普通文案错误独立修复 | 可先得到真实蒙版；不会让墙色 ID 或普通排版缺项挡住本地工具 |
| 接受内容、物理请求和额度身份分开 | 无关文件/字段变化不撤销成功兄弟图位；真正消费的依赖变化仍正确失效 |
| 保留 main/scene 显式空文案表示 | 草稿接受与编译重建保持一致，修复“已 accept 却被误报没有接受”的交接错误 |
| 保存有效修改提案后执行；最后一次请求可产出本地工作 | 不因缺后续确认额度而先丢弃修改，也不重新购买已有决定 |
| 请求、SAM 动作和生图响应均可持久恢复 | 中断/资源等待后续做本地工作；减少重复分割和重复付费提交 |
| 文案/图片依赖分支分开，模板校验归位 | 文案任务级失败或 XLSM 问题不会提前丢掉可用图片产物 |
| 模型负载分配、共享网关冷却与本地完成队列分开 | 能利用多个已配置模型，同时控制共享故障和本机资源争用 |

这些是从当前代码能确认的变化。没有同一批输入的前后耗时/token对照，本文不报告具体提速比例或固定调用次数保证。

## 8. 未完成工作如何继续

| 当前情况 | 现有恢复方向 |
|---|---|
| 商品事实或源图证据缺失 | 修复对应 fetch/classify 证据，保留其它图位 |
| 草稿某个字段不合合同 | brief 针对该角色具体字段工作 |
| SAM 等待资源 | 保留草稿/提案，恢复本地工具，不购买同一决策 |
| 修改已完成，等待确认 | 确认当前新内容；预算缺项保留实际阶段和具体根因 |
| 已有当前有效候选 | 按候选清单复用，不重新生图 |
| 远程响应已落盘，候选未提交 | 从响应恢复并本地完成校验/尺寸处理/提交 |
| 远程结果未知 | 查看对应回执，按已有授权处置；状态本身不证明成功或失败 |
| QA/人工审核不通过 | 根据定位修改现有计划或使用现有 revise 命令；重检新候选 |
| 部分发布/模板未就绪 | 继续缺失 URL/必需图位/文案或字段，不把部分结果标为完整家庭 |

正常新任务使用现有 `run`。`--generation-tasks` 只用于 generate-only 调试授权，不缩减源图/图位库存，也不补救规划缺项；回到此前明确限定之外的全部生成范围使用现有 `--all-generation-tasks`。

```powershell
# 新调试任务按固定的两个子体运行至生图；<job> 和子体为实际值。
& 'D:\anaconda\python.exe' -X utf8 scripts/factory.py run --job '<job>' --children '<child1>,<child2>' --stages fetch,copy,download,classify,brief,generate

# 相同任务继续未完成的 brief 和 generate。
& 'D:\anaconda\python.exe' -X utf8 scripts/factory.py run --job '<job>' --stages brief,generate --resume

# 查看现有状态和汇总。
& 'D:\anaconda\python.exe' -X utf8 scripts/factory.py status --job '<job>'
```

历史任务涉及退休协议时，先按已有显式维护工具证明/安装等价元数据；不能只改版本号或另开任务规避未处理的付费回执。
