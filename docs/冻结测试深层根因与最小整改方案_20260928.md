# 冻结测试深层根因与最小整改方案

日期：2026-09-28。状态：方案，尚未实施生产修改或发起付费测试。

## 1. 结论：要修的是决策边界和验证方式

这次不能把问题统一归结为“模型不行”，也不能断言“全部是某一句提示词导致”。证据支持三个层次：

1. **已确认的输入设计问题**：同一张图存在多个场景决定来源；目标可以要求首图不适合表达的关系；辅助图与首图的作用只有文字区分，不能视为模型已可靠遵守。
2. **已确认的执行残余问题**：只有一张参考图、提示词已经要求保留连接，仍然出现局部连接重绘。消除冲突是必要修复，但不是产品像素锁定机制。
3. **已确认的验证问题**：旧规划套上新合同，绕过正常规划和生成执行链，再把文件生成成功写成画质通过。由此得出的“修改已经全面有效”不可靠。

推荐整改：**删除重复的场景决定来源；在既有规划及审查中把每张图绑定到实际编辑底图；让摄影图执行明确的环境修改，而不重复接受抽象卖点对产品的改造要求；通过既有生成与修订入口验证实际结果。**

不能承诺任何提示词使模型永不重绘。本方案给出可直接修复的代码缺陷、必须实测的假设及明确停止条件；不把尚未证明的办法包装成最终保证。

## 2. 问题重新归类

| 项目 | 事实 | 当前能确定的程度 | 不应采取的处理 |

## 3. 当前链路及深层原因

### 3.1 场景决定权分散，审查并不能可靠消解这些冲突

当前调用关系：

`visual_design_kit_prompt → compile_visual_design_kit_response → design_binding_request / review_planning_bindings → build_image_tasks → compile_task_prompt → generate`

实际生图同时收到：

- `image_direction.visual_goal`：本图目的，旧数据中还包含具体房间。
- `image_direction.presentation.state`：产品状态和具体使用环境。
- `family_art_direction.environment_and_staging`：整套共享环境，旧数据中也包含具体房间和道具。
- 类目 `allowed_internal_props`、`replaceable_staging`：泛化的道具许可和可替换范围。
- 共享摄影描述：旧数据中还重复定义产品木纹／饰面。

黑柜实际 goal 要 kitchen/dining，共享环境却要 bathroom/grooming；state 写 tiled wall，组件又指定 painted drywall。把这些原样发送，不构成一个无歧义的执行任务。

**新发现：现在的规划提示词已经写了“具体房间属于 presentation.state”“共享环境不能写固定房间”。因此再把同一句要求追加一遍没有实质价值。** 本次旧任务没有重新规划，这条新规则从未在此次样本上执行。

进一步核查发现，`factual_shared_finding` 只接受带产品事实证据 ID 的共享方向反例；`_planning_review_rows` 会过滤不符合条件的 finding，并从剩余 findings 重算状态。厨房与浴室可能都适用同一柜子，它们之间的任务指令冲突不必然是产品事实矛盾，不能指望这个事实审查器充当通用设计冲突裁判。

已用当前真实解析函数进行一次离线诊断：模拟 product_depiction=supported、shared_design:environment_and_staging=contradiction 且无产品事实 ID 的返回。实际结果为冲突 finding 被过滤、总体变成 supported、errors 为空。这是对解析规则的可复现证明，不是对上次未运行的规划审查伪造历史回执；没有调用模型。

**整改应从源头减少场景决定来源，不能放宽事实审查让它开始审核风格喜好。**

### 3.2 选到了来源图片，不等于目标能够在首图中实现

`resolve_edit_references` 把 `product_sources[0]` 转成第一张编辑底图，其余全部作为产品证据附上。校验确保 ID、所属子体、哈希及列表有效，但不能证明底图视角适合当前表达目标。

`_image_direction` 对整件图的完整性检查是“列表中任意图片存在 whole_view”，并没有由此证明第一张本身就适合直接编辑出整件。这个缺口不等于白床此次错误的唯一原因，但属于相同的权限问题：其它图能证明产品事实，不等于授权重建首图没有展示的视角。

规划模型实际只看一张外观原图，其余来源主要以观察目录提供；现有规划审查则能看到实际选中的原图及附件顺序。**应利用已有审查核对首图与目标，不要求规划模型仅凭一张外观图就准确推知所有机位，也不增加第二轮规划或把所有原图一股脑塞入规划。**

白床当前首图展示的近侧是完整长护栏，而目标强调入口。合理处理是使用当前视角能回答的问题，或由已有规划选择真正适合入口展示的原图；不能让生图模型为了卖点自己换面、缩栏。

### 3.3 通用保真声明没有把“理解结构”和“输出不重绘”变成同一件事

原木床实际只有 `source_00` 一张附件，已要求保持 geometry、joins、part count，仍出现连接变化。这排除了“所有错误都因多图”的解释，也证明提示词出现保真词汇不是验收条件。

可见产品的数量、连接、材质必须来自原图和已核实事实；规划可以选择展示什么、改变什么非销售物品，不能再根据“更安全、更方便、更清晰”等目标创造新的产品结构。

原木床的旧摄影描述还写了 natural pine grain / satin finish；state 写了 6-inch mattress。这说明旧规划中混有产品外观重述和具体道具规格。**现有证据不足以证明它们导致本次连接条错误，也不足以说 6-inch 一定是凭空产生。** 可以确定的是：这类非必要数字／产品饰面重述不应成为摄影图重新构造产品的第二依据。

### 3.4 测试与实际生产不一致，掩盖了修复是否生效

本次 `compile_freeze.py` 复制旧 ImageTask，更新 policy、合同及指纹；旧规划仍在。`generate_freeze.py` 直接调用供应商重试函数并复制结果，未经过完整生成执行器。

`finalize_freeze.py` 给每个成功文件统一填写“主要结构通过”，断言只涉及文件与哈希。错误发生在人工判断和报告形成，不能据此说正式 QA 已经误判，因为本次没有运行正式 QA。

还有一处测试盲点：`tests/test_image_branch_v1.py` 的厨房用例先手工把共享环境改为中性内容，再验证厨房保留。这个用例测试了已协调的输入，没有复现这次“厨房目标＋浴室共享方向”的真实失败条件。

## 4. 推荐实施方案

### A. 收回重复的场景决定权：删除一项旧字段，不增加字段

**推荐删除 `family_art_direction.environment_and_staging` 的生产合同字段及全部读写、投影和旧测试依赖。** 不保留兼容读取或默认空值旁路。

理由：它曾承担整套氛围，但具体房间又由 state 决定，现有校验无法确定两段自然语言永不越界。继续同时执行，仍会把冲突交给生图模型裁决。

替代安排使用现有字段：

- 每图的房间用途、非销售物品安排及简短环境风格，由 Gemini 在 `presentation.state` 中一次定好。
- 成套色彩／材质仍由 `palette_direction` 和 `presentation.components` 负责。
- 成套摄影质量由 `photography_direction` 负责，不能指定新的产品纹理或饰面。
- 文案、测量、字体、图形仍由各自现有字段负责。

这样删除一个重复权威，保留成套设计能力，不增加模型调用。规划模型在原本那次成套规划中保证风格一致。

涉及：`visual_design_kit.py`、`visual_design_kit_compiler.py`、`image_task_inputs.py`、`image_prompt_compiler.py`，以及实际引用该字段的现有测试夹具。

同时把类目道具条目的语义明确为“可替换范围／可选许可”，不能编译成当前图必须摆放的物品清单。黑柜 manifest 中“必须镜子、洗手台”的泛化要求，应改为以该子体支持的安装和用途为条件；保留浴室作为建议，不让建议否决已证实的厨房用途。只改这个已发现矛盾的类目条目，不扩大全品类配置重构。

### B. main / scene 的执行提示只表达实际修改，不再复述抽象卖点目标

保留 `visual_goal` 供现有成套规划、角色分配和规划核查使用；**main / scene 的最终生图提示不再输出独立的 `Image goal` 段**。这条投影应实际删除，不能在后面再加一句“忽略冲突”。

摄影图的执行输入保留：

1. 实际首张编辑图片与产品身份、销售数量。
2. 保留该图可见产品结构、机位、颜色材质的现有边界。
3. 经过底图核对的 `presentation.state`，只列必要的展示状态与环境修改。
4. 该图选中的非产品组件设计。

功能／尺寸图不能直接照搬此精简：其功能目标、授权文案、测量主体和端点仍需执行。保持现有角色差异，不新建摄影专用管线。

这不是取消卖点规划。卖点仍影响选图和场景，但必须先转成底图能够完成的编辑任务，再交给生图模型，不能让模型二次解释为修改产品。

### C. 在已有规划审查里核对实际首图，不增加新的审查阶段

修改已有 `product_depiction` 检查的范围及提示：

- main / scene 的产品视图关系也纳入原有同一次审查，不再只因是否存在销售数量 claim 决定是否检查。
- 按 `execution_inputs` 的真实顺序确定编辑底图，不能只证明“参考图中某一张支持”。
- 核对当前目标是否需要改变首图的可见结构、安装面、固定入口或机位；核对辅助图是否在补充必要事实。
- whole_product 应由第一张支持整件直接编辑；辅助全景不能授权从第一张局部图重建整件。由现有 brief 修订选择已有合适底图或修订非必要目标，不靠重排附件的静默后处理。
- 没有额外辅助图、没有蒙版、看不到与当前任务无关的连接，不构成失败。
- 正常替换床品、摆件、房间及有证据支持的销售数量纠正继续允许；不把源图数量机械当成输出销售数量。

使用当前 `product_depiction`、`revise_plan` 和现有局部 brief 修订预算，不增加新的状态、必填审核表、重试轮数或人工确认。仅对具体冲突修订当前 brief，不连带重跑其它变体。

**不建议在编译器加厨房／浴室关键词黑名单、凭文字自动交换参考图，或给每一根护栏创建新字段。** 这些处理难以跨类目复用，也会带来误阻断。

### D. 主体保护采用统一原则，局部失败按现有修订处理

跨类目统一保护的是“销售产品的可见实体及其关系”：床的梁／栏杆／连接，柜的门面／格子／合页，树的枝干／叶形／盆，镜柜的框体／镜面材质。可更改对象由实际销售归属确定，不按“木头全保护、植物全替换”等颜色或材质口诀处理。

对于原木床连接错误：

- 不把所有 `Observed physical_facts` 重新灌回摄影提示，避免恢复已删除的冗长文字重建路径。
- 如果表达某一连接确属当前画面必要条件，利用已有 `presentation.state` 引用经过核实的可见关系；不能由程序生成未经核实的螺钉数或连接方式。
- 优先验证 A—C 后的一次正常编辑。若仍有局部连接错误，使用已有 `revise_image_candidate` 的 targeted_edit，将原图作为结构证据，修正候选的具体部位，保存修改前后结果。
- 对白床整幅改机位、护栏范围改变，不把它假装成一个小范围修补。先修正规划，再从正确底图执行正常生成。
- 局部修订是现有的失败处理能力，不变成每张图必经第二次生图。只到生图的实验仍由逐图人工复核发现问题，不暗中启用正式 QA。

**限制明确：局部编辑本身也需要实图验证。若相同连接错误持续出现，不能宣称已经解决，更不能无限叠加提示词、自动换模型刷到一张看似成功。**

### E. 把验证接回现有生产入口，撤销测试里的虚假通过逻辑

- 新测试任务沿用同一组来源素材和 ASIN，正常建立当前事实／观察、当前规划及对应任务，不升级复制旧 ImageTask 冒充新规划。
- 生产验证使用 `scripts/factory.py` / `core/production.py` 的现有阶段入口，到 generate 停止；使用既有生成执行器、路由、回执和候选保存。
- 受控提示词实验可以使用隔离的研究样本，但报告必须写“实验”，不能用它证明完整生产链通过。
- 旧 `finalize_freeze.py` 的统一通过赋值删除／退役；报告展示只读取明确逐图记录。文件成功不能自动填写视觉通过。
- 同一回执 ID 去重统计，未知原请求与替代请求分开描述。替代请求失败不等于原请求已查明；直接复用当前回执机制，不为测试复制第二份可变状态。

这些是修复测试方法，不新增生产环节；原始失败图和旧报告作为证据保留。

预计修改约 7 个生产 Python 文件及 1 个已证实矛盾的类目配置；最终范围以实施时实际调用确认，不新建生产模块，不修改供应商传输／并发调度／事实优先级控制器。

更新受影响的既有 schema／policy／fingerprint，当前任务通过现有失效重建机制重新规划；不兼容读旧字段、不批量迁移或清扫历史 jobs、不整批强制重跑无关产品。

## 6. 有界实验与验收

### 6.1 先做离线验证，不能把错误留给付费生图

在现有测试方法中替换／合并以下行为断言：

1. 房间用途只有本图 state 一处执行权；成套 palette 和字体仍正常投影。
2. main / scene 不输出抽象卖点段；func / size 仍有必要目标、文字及测量端点约束。
3. 首图为局部、辅助图为全景时，不把“列表中存在全景”当成可直接生成完整产品；通过原有修订纠正选择。
4. 辅助图不能改变首图机位；targeted_edit 第一张仍是候选图，不能破坏现有修订链。
5. 不因没有蒙版、没有额外视角、正常床品变化或局部未知而新增阻断；错误只归属具体任务。
6. 厨房和浴室各自有证据时均可用，棕柜合法浴室不应被黑柜问题连带否决。

定向运行现有 `tests.test_image_branch_v1` 与 `tests.test_visual_design_remediation`；生产套件最后只运行一次 `D:\anaconda\python.exe scripts/run_production_tests.py`，保持不超过 100 例、60 秒。不新增重复测试堆数量。

### 6.2 实验先回答因果问题，最多 12 次诊断生图

## 7. 如何避免新流程和新阻塞

- 不增加分割模型、蒙版制作、逐图手填表或新 API 依赖。
- 不增加规划次数、审核阶段、QA 阶段、重试预算或第二套图像控制器。
- 以删除重复字段／投影为主，规划问题用现有 brief 修订解决，实际局部失败使用现有 candidate 修订。
- 不要求证明隐藏面，不因缺少非必要辅助图失败，不以风格偏好否决事实正确的图片。
- 不把一个角色的问题扩大到全部变体；不改销售事实优先级和已验证的数量判断。
- 无法在证据允许范围完成的特定产品表达，仍按现有失败边界处理。这里不能承诺“所有错误都无条件继续”，否则只是把阻塞换成错误产品图。

**实施完成的判据：不是代码通过或提示词变短，而是当前正常链产生了无冲突的任务，实际图片保留关键产品关系、完成预期编辑，失败记录没有被隐藏。**
