## 三、SAM 与请求链究竟验证了什么

### 1. 白玫瑰候选选择缺陷确已修复

真实规划器收到全部 7 个候选及候选拼图，选择两侧树体和完整地钉候选，再确认实际新组合。两侧原完整杆盘候选的保护交集分别从 4,288/7,767、4,372/7,891 到完整候选覆盖；组合净新增保护 6,998 像素、移除 255 像素。

这是“已有合适候选能够被看见、选择并确认”的真实证据，不是人工边界全覆盖证明。输出的放大窗位于新图形区域，源图地钉被保护也不会自动锁住这个由模型重新画出的放大副本。

### 2. 白柜已正确换底图，但细部漏选仍存在

实际第一附件为 source_01 单柜，SHA `4f70c4f6d9eae6500f429ac9254f37663164a3f7aad57a82510da1389d6f77ba`。区域底图、源文件、上传第一附件和蒙版均绑定同图。

脚垫在原图明确可见。两个独立核对点 `(580,1358)`、`(980,1404)` 的实际 API mask alpha 均为 0，局部蒙版图也显示底部漏保护。新图的白色脚块在模型原生输出中已经出现。这解释了为什么“主柜选中”仍不能推导出“小型售卖结构全部保住”。

### 3. 客户端上传正确，不能替网关和模型作保证

三张首图的原始 SHA 与实际发送 SHA 一致；蒙版上传时仅 PNG 重编码，已本地复现发送 SHA，RGBA 与 alpha 逐像素相同。没有发现客户端错传源图、错绑蒙版或将蒙版当普通参考图的证据。

这些证据不能观察网关内部如何传给真实后端，也不能证明后端完全遵循蒙版。当前不把残留重绘归罪于一个尚未被证实的网关或量化问题。

### 4. 纠正本轮对照器的一次错误

初版隔离对照器误将 manifest.source_path（角色最初分类源，双柜）当作实际编辑底图。真实生成早已使用 generation_references[0] 的单柜。已按 HTTP 第一附件 SHA 修正对照器，并保存错误索引和更正记录。该问题没有改变真实请求、生产代码、候选或批准。

## 四、剩余问题的最小处理方向

以下是依据本轮证据的下一步处理范围，本次没有追加模型调用或生产改动。

1. **白柜脚垫**：在现有 region_intent 和现成候选决策内检查“柜体下方真实支撑件”，先确认是否已有可选脚垫候选，再决定既有局部修正；不要泛化为要求所有产品百分百分割，也不要直接重生同一请求。最终仍按整图验证脚垫的形状、颜色和连接。
2. **功能放大窗**：原物体与它的新放大副本不是同一组受 mask 约束的像素。沿现有唯一规划器明确本图是否需要新副本、引用哪个已见局部及其可见范围；已有两棵树完整展示安装件时，可以选择直接在现有硬件旁标注，避免凭空再造一个副本。不能全局禁用功能窗或用局部数量代替整件数量。
3. **玫瑰场景状态**：让当前 presentation.state 只描述当前裸露杆盘连接和展示状态，将未来户外用途留在事实用途里，保持 graphic_canvas 的明确目标。现有 localized soil 语句仅适用于真的要求安装演示的图；本图没有该动作。不能声称去掉一个词就一定解决全部重绘。
4. **白床引线**：在原规划中选择清楚的标签呈现方式。近邻独立功能窗可用无引线标签；确有必要时才让引线指向可见木条表面。维持尺寸图既有端点合同，不扩大成全部文字禁止引线、不另建本地绘图流程。

本轮证明了程序修复有效的具体位置，同时证明“蒙版更完整＋上传正确＋合同 ready”仍不足以保证编辑执行正确。后续验证应改变上述已定位的输入责任，不原样重复三张请求，也不引入第二个 QA 模型。
