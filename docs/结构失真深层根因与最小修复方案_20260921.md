# 结构失真：深层根因与最小修复方案

日期：2026-09-21。范围：上一轮浴室柜两个变体的 18 张当前候选，以及生成它们的当前代码、观察、规划、实际请求和附件。本次只做核查和方案，不修改生产代码，不调用付费模型，不运行 QA。

## 一、核查结论

最优先的修复点已经明确：**现有设计复核没有实际覆盖这些结构问题。**

对本轮产物重新构造现有 `design_binding_request`，并核对真正发送的复核请求，结果为：

| 项目 | 原木柜 | 白柜 |
|---|---:|---:|
| 当前 brief | 9 | 9 |
| `physical_operations=[]` | 9 | 9 |
| `design_review={}` | 9 | 9 |
| 实际发送的 `design_binding` | 0 | 0 |
| 实际发送的 `product_claim` | 8 | 7 |

因此，之前“已有事实/文案复核”的描述需要进一步限定：这些请求核查了文字声明，**没有完成层板位置、磁吸扣安装面和防倾倒装配关系的设计复核**。文字“Magnetic Catches”得到 supported，不表示磁吸扣可以安装在开放格上方。

证据：[结构复核覆盖核查.json](../test_runs/freeze_4asin_2var_20260920/audit/remediation_20260921/结构复核覆盖核查.json)。该文件由当前产物和当前函数只读计算而来，未构造远端请求。

## 二、代码层为什么漏掉

当前调用链：

`observe_child_sources → FinalSourceIntent → visual_design_kit_prompt → _finish_image_briefs → design_binding_request / review_planning_bindings → ImageTask → compile_task_prompt → generation`

### 2.1 复核对象的选择条件不完整：已确认的程序缺口

`core/visual_design_kit_compiler.py:308` 从空 risks 开始，当前只在对象 `sale_membership == unknown` 时加入 `sold_membership:<source_id>`。

也就是说：一个部件只要被观察器认定属于商品，即使位置、形状或装配关系写错，也不会因此生成必查 operation。销售归属与结构正确性是两个不同问题。

`core/visual_design_kit.py:478` 只在缺少 operation 结果时把设计项放进实际复核请求。空集合就直接跳过。

`core/visual_design_kit_compiler.py:342` 的 `_validate_physical_review` 又允许“没有待查 operation，也没有复核结果”的情况通过。这对于无需复核的普通展示可以合理，但对功能/尺寸表达没有覆盖结构合同。

这条链能解释为什么观察器的错误事实没有被发现，既有 `source_product:<source_id>` 回流纠错也没有被触发。并非系统没有纠错入口，而是入口没有收到这些问题。

### 2.2 现有提示已经提醒过，但没有形成实际核查

观察提示已经写了替代位置、箭头、虚影不是额外部件；规划提示也写了强调图形不是实体。仍然发生实体化，说明继续复制同类警告的收益有限。

`physical_facts` 目前是自由文本列表。结构验证检查字段、类型和非空，不理解“top”指哪块板，也不能凭字符串判断圈线是不是实物。程序能保证来源和流转，却不能把模型一次观察自动变成已证实事实。

### 2.3 测试覆盖了当前行为，也固化了遗漏

`tests/test_image_branch_v1.py:470` 明确断言这些 brief 的 `design_review` 为空；另一些测试主要使用销售归属争议来触发复核。它们没有复现“销售归属明确、部件关系却错误”的情况。

上一轮 100 项通过说明已有合同未被破坏；不能据此推断这条缺失的结构复核已经运行。

## 三、逐问题的根因与责任

### 3.1 层板实体化

对象：原木 `func`，源 `source_05`，辅助整体图 `source_00`。

实际观察：`Interior adjustable shelf movable 2.5 inches up or 2.5 inches down across 3 positions`。

实际目标：`showing 3 height positions with 2.5-inch adjustment range up or down`。

这里保留了“可调三档”和数字，却没有完整表达：**同一块活动层板，在三个互斥位置中的一个安装；其他位置只是示意。** 源图中黄色强调/替代位置又与实际板面接近。生成模型最终把多个位置同时画成木板。

责任判断：观察/规划的展示语义不足，结构复核未运行，随后图像模型作出了错误实体化。白柜同类图没有出现相同多板问题，不能把所有层板请求都归因于模型必然失败。

最小修复：在现有物理事实及 `presentation.state` 中说明单块层板、互斥安装位置及非实体示意；由 Gemini 在原规划中选择孔位或虚线示意方式。原复核核对板数与位置关系。不得把“三档可调”改成“三块层板”，也不新增局部合成服务。

### 3.2 磁吸扣错位

对象：原木 `func_03`。

源 `source_07` 观察：`White magnetic catch mounted under top horizontal divider`；整体源 `source_00`：`Magnetic catch positioned at top center edge of door frame`；规划目标只剩 `top magnetic catch`。

柜体同时有台面、开放格下板、下柜门框等水平构件，`top` 缺少明确所属对象。输出把磁吸扣装到开放格顶部，且引线指向错误位置。

责任判断：这是关系主体不明确，不是把文字再换个说法就能解决。现有文字复核只能确认有磁吸扣，未核对“哪块板的哪一面、与哪扇门接触”。

最小修复：回到同 child 的整体开门源图定位，以“下柜门洞顶部、开放格下方隔板的下表面、门扇闭合时接触”这样的关系表达替换模糊 top 描述；如果某一接触细节不可见，不补造内部结构。原复核同时核对主画面和局部示意所指的同一部位。

### 3.3 柜脚强调环实体化

对象：原木 `func_03`。

观察器实际写入：`5 support legs ... with round plastic base pads`。编译后的 Prompt 原样包含这个断言。

源图中的夸张同心环不足以证明存在这种实体底垫，更不能证明“塑料”材质；白柜相近源图的观察没有做出相同判断。错误在生图前已存在。模型遵守了错误事实，继续要求它“忠实保留结构”反而会保留错误。

最小修复：用现有来源复核/重观察替换这条错误事实；只保留有证据的脚体、连接与数量。不要在编译器按“pad”关键词删词，也不要一边保留 plastic base pads、一边在修订 reason 中写 remove pads。

### 3.4 防倾倒件安装面和形状重绘

对象：原木 `func_02`、白柜 `func_04`。

原木观察至少写了 `upper rear side`，白柜却只写 `rear top edge`。后者未明确竖直安装面与水平顶面，规划又简化为 rear top frame。白柜结果把源图局部所示的竖直面连接改成柜顶水平安装，五金形状也改变。

白柜这一张实际只有 **1 张源图附件**，没有辅助整体图。因此，不能把此问题统一归因于多图冲突或“只留一张参考就能修好”。

责任判断：安装面关系描述不完整，细节被要求重新展示时又允许图像模型补全几何。`source_setting` 只是环境语义，不是像素锁或几何锁。主画面与局部图一致，只证明同一个错误被画了两遍。

最小修复：将“柜体哪一可见面—角码哪一边—墙面—对应固定点”写清，保持可证实的安装关系。细节证据只支持当前观察角度时，保留该角度，允许改周围留白、文字和图形，不授权生成未知背面。读不清的内部连接不猜测；沿原局部纠错机制处理受影响角色。

## 四、已经排除或不能认定的原因

1. **不是发送时换错 Prompt。** 本轮 18/18 指纹一致。
2. **不是功能图附件在传输时被偷偷裁剪。** 8 张 func 的回执记录均为原附件 unchanged，顺序与任务一致。
3. **不能认定放大是结构错误根因。** 原始响应按原策略已清理，本次没有基础图/放大图逐像素对照；已经发现的错误语义在放大前输入中就存在。
4. **不能用单外观图解释全部失败。** 整体规划只看一张图，但功能原图仍参与生图；白柜防倾倒单附件照样失败。关键是文字事实和结构复核是否可靠。
5. **不是没有 QA 导致错误生成。** 本轮按要求停在生图；QA 是后续评价，不会替生成端理解安装面。

## 五、最小可执行修复方案

### P1：补齐原复核调用的结构覆盖——优先实施

修改点：`core/visual_design_kit_compiler.py::design_binding_request`。

- 为 func / size 的当前输出添加一个明确的“产品结构与展示关系”复核 operation；沿用已有 `physical_operations`、review key、findings 和 pending 机制，不建立第二套审查数据或控制器。
- 查当前 brief 实际展示且有来源依赖的部件、连接面、替代状态、测量对象；不要求所有图片把全商品所有结构都展示出来。
- 保留已有 sold_membership 检查；普通 main / scene 不因为这次修复新增一轮全量结构复核。
- 原 `_finish_image_briefs` 在同一现有复核批次中提交新增 operation；原验证函数要求得到该 operation 的结果。此处先补调用缺口，不另写一个“全图检查阶段”。

本次两个 child 已有复核请求，可将结构项并入既有批次。其他原本没有任何复核项的 func / size 可能会开始调用已有复核服务，这是补齐必要工作；不能承诺所有输入都零增加请求或零增加耗时。

### P2：替换原观察及复核语义，使用原纠错出口

修改点：`core/visual_semantics.py` 的原观察/原规划复核提示及 policy 版本。

- 替换现有宽泛关系提醒，要求事实保留“部件—连接面—被连接对象—互斥/同时状态”；仍用现有 `physical_facts`，不增加产品关系图数据库。
- 图形不能支持材质、实体数量或连接方式的断言。对源图未能判明的事实保留 unknown；不要把未知写成否定或凭常识补全。
- 原复核对照所选原图像素及声明，不把 physical_facts 自身当作独立证明。
- 观察错误：返回既有 `source_product:<source_id>` 和 `correct_evidence`，走原来源纠错。
- 观察正确但展示要求错误/缺关键关系：返回该结构 operation 的 `revise_plan`，走原 brief 局部修复。
- 仅因图形风格、房间选择、引线样式或未展示无关隐藏结构，不返回结构失败。

### P3：把必要展示关系带入最终请求，替换含混表达

修改点：`core/visual_design_kit.py` 的原规划提示；`core/image_prompt_compiler.py::_role_content` 的既有展示说明。

- 将已证实关系写进原 `presentation.state`，直接投影到最终 Prompt。纠正旧词后再编译，不叠加一套相反的约束。
- 对“一个部件的多个可选状态”，明确它们互斥，示意线不是实体。
- 对安装细节，限制涉及未知连接面的视角变换；仍让图像模型设计版面、文字、灯光和留白。
- 对标题仅维持既有 title/labels 职责；本轮不新增字号判定器或版式评分门。
- 更新对应 policy/Prompt 版本，使旧结论失效；不静默迁移旧观察、旧 brief 或候选。

预计限定在上述 **4 个现有生产文件**，不新增生产模块，不改调度、供应商路由、QA、发布、模板，不改图像基础尺寸，不添加自动裁剪或强制蒙版流程。

### P4：替换漏检测试，验证局部失败不会扩散

在当前行为测试中替换“func / size 空 design_review 也 ready”的相关旧断言，保留无需新增复核的正常角色断言。最少覆盖：

1. 销售归属全部明确，func / size 仍实际发送结构复核；空结果不能冒充查过。
2. 模拟源图把强调图形误当部件，能产生原 source_product 纠错并更新受影响绑定。
3. 模拟事实正确、安装面计划错误，只修对应 brief，不重规划其他 child 或清掉已成功角色。
4. 复核已支持且当前性匹配时不重复付费；超时使用原有限重试，不加无限循环。
5. 互斥层板语义到达最终 Prompt；基础事实与修订要求不冲突。

不新增纯实现细节测试或历史路径测试；在现有方法内替换/合并，保持生产套件 ≤100 项 / ≤60 秒。实施时定向测试，收尾只跑一次默认生产套件。

## 六、如何避免产生新的无谓阻塞

- 使用原 brief 阶段与同一批次复核，不在每张图前新增独立服务调用链。
- 查图中真正要表达的结构关系，不把不可见但无关的细节列为必需证据。
- 未知只影响依赖该事实的角色；普通场景、其他 child 和已有成功任务按各自当前性与原机制继续，不因为某张图的失败直接整批失败。
- 观察错误回观察，规划错误回规划，正确合同下的画错回原候选修订；不让它们相互循环修饰提示词。
- 不增重试次数、不放宽事实条件、不因房间偏好或审美增加门槛。

这里“无新增无谓阻塞”不等于把真实缺证据放行为成功。若所需安装关系确实无法看清，应保留原局部 pending 和原因，不能为了计数齐全编造。

注意当前性的实际限制：事实/规划修正后 task_fingerprint 会变化；`candidate_by_sha` 只接受当前任务的候选，不能拿旧 SHA 直接做新合同 targeted_edit。用既有 child + role 定向入口生成新合同首张；新合同下仅图像执行错误时，再按当前候选 SHA 使用原 targeted_edit。不得为了复用旧图新增跨合同兼容路径。

Policy 更新可能使六张之外的缓存或任务也失去当前性；实施时先列出实际变化集合。六张是实图验证范围，不能据此宣称其余十二张已在新版本验证，也不能把旧成功候选自动算成新版本可交付。没有必要为了填齐数量扩大付费生成。

完成条件：

- 实际复核请求存在结构 operation，实际返回绑定到对应源和 brief；不能只看 ready 数量。
- 错误事实在新观察、brief、Prompt 中消失；替代状态与安装面表达一致。
- 查看六张实图及其局部，对照实际附件与 Prompt；数字/标签正确不能替代结构正确。
- 正常两张对照不退化；其他角色不因复核服务的局部问题整批失败。
- 只验证到生图，不运行 QA 或发布。若依然画错，如实保留，不凭测试通过或复核 supported 宣布视觉通过。
