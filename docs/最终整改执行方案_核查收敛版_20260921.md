## 二、修改清单与实施方式

### M1：事实保留与必要关系观察

**文件/入口**：`final_source_intents.py::_build_final_row`，`visual_design_kit.py::_validate_source_manifest`，`visual_semantics.py` 现有联合观察指令。

具体修改：

1. 对身份有效、可作为商品证据使用的 main/scene/func/size 来源，保留已经通过原提取与绑定规则的声明。取消仅因角色为 main/scene 而清空 claims 的条件。
2. 错误变体、身份冲突及不可用来源继续遵守原排除与复核规则。不能简单把所有行无条件升为可信来源。
3. 将现有声明结构、来源 SHA、证据 ID 及去重校验应用到实际携带声明的来源，不再只检查 func。
4. `_source_manifest()` 和 `cleaned_source_claims()` 当前已能传递声明，保持接口，只补行为验证；除发现真实过滤外不重写。
5. 替换观察中笼统的连接描述要求：对本图清楚可见的机构，说明连接对象、接触面、方向和状态。例如角码哪一面连柜、哪一面连墙。可见数量与总数量分开，标注图形与实体部件分开。
6. 继续使用 `physical_facts`，不增加部件表或关系图 schema。看不见的连接保留未知，不按品类常识补全。

**删除/替换**：main/scene 清空合法声明的分支；只校验 func 声明的条件；被新的关系说明替代的泛化语句。

**验收**：同一合法来源改为 scene 后，事实 ID、SHA、声明仍可被 func 引用；main/scene 的可渲染营销文案权限不变；无文字功能特写仍可判 func；安装所需墙面不自动变 scene。

### M2：标题与标签职责进入实际 Prompt

**文件/入口**：`image_prompt_compiler.py::compile_task_prompt/_render_text_block`；必要时调整 `image_task_inputs.py` 的现有文字投影。

具体修改：

1. 从已绑定的 `display_copy_contract` 读取标题和标签身份。
2. 在原 TEXT 区域中标明职责，授权文字本身只出现一次；明确字段说明不是需要绘制的文字。
3. 无标题明确写无标题，不能把第一条标签自动升为标题。测量文字仍由原测量授权表达。
4. `renderable_text_contract` 继续用于字符串集合与 QA 比较，不成为第二个编辑入口。
5. 让现有基于编译内容的任务指纹感知职责变化，不另建标题 hash。编译不得原地修改 task。

**删除/替换**：仅将授权文字压成无职责列表发送给模型的旧表达；更新保护这一行为的测试断言。

**验收**：相同字符串集合，标题与标签身份不同，Prompt 和 task 指纹必须不同；重复编译、JSON 重读后编译相同；实际授权字符串不增不减。

### M3：目标状态唯一，参考状态保留为观察

**文件/入口**：`image_prompt_compiler.py::_role_content`，`image_reference_context.py::reference_prompt`；规划指令联动见 M4。

具体修改：

1. `presentation.state` 明确表达本图要画的目标状态。
2. 将所选参考的 `physical_facts` 标注为对应附件的来源观察。它们证明结构、身份及可见状态，不要求所有来源状态同时出现在结果里。
3. 第一编辑附件优先支持目标状态；辅助图只补它确实增加的证据。缺少新证据的辅助图由 planner 不选，程序不按关键词删除。
4. 用既有 `product_sources` 的顺序、kind、source_id 和附件说明表达职责，不新建平行的参考决策表。
5. targeted_edit 模式继续以候选为第一附件，原图用于事实核对。普通生成的附件编号变化必须同步到实际请求和 trace。
6. 目标状态仍须有证据支持；“目标优先”不授权 planner 发明来源未证明的内部结构或状态。

**删除/替换**：把目标与来源状态无区别并列成执行要求的表达。保留原观察全文，不删除半开/关闭等真实状态。

**验收**：#59 对照中，双开是唯一输出目标，半开辅助图只提供原始观察；尺寸测量附件仍存在；必要安装证据没有因旧海报版式而被删除。

### M4：同一次规划完成分工、短文案和唯一主体定调

**文件/入口**：`visual_semantics.py` 既有观察和校验，`image_reference_context.py::planning_reference_inputs/prepare_planning_references`，`visual_design_kit.py::visual_design_kit_prompt/_finish_image_briefs`。

#### 4.1 唯一主体图如何产生

1. 复用联合观察的 `reference_purposes`。本轮将 appearance 明确定义为共同定调使用的首选主体参考；有可用完整商品视图时，只标记一个首选来源。
2. 选择优先级由现有观察模型判断：身份与饰面可靠、商品完整、干扰少。无需 source_00，不能只按下载顺序取第一张。
3. 其他有效视图保留功能、测量及物理事实。取消额外 appearance 标记不等于删除来源，不降低具体生图的多图证据能力。
4. 原有完整性校验在既有响应修复预算内处理重复首选或无效引用。程序不另开选图模型调用，不通过截断列表掩盖错误。
5. 带房间或普通道具的图，只要商品身份、完整结构和饰面可辨，仍可作为首选；它不是绝对“干净图”。观察和规划不得把道具颜色当产品调性。
6. 没有可靠主体证据时，保留原有该 child 的证据缺口，其他 child 和 Copy 继续。可用来源尚未恢复时走原恢复/重观察入口；图库本身缺图且没有商品图导入能力时，如实记录能力缺口，不伪造导入命令。

观察缓存更新后重新按新语义取得选择，不将旧多 appearance 记录静默迁移为第一张。

#### 4.2 实际请求如何保持一张

1. `planning_reference_inputs()`、实际路径准备、manifest、初次规划和局部 repair 使用同一来源选择与 SHA。
2. 移除共同规划请求自动追加所有 appearance 图和已批准风格图片的路径；共同规划/普通 repair 实际图片附件为一张主体图。
3. 保留已批准设计参考的文字目录、授权边界及 role 限制，不能给未发送的图虚构 attachment_number。可在原事实/设计复核和具体生成中使用必要的批准图片。
4. `design_transfer` 的选择、复核和生成附件继续沿原链，不删除已批准设计能力，不把未附图片描述成 planner 已亲眼检查。
5. 不改变具体 func/size 生成的多图附件规则，不把定调主体图强行当成所有角色的第一编辑附件。

#### 4.3 同一次规划的决策顺序

```text
理解商品与证据 → 共同调性 → 本套不同买家问题
→ 分配到既有角色 → 选择目标状态与必要证据 → 精简图片文案
```

- `visual_goal` 承载本图主要问题；不另建策略合同。
- 允许必要信息复用，但不能让数张容量图只换房间。证据确实不足时，不为追求差异编造新卖点，也不删槽位。
- `display_copy` 删除与标题/图示重复的说明、泛泛赞美及无事实增量的段落；保留数字、对象、范围、条件和限定。
- #49 的 221 字符长段落应由 planner 编辑为必要短标签或删除重复说明；不能程序截字，不能让生图模型在 exact 后自行缩写。
- 准确简短原句可以保留。合法改写沿原批量语义复核与有界 repair 处理，不新增改写率、字符数审美门。
- 局部 repair 修文案时同步检查 goal/state 是否仍残留已撤回的性能表达；未受影响的共享设计和 ready 角色保留。

**删除/替换**：允许增加第二定调外观图的旧说明及附件路径；自动追加风格图到共同规划的路径；被整套信息分工要求替代的重复提示。

**验收**：两个以上候选来源时实际仍只有一个规划附件；初次和 repair 一致；其他证据可供生成；#49 文案简洁且限定不丢；套图 brief 能说明不同的信息责任。真实调用结果验收，不以提示词出现 buyer question 代替。

### M6：补齐同逻辑任务跨版本的未知请求保护

**文件/入口**：`image_response.py` 原恢复与提交检查；必要联动 `image_generation.py`、`image_generation_executor.py` 的现有调用点。

具体修改：

1. 精确结果恢复继续按原 response_binding 匹配，不能将旧图绑定给新任务。
2. 在原付费提交边界增加同 job、同 logical_task_id 的未结回执核对。现有 request_audit 已记录 logical_task_id，可利用原 JSON 回执，不新增总账。

5. 旧绑定有已保存响应时，先在原绑定下恢复或明确处置，不能当作新任务响应使用。
6. 检查和新 receipt 登记使用原锁机制，在同 job 的提交边界保持原子性，避免两个新绑定并发穿过检查。只串行化短暂元数据登记，不锁住远端生图全过程。
7. `confirmed_not_generated` 继续表示已有明确处置；`approve_one_resend` 继续只授权其原精确请求的一次补发，不能自动授权新 Prompt，也不能在两个绑定下重复消费。
8. 已知失败、已完成回执及其他 child/role 不阻塞当前任务。版本升级不迁移旧成果，也不清状态绕过未知。

**删除/替换**：把“当前 binding 没有回执/当前 revision 没状态”等同于“可直接再付费”的判断。保留精确恢复，不增加第二恢复控制器。

**验收**：同逻辑任务跨 hash/Prompt 仍识别未知回执；其他角色正常；本地保存后提交失败能恢复且供应商调用数不增加；原一次补发授权不扩大范围、不重复消费。不得仅断言 response_binding 不同就算完成。

## 三、没有现成入口的事项如何处理

| 需求 | 本轮可执行方式 | 明确限制 |
|---|---|---|
| 本次规划信息分工/短文案不合理 | 更新上述规划规则，用新版本在指定测试范围形成新 brief | 新规划可能影响同 child 多个角色，不能承诺仅改一张 |
| 来源观察错误 | 原 `review-source-role --role reobserve`，随后原 classify/brief | 只处理明确来源，不重跑全部历史任务 |
| 品牌方向确实要改 | 原 `run --brand-brief` 配合 brief | 它不是任意单图目标编辑器 |
| 候选未执行正确要求 | 原 `revise --mode targeted_edit`，绑定实际父候选 | reason 只能纠正执行，不能覆盖旧授权文字或状态 |
| 任意 ready brief 标题 A 改 B | 本轮不提供通用人工编辑接口 | 不手改 JSON；此能力不是本轮验收前提 |
| 缺少可用真实商品图 | 恢复既有下载/观察；无可恢复来源则记录素材缺口 | 设计参考导入不能冒充商品证据导入 |
| 已完成候选的原始供应商字节已清理 | 使用最终候选、请求及回执进行本轮对照 | 不声称完成原始/最终像素归因；不重发请求只为补原始图 |

本轮保留原响应清理机制，不增加常驻取证选项。若后续确实需要排查本地最终化，应另行明确少量样本的取证安排；没有原始字节时，只报告这一归因未验证，不扩大为本轮所有生图的启动条件。

## 四、实施顺序与版本处理

### 第 1 步：固定基线

记录实际 HEAD、分支及工作区差异。保护已有分类修正和核查报告。不 reset、不清 jobs、不自动推送。

### 第 2 步：先完成恢复边界，再实施图像内容修改

顺序为 **M6 → M1/M2/M5 → M3 → M4**。这是代码实施顺序，不增加生产阶段；期间不调用付费模型。

先完成 M6，避免后续政策版本升级后测试误绕过旧未知请求。各项修改连同消费者、缓存、trace 和对应测试在同一实施任务内完成。

### 第 3 步：同步真正受影响的版本

- 观察语义变化：更新现有观察 policy。
- 最终来源声明语义变化：更新最终来源 policy。
- 规划请求、附件选择变化：更新现有规划 policy/请求身份。
- 标题及状态投影变化：更新 Prompt 合同/策略所需版本；由现有实际 Prompt 指纹区分候选。
- 只改 QA：更新 QA policy。
- 不为“统一升级”而递增全部 schema。只有结构真的改变才同步 schema/readers；不留旧读法 fallback。

公共政策变化可能使受影响 child 的计划失效，需诚实记录重规划范围。本方案不承诺公共规划变更后所有旧计划仍当前，也不允许直接覆盖旧候选使其看似当前。

### 第 4 步：离线回归完成后冻结代码

保留现有不超过 100 项、60 秒的生产套件。新增子场景合入现有方法；删除被替换旧行为的断言，不能删除正常恢复覆盖来凑数。

## 七、验收与失败处理

### 代码完成条件

- M1—M6 对应行为通过；被替换分支与旧断言已删除。
- 编译保持确定性，标题职责可改变指纹，未用组件不改变实际 Prompt。
- 单图定调请求与 manifest/trace 一致，多图事实能力保留。
- QA gate 消费任务政策，完整当前性检查保留。
- 跨版本未知回执不能绕过；同绑定保存响应可以恢复；其他角色不受牵连。
- 生产套件 ≤100 项、≤60 秒，记录命令、耗时和外部模拟边界。

### 图像验证条件

- 每张按原图、实际附件、brief、最终文字、Prompt 和候选对照。
- 分类按主要用途，func 可带必要环境；graphic_canvas 的执行偏离单独记录。
- 结构、状态、尺寸和授权文字正确；不凭数字正确认定全结构正确。
- 文案有信息层级，套图分工可解释；不以改写率或源图差异率判定。
- 正常图无新增明显错误；模型未做到的要求如实列出。

### 失败只回到负责位置

| 失败 | 处理 |
|---|---|
| 观察用途或事实错 | 原来源复核/重观察，更新受影响 brief |
| 文案、信息分工或目标错 | 原规划/绑定修复，不让生图自行修需求 |
| 要求正确而候选画错 | 原候选修订，保持父图和请求追溯 |
| submitted 远端未知 | 原回执处置，禁止换身份直接重发 |
| 本地提交失败且已有响应 | 原精确绑定恢复，不再付费 |
| 独立 child 或来源服务失败 | 局部保留缺口，正常工作继续 |

不把检查失败变成全图预检或额外审批阶段。真实证据不足时不声称“全部修好”。
