## 3. 六组最小代码修复

### R1：把最终事实投影与销售数量范围统一到现有事实责任中

**原因：** 已有 `effective_product_facts`，但模板继续重新择值；数量正则只识别数值和 pack 字样，缺少被计数对象；生产者与 schema 对异常状态的约定又不一致。

**修改位置：** `core/product_family.py`、`core/template_engine.py`、`products/generic_extractors.py`、`core/source_fetch/apify.py`、`schemas/product_family.schema.json`。

1. 模板的 variation、attributes、最终字段统一消费有效事实。confirmed 使用裁决值；conflicted/unconfirmed 不得从原始 variation、spec 或别名中恢复；没有裁决记录时才沿用已定义的合法来源顺序。
2. 在现有事实投影中统一 color/colour/color_name、size/size_name/size_class、style/style_name 等实际使用的别名。不能只在模板优先读取一个字段，而让其他消费者仍读到旧别名。
3. 数量提取必须确认“多少个、什么对象、属于商品套装还是随附部件”。保留真实商品多件套及 Number of Items 的证据；安装件、包装、局部层板等不授权整件套数。应替换无对象绑定的裸 pack 匹配，不能只加 screws 黑名单。
4. 同一来源出现多个明确商品数量时，保留真正冲突，不取第一个匹配。对象不清楚的文本保留为原始线索，不直接升级为确认事实。
5. 数量 source 枚举与当前返回状态对齐；无效显式数量不得在补齐 schema 后把占位 1 当成确认销售事实。复用已有 resolved_facts 的 unconfirmed/conflicted 表达，并让有效投影排除未确认数值，不新建事实文件。仅“完全没有明确数量证据”的情形继续遵守既有单件 listing 政策。

**删除：** 模板二次读取旧变体进行裁决的路径、裸 pack 命中即授权销售件数的路径，以及锁定上述旧行为的断言。

**验收：** 颜色四反例及别名通过 `_family_specific → _build_listing_row_data → compile_template_field_plan` 检查最终值；数量覆盖单柜配件包、真实双柜、真实套数冲突、无效值、无证据和同句多数量，验证到实际 family schema、任务事实与模板 number_of_items。

**防止新增阻塞：** 无歧义正常商品保持可执行；数量状态能够写入当前 family，避免内部 enum 错误拖垮整份 family。未确认事实只按现有下游规则影响依赖它的字段或任务，不能全家族统一清空或把所有候选作废。

### R2：在原有解析与校验中补齐数值语义

**原因：** 分数归一化丢失整数边界；字段分类漏掉真实数值字段；承重以键名存在代替有效证据存在。

**修改位置：** `core/text_evidence.py`、`core/template_field_plan.py`、`core/copy_writer.py`；必要的字段别名复用 `template_engine.py` 现有映射。

1. 在 NFKC 破坏连写关系之前展开 Unicode 分数，保留 `3½ = 3 + ½`。只把分数斜线改成 `/` 会产生 `31/2`，并不是修复。统一处理纯分数、带整数分数、普通分数和尺寸链，拒绝分母为零或畸形表达被截成另一个合法数字。
2. 数值识别使用当前实际字段映射及字段末端类型，补齐重量、最大承重、门/抽屉/层板数量等。`[language_tag=en_US]` 是字段路径限定符，不能因为整条路径含 language_tag 就跳过数值检查；真正的 unit/type/language_tag 值字段仍按其本义处理。
3. 统一要求有限数值。数量按对应字段要求整数和合法范围；库存 0、没有抽屉的数量 0 等合法值不误杀，商品销售件数遵守其已有最小值，尺寸/重量按各自现行语义处理。
4. 承重声明必须匹配可用的正向、有限、有单位、对象及条件一致的承重事实。删除键名命中后的空集合放行分支；未知/否定/零/缺单位/商品自重不能授权承重。已有每层与整件区分及单位换算继续使用，不再增加新的审核模型。

**删除：** 仅凭 capacity 键名放行、known_capacities 为空就跳过比较的路径；被替代的字段分类条件及对应旧断言。

**验收：** 分数/公制英制/普通小数对照；四个真实字段须得到 invalid_numeric，正常有限值及合法 0 通过；承重反例通过完整 Copy 校验入口，并检查单位等价、每层与整柜、缺单位、负值及正常声明。

**防止新增阻塞：** 只约束被表达的数值和承重声明，不把“所有商品必须有承重”变成新要求；没有承重证据时仍可生成不含承重宣称的正常文案。

### R3：在现有回执与候选提交中修复中断恢复

**原因：** prepared、submitted、response saved、candidate committed 是不同事实，当前几个入口对它们的判定不一致；部分恢复又依赖当前远端配置。

**修改位置：** `core/image_response.py`、`core/image_generation.py`、`core/image_generation_executor.py`、`core/candidate_state.py`；`core/image_provider_routing.py` 的 worker 异常判定同步消费同一恢复结果。

1. `begin_response` 只准备新请求，不能因此解除旧未知请求对不同绑定的约束。提交时在现有回执锁内更新替代关系；旧 `superseded` 标记不能单独证明未知结果已处理。必须覆盖提交标记写入前后崩溃，避免仅把那行赋值搬到另一个函数后留下新的双文件窗口。
2. 在当前绑定内识别已有 `.http`/`.bin` 与元数据不一致的中断状态。原子写出的完整正文应先验证并补齐原回执，再复用现有解码/下载与候选提交；`.partial`、无效正文和不匹配绑定不能当成功图。
3. 请求授权和 worker 异常归类均先查询同一份恢复事实。有可恢复响应时不消耗重发次数；准备失败不冒充已发请求；未知结果继续遵循用户已授权的同绑定最多三次重发，不增加模型或自动扩大额度。
4. 普通 resume 复用已提交候选时，同时完成与其一一对应回执的幂等结算。必须核对 candidate SHA、任务/请求指纹、候选版本和回执身份，不能凭“目录里有图片”批量 finalized。
5. 修订与普通生成使用同一顺序：复用已完成候选/恢复已有响应，确实需要新请求时才筛选供应商、检查当前额度与路由。保留已有调度和本地最终化函数，不增加恢复控制器。
6. CandidateManifest 的 model 与物理 endpoint 从实际请求 audit 的保存快照生成，停止在首次延迟提交时按当前 provider 别名反查历史身份。优先复用现有 audit.model/endpoint，校验二者一致，不为恢复新增必须从远端取得的字段，不迁移历史 jobs。

**删除：** prepared 提前 supersede、只凭 JSON 的 body_sha 判断有无本地结果、候选复用不结算、修订先筛路线后恢复、延迟提交反查当前 registry 的旧分支。

**验收：** 在现有恢复测试内覆盖准备中断、提交状态中断、正文已落盘、bin 已落盘、manifest 已提交、finalized 清理中断六类窗口；已保存结果恢复时生成 POST 次数为 0；停用供应商和同别名改 model/endpoint 后仍归属原请求；第四次未知重发仍被既有额度规则拒绝。

**防止新增阻塞：** 有本地结果优先恢复，候选已经完成可自动结算；正确候选不重生。URL 响应可能仍需原有下载，下载故障保留响应，不转为新的付费生成。不能删除未决回执或伪造 finalized 来让页面变绿。

### R4：在原有资源账本中修复 Job 隔离与租约所有权

**原因：** 请求内容绑定可以跨 Job 相同，不能单独充当全局资源占用键；无条件 finally 释放会伤及另一执行者。

**修改位置：** `core/image_resources.py`、`core/image_generation_executor.py`。

1. 资源键使用规范化的 Job 绝对路径/响应目录加现有 response_binding；容量计算与 reserve/release 使用同一键。保留回执的请求内容绑定语义，避免为了改资源键使付费响应失去归属。
2. 释放核对 directory、PID、process_start 和本次取得的租约标识。只有成功取得租约的执行段才释放；同进程旧调用不得释放后来重新取得的租约。
3. 死进程仍按现有规则回收；已保存响应的磁盘占用继续记账，由后续合法恢复接管。

**删除：** 仅 response_binding 作全局键、无所有者检查的 release，以及未获取租约也释放的路径。

**验收：** 两个 Job 同语义任务可各自占用；A 不能释放 B；获取失败不改变别人记录；同 PID 旧租约不能释放新租约；死进程恢复和保存正文磁盘记账正常。先做隔离双进程验证，不用付费生图模拟并发。

### R5：修复现有文字 QA 的授权匹配

**原因：** 字符串“属于授权集合”被当成“授权表达完整正确”；观察已有位置和置信度，判定时却丢失出现次数与位置。

**修改位置：** `core/image_qa.py`。只有现有观察说明不足以区分物理文字块时才调整 `core/visual_semantics.py` 的同一次观察说明。

1. 高置信度文案按保留语义的大小写、空白、换行和排版标点归一化匹配。移除任意单字符替换/插入/删除自动通过，以及会改变字母身份的无条件 OCR 修正。
2. 低置信度或位置无法确定时继续使用现有 inconclusive；不能为了减少不确定把错词当正确，也不因一处低置信 OCR 直接断言产品事实错误。
3. 用已有 region 将相邻分行还原为一个物理文案块；同一物理位置的重复观察去重；不同位置重复绘制的授权营销文案按允许次数检查。
4. 测量文字按 measurement_id/物理关系检查。同为 8.5″ 的三个合法隔层和两个 1.5″ 调节关系不能按纯字符串去重或报重复。普通摆件文字仍按既有类别处理。

**删除：** 通用单字符容错放行函数（若无其他当前调用）、不消耗授权次数的营销文字成员匹配，以及要求错词被接受的旧测试。

**验收：** FSC/FCC、Pine/Fine、高置信拼错、低置信未知、同标题重复位置、标题跨两行、同位置重复观察、三个合法相同尺寸均有正反对照。最终验证现有 unauthorized_text gate，无额外 QA 阶段。

### R6：让环境配置加载失败时不泄露、不生效

**原因：** 边解析边写进程环境，直到末尾才报告冲突，并把两个完整值带入异常。

**修改位置：** `core/io.py:load_env`。

先在局部字典解析并完成重复校验，再按既有 override/only_keys 规则写入环境。冲突报错只包含键名、文件及行号，不含完整值或值的片段；相同键的相同值维持当前允许行为。失败前后环境应一致。

**删除：** 冲突记录中保存值的 repr，以及完成校验之前修改 os.environ 的路径。

**验收：** 使用合成值测试不同值冲突、相同值重复、only_keys、override 真/假、预存环境不变。日志中不得出现合成密钥。无需查看或轮换用户真实密钥，也没有证据认定已经发生泄露。

## 4. 图像问题的处理边界与下一次验证

已保留的实图证据支持“层板实体化、床底测量端点混淆、部分任务机位漂移仍存在”。它们不能全部归结为提示长度，也不能由这两份静态报告证明是模型随机问题或 planner 已经修复。

当前提示的两个直接证据：

- 白床提示同时要求 preserve viewpoint，却包含旧设计的 `Low-angle side view`；两个尺寸虽写了 rail bottom/slat level，未证明图像模型正确落到两个真实高度。当前新 planner 是否仍产生这类目标，需要运行现有 brief 才能判断。
- 黑柜已写了 primary position 与 dashed alternatives，仍产生新增实体层板。说明这句文字的存在不能当成关系正确的验收结果，也不能简单再加一遍同义禁令。

下一次验证应采用当前正常链生成的任务与正式候选，优先覆盖原失败的黑柜层板、白床净空、白床摄影机位，加一个已知正常柜体 size 对照。只对有变化的证据运行对应现有阶段；新 Job 用于当前事实合同，旧冻结图片仍可作审计反例，不把旧任务换版本头当新生产输入。

具体责任仍放在已有环节：

| 问题 | 现有环节应表达什么 | 验收看什么 |
|---|---|---|
| 层板与替代位置 | 观察区分实际木板和印刷虚线；planner 的 state 表达唯一安装实体及未占用位置 | 实体数量与源图一致；替代高度没有变成新实体；两个增量归属正确 |
| 净空端点 | 测量权威保留源图端点；state 只说明本图必要的上下表面和机位 | 12″ 与 8.5″ 指向不同真实表面，数值和来源同属该对象 |
| 机位及辅助图干扰 | 首图几何为编辑基准；辅助图只有明确缺失证据用途；保留机位的任务不能另发换机位指令 | 可见结构/颜色/材质/纹理保持，背景与床品可变 |
| QA 能否识别 | 已有 QA 观察现有失败图与正确对照，并使用已有位置/端点字段 | 能指出错误位置；未知保持 inconclusive；不错杀合法同值尺寸、反射和局部图 |

若发现观察已经正确、state 也明确而模型仍画错，保留该样本为执行失败，使用既有修订能力；不能将它归因成“缺少一个规则”就继续扩张通用提示。若正式规划仍有内部冲突，则修现有规划说明与同一次审查，替换冲突文字，不建立第二轮强制规划或总审查。

现阶段保留用户“先到生图”的实际测试边界。已知图进入现有 QA 的验证可以作为独立的受控检查，不把 QA/发布/平台回执追加为每次生图的前置步骤。完整交付验收在实际准备交付时，沿原有 QA、人审、publish、template 完成。

## 6. 执行顺序、删除项与验收预算

开发建议按 **R6 → R1/R2 → R4/R3 → R5 → 文档修正与现有链实图复核** 执行。R4 与 R3 应在同一批恢复验证中一起检查，避免账本所有权与回执结算各自正确、组合后仍相互阻挡。

- 每组先检查当前调用者及旧分支，修改现有责任函数，物理删除被替代的逻辑与断言；不保留 legacy 路径或默认关闭的新控制器。
- 新增生产模块目标为 0，新增生产阶段为 0，新增外部服务为 0。无需扩建事实 schema；数量 source/status 与当前返回值作最小对齐即可。
- 沿用现有 `test_root_cause_remediation`、`test_template_field_plan_contracts`、`test_copy_v1_contract`、`test_us_measurement_contract`、`test_freeze_recovery`、`test_provider_runtime_v1`、`test_qa_lite_v1`、`test_env_layout` 的相应测试，合并重叠案例。中间只跑相关测试，完成后运行一次生产套件。
- 不新增强制完整家族抓取、每图手工标注或每图二次模型审查。必要事实缺失继续由原有状态表达，正常商品与无关角色不被误伤；“不新增阻塞”不等于把错误事实默认通过。
- 更新真正受语义影响的既有 policy/指纹；不全局修改所有版本，不清理历史 jobs，不用旧审批证明修改后候选已通过。R3/R4/R6 的恢复、资源、环境修复不改变生成 prompt/task 指纹；R5 的 QA 规则变更只使相应旧 QA 结论需要重评，不据此强制重生图片。新事实/新计划确有语义变化时按原指纹规则重新生成对应任务，旧未决回执始终保留原绑定，不能用新版本请求覆盖。
- 提交完成报告须列生产文件增删改、行数、被删除旧路径和测试、命令与耗时，以及哪些环节尚未经过真实输出。当前文件最大的 copy_writer 为 1,768 行；实施时仍遵守仓库行数上限。

可接受的结果是：正常数据顺畅通过；错误事实不被默许；已有结果能自动恢复；同一任务只使用一套事实、一套回执、一套候选和一套 QA。六组代码修复的通过与图像质量通过分别需要各自证据，不能互相替代。
