# 三张反复失败图片：责任链根因复核

本轮只读取原白床、白玫瑰、白柜的既有证据及当前生产代码；不生图、不调用规划器或 SAM、不改生产代码和原作业。新增材料仅在 `test_runs/three_image_root_audit_20261014/`。

## 一、首先更正上一轮审计的遗漏

**白床烟囱上一轮就已消失，并非这轮改文案后才新出现。**上一轮原生图可直接确认这个事实，但 `VISUAL_DETAIL_LIVE_VALIDATION_20261014.md` 只列了引线和位置错误，甚至使用了“床架主体……继续保留”这种过宽表述。

这说明之前的人工审计不完整：检查了整床视图和板条视图是否存在，却没有检查整床内部的小构件是否仍存在。后续据此把修改范围收窄到 `visual_goal`、`display_copy`，复用了缺陷蒙版。不能把这种漏审说成模型又产生了一个全新的问题。

## 二、目前已经查清的原因链

### 1. 白床：产品身份信息已存在，但功能图保护只覆盖了两个大视图

原子体观察中并非完全没有识别烟囱：

- `source_00`：`Left-side chimney accent block attached to the roof peak`。
- `source_06`：`Slanted brown gable roof pieces framing the top edge with chimney ornament`。
- 实际 func 编辑底图 `source_03` 的观察只记录了 `slats_structure`，包含“10 根胶合板支撑条”和“松木框架”两项事实。
- `source_03` 的 `product_extent` 被标为 `whole_view`，`evidence_gaps` 为空。它不代表可见构件已经逐项记录完整。

实际 SAM 意图为：

```text
reason: Maintain the slat layout and frame joinery accurately.
query: wood support slats and bed frame
crop: left=.08, top=.05, right=.98, bottom=.98
parts: []
```

烟囱在这个裁剪范围内，因此**不是被 crop 上沿裁掉**。问题在于该语义查询取得的候选没有覆盖它。本轮逐一读取原有全部 10 个候选：人工标定的烟囱核心区域，9 个覆盖率为 0，另一个约 4.2%。**没有一个完整烟囱候选等待被选中。**这里不能继续诊断成“选错最高分候选”，也不能靠并集更多旧候选补好。

原规划器选了两个候选，理由是分别保护“板条结构视图”和“卧室整床视图”，随后接受理由也是“两个视图已经保护”。这个判断漏掉了：视图存在不等于视图中的构件完整。

之后两次文案修订使用 `accept_current_region:true`。物理依赖未变，所以复用蒙版在代码指纹规则上是合法的；**合法复用没有纠正原先错误的视觉接受判断**。最后缺少保护、又没有在当前图的部件描述中被明确保留的小烟囱消失。

责任位置：

1. 原观察/规划将功能卖点事实与整件产品可见结构覆盖混为一谈。
2. 原 SAM 确认只验证了大视图完整，漏掉局部构件。
3. 我的逐图审计没有发现上一轮已经发生的删除，后续限定修复范围也漏了它。

不能据此断言 INT8 权重必然有错，也不能保证换一个查询就绝对保真；但这条漏保留链已经有具体输入、候选和接受记录可追溯。

### 2. 白玫瑰：文案矛盾已解决，剩下的是局部几何被执行端改变

实际新合同只有左树一条文案，右树明确不复制；实际图也实现了这个要求。两根地钉均保留尖端和圆盘，未再出现生活场景或多余硬件窗。

重新测量时直接使用原文件尺寸，不把非正方形源图误当作正方形：

| 对象 | 源图 | 新原生输出 | 按图片高度归一化后的长度变化 |
|---|---|---|---:|
| 左地钉 | 222 / 1500 | 205 / 1254 | +10.46% |
| 右地钉 | 222 / 1500 | 207 / 1254 | +11.53% |

测量是圆盘至尖端的暗色连通区域，两个阈值下结果接近；不是商品物理尺寸。圆盘相对宽度基本相近，不能用整张图整体放大解释地钉加长。原图 1461×1500、输出 1254×1254 的比例差异也不能解释纵向约 11% 的增长。

更具体的证据：**两个新尖端在原蒙版对应位置的 alpha 都为 0。**原地钉主体大部分在保护区内，但模型把新地钉向原本属于背景的区域延长了。

因此，旧蒙版覆盖原地钉约 98%，只能说明原地钉多数像素有保护引导，不能证明新图不会向保护区外继续长出产品。即使补齐那约 2% 的边缘，也没有证据保证这种外扩会消失。这是“源产品覆盖率”与“输出产品轮廓不变”两种不同约束。

这条观察说明错误如何表现，并不单独证明网关忽略 mask 或模型内部的具体原因。当前可确认的是：原有标签数量错误已解除，几何变化仍在远端返回的原生图中发生。

### 3. 白柜：修复执行正确，错误已从漏选转为生成几何变化

本轮真实链路完整执行了：修订完整 `region_intent` → 采用封存提案 → SAM 整柜/脚垫两次查询 → 选择整柜、左脚垫、右脚垫 → 确认新蒙版 → 生图。

两只脚垫均在最终选区中，两个局部候选的归属均为 `cabinet_01`。没有旧蒙版冒用，没有只取左脚垫，也没有把原提案停在协议错误后直接接受旧状态。

输出保留了黑色短脚垫，修正了上一轮白色长腿问题；但右前脚垫轮廓明显增厚，柜体位置/高度也有轻微变化。变化在原生图中已经存在。

还检查了 `adjustable foot pads` 是否由分割查询凭空带入：原子体商品事实已有这一描述，因此**不能把该词判为本轮虚构事实并当作根因删除**。

本例已排除“脚垫修复没有续接”这一解释。当前责任边界是图片执行保真，不能继续靠重复跑 SAM 或修字段格式来解释/解决它。

## 三、本地请求传输是否出错：已做字节级离线复核

使用真实源文件、真实实际提示词、真实参数，调用当前 `_prepare_edit_inputs` 和 `_openai_images_edit_multipart_body`，在禁止联网的脚本中重新构造 multipart，再解析其各个字段。

三例均验证通过：

- 字段确实包含 `image` 和独立的 `mask` 文件；不是把蒙版当普通第二参考图。
- 重建发送图片字节 SHA 与实际回执 `sent_sha256` 相同。
- 重建发送蒙版字节 SHA 与实际回执 `mask_sha256` 相同。
- 蒙版 RGBA alpha 只有 0/255，与原蒙版逐像素相同；没有保护/编辑区反转。
- 原图与蒙版尺寸一致，三例图片均原字节发送，没有本地缩图、裁切或位置偏移。
- 原蒙版与发送蒙版 SHA 不同，是 PNG 重新编码造成；alpha 内容完全相同，不是保护内容被改了。
- 发送的实际提示词 SHA 一致；质量参数为 `high`，不是默认 `low`。

**这排除了当前本地串图、漏传 mask、反转 alpha、缩图错位、低质量参数等具体假设。**不代表已经获得第三方服务器内部传递 mask 的证明。

### provider 能力判断中的证据缺口

`core/api_registry.py:119` 的 `image_provider_supports_mask` 实际只检查：

```text
api_type 属于允许类型
并且配置 capabilities 包含 protected_mask
```

它没有检验远端是否保留产品形状，其 docstring 却使用了 `enforce an immutable pixel mask`，表述超过证据。

`core/provider_smoke.py:188` 的测试创建一张 **32×32 全透明蒙版**，要求返回一张正常图片；检查仅为非空且图片可解码。全透明意味着没有保护区域，这个测试无法验证任何区域保留效果。

当前三个回执也没有远端实际 mask 应用信息。它们的模型标识最多是网关自报，不能用同名模型、HTTP 成功或正确 PNG 证明远端的执行语义。

还发现证据边界：`core/image_provider_transport.py:298` 只投影 `model/id/created`；`core/image_response.py:436` 在完成后删除原 `.http` 包，保留图片及回执哈希。因此当前不能从原 HTTP 包追查是否曾有其他非图像诊断字段；也不能假设服务器一定返回过这些字段。此项是追溯限制，不是已证实的重绘原因。

**远端究竟忽略、转换了蒙版，还是实际模型只进行了不够严格的区域遵循，目前仍缺服务器侧证据。**这不是再跑几张普通商品图就能明确区分的事情。不能为了给一个确定答案而把其中任一猜测写成已查明的根因。

## 四、为什么修了很多次仍反复：此次执行方式和验收方式都有问题

### A. 本轮是重新出整张候选，不是只修旧候选的错误局部

三份 CandidateManifest 一致记录：

```text
revision_mode = initial
edit_parent_candidate_sha256 = ""
generation_references = 原图 1 张 + 独立蒙版
```

隔离脚本明确请求 `full_redraw`。合同修订导致任务身份改变，原候选不再属于当前任务；`core/image_generation.py:461` 因没有当前候选，将模式记为 `initial`，从源图重新执行整个场景/功能图编辑。

这不是误走文生图接口，仍然是图像编辑。但**修改范围只限于几个合同字段，并没有把模型此次生成范围限制在几个错误像素上**。整张产品图再次经过生成，之前看起来正确的部位也再次暴露于变化。

不能只把 `initial` 改名或硬选旧候选当作修复。旧候选已有错误，当前指纹隔离有真实用途；现有 `targeted_edit` 也会移除原图坐标的蒙版，避免把旧蒙版错误套到新候选上。直接换模式不是已验证的保真解决方案。

### B. 审计把局部症状作为下一轮唯一目标，漏掉旧的整体结构问题

白床旧图缺烟囱是实证。上一轮检查盯住引线和构图，下一轮只开放文案字段，又把旧 SAM 接受结果作为足够的保护依据。这样会形成“修好标签→发现结构→再改标签/蒙版”的循环。

今后同一张问题图的核查必须沿现有人工检查入口完整比较可见主体、结构、附属件、比例与文字，记录整个差异集合。不是增加一次模型 QA，也不是新增审批流程。

### C. 离线通过证明了事务正确，没有证明生成能力稳定

现有测试能验证字段事务、回执封存、候选绑定、额度和失败续接；生成器通常被替身模拟。`assert_acceptable_region` 主要验证归属和非空选区，完整视觉覆盖由原规划器判断。两个视图/非空实例存在，并不能证明每个附属件覆盖。

这些测试有用途，但不能用其通过来推断形状生成一定可靠。这一边界之前虽写过说明，实际整改决策仍反复依赖“合同通过后再整图生成看看”，缺少能区分不同原因的验证设计。

## 五、接下来应该针对哪一层，不能继续做什么

1. **白床修原规划/选区判断。**使用同子体已有身份事实，核对实际底图中可见的烟囱；在现有 `region_intent.parts` 或交互修正中补该部件。既有 10 个候选没有它，继续改候选排序无效。不要把功能文案需要表达的部分等同于整件商品需要保留的部分。
2. **白玫瑰和白柜先查执行能力，不再把 SAM 百分之百当作前提。**保留本次正确合同、蒙版与原生差异。用现有三个 remote request ID 定位网关侧实际模型、mask 转交及预处理信息；本轮没有联系第三方或发新请求。如果拿不到服务器证据，需要另行明确一组只改变一个因素的判别测试，不能用普通三图重跑假装排除了网关问题。
3. **普通商品重跑不能继续当根因定位工具。**若需要后续实验，固定源图、目标、尺寸、provider、模型和蒙版，只比较一个变量；先写清哪种结果支持或排除哪条假设。一次效果改善不能证明稳定保真。当前不执行任何新付费测试。
4. **修订验收表述和证据范围。**mask 参数可发送、规划接受、请求成功、局部问题改善、整图可用分别记录，沿用当前人工入口；不新增生产闸门、不自动删除旧候选、不放宽旧合同约束。
